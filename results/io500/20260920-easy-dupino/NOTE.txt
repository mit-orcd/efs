IO-500 ior-easy read-verify errors (76108 in 20260919-debug-9x4) + unremovable
ior-easy files: ROOT CAUSE = duplicate ino allocation on concurrent CREATE.

Repro (raw IOR easy geometry, 9 nodes x 4 ranks, 1 GiB/rank, -F -C -Q 1):
  tests/perf/io500/run.sh ior-easy-write 1024   (SLOTS=4)
  before fix: 36 files -> 10 DISTINCT inos (before-fix-inos.txt; 8 names on
              ino 4460). write 463 MiB/s. Inos step by 4096 = one shard's
              allocator handing out the same value.
  after fix:  36 files -> 36 distinct inos. write 902 MiB/s.
              ior-easy-verify (-r -R, cross-node): 0 mismatches, read
              1330 MiB/s eff (19 GB/s raw, open phase 25.8 s of 27.7 s).

Mechanism: server_raft_host_create peeks the alloc watermark on the
PROPOSER (efs_meta_apply_peek_alloc on applied state) and packs the ino into
the CREATE cmd; create_file_batch(want_ino) then used it unconditionally.
Two creates on one shard that peek before either applies (other voters,
forwarded creates) carry the same ino; the 2nd apply PUTs a fresh inode row
over the 1st's key -> two names, one row; both writers publish onto one ino
(mixed content = read-verify errors); first unlink deletes the row, sibling
dentries dangle (resolve -> I9 EIO; rm ENOENT; rmdir ENOTEMPTY).
Fix: meta_apply alloc_hint_or_next — hint honored only if >= watermark and
no row exists, else alloc_next_free; deterministic per replica. Same for the
mkdir same-group fast path. Gate: test_meta_apply test_create_log_at_dup_hint.
The hashed-create and mkdir txn paths CAS the alloc key and were never affected.

Leftover garbage on 19810 (dangling dentries, cannot be unlinked by design):
  /io500/easyv (26 names), /io500/2026.09.19-22.52.15/ior-easy (27 names).

Open cost noted (not fixed): open of a 1 GiB file = 0.2-0.8 s unloaded
(8192-row chunk-map adopt = 128 GETCHUNKS + 64-lane stat); 36 concurrent
opens -> 25.8 s. Spec §8 per-lane range fetch item.
