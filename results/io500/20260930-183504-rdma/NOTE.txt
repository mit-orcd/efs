What changed (all in this tree, commit after this run):
 1. Server identity of a span record is (object gen, off, len), not the
    gen alone. The object name is a content hash; two clients that merge
    to the same 128 KiB image PUT one object under two ranges. The apply
    took the second range as a replay ("same span object") and the REPORT
    pack skipped it as held (efs_meta_apply_chunk_holds) -> its bytes were
    never recorded. That is the ior-hard-read loss of every run today
    (40-208 records per run, always the client-boundary piece of a chunk
    shared by two hosts; the server row showed the peer's range under
    the missing client's object gen, e.g. ino 547783 chunk 238434:
    span off=25344 len=47008 gen=0xe990ec58f2c8212d = fcstor009's object,
    whose own piece was [0,25344)). test_meta_apply covers it.
 2. Client STALE classifier: a span is "committed" only if the row holds
    its gen at its range; a full image only if the base gen is ours; and
    a chunk the repull found NO ROW for is never "committed" - the local
    table's generation there is our own unreported PUT (pull_chunks_range
    returns an absence bitmap; the replay for an absent chunk starts from
    zeros with an empty observation and publishes our ranges / span /
    image with expected gen 0). This was the 41745-class loss: base CAS
    STALE against no row, then "committed == ours, done=1", dropped.
 3. First partial write into a chunk installs have_base/base_gen/range
    under the same lock as the buffer (dcache_init). A flusher between
    dcache_take and the second locked section saw dirty=1 nrange=0, PUT
    the buffer as a full image, and the merge overlay dropped the bytes
    (`snap-inner | dirty=1 hb=1 bg=0 obj=0 r=` in fcstor009's trace).
 4. span_of: contiguous coverage from the range start (a span extends
    cover only if it starts at or before it; head-uncovered + tail-
    covered folds instead of "covered"), and this client's own unreported
    span in the table covers nothing (one object per chunk in the REPORT;
    a tail-only publish replaced it in putid and its bytes never reached
    the host).
