perf annotate of stage_evict_main puts every hot instruction in the inlined
evict_pass() LRU scan (stage_evict.c:489–515): the loop over
g_lru_keys[0..g_lru_mask] / g_lru_ticks[] with the 256-entry cand[] replace-
worst (the `cmp $0xff` and the 16-byte `shl $0x4` indexing into cand[]).
That scan is O(LRU table) per band, up to 4 bands per wake, and the table is
sized 4× the staged-ino count (lru_ensure), so one wake reads 4·(4..8)·N slots.

Why it never stops: this is D18 (START-HERE, pending ask). The per-tab floor
of the staging table (~90–170 KB × up to 4096 tabs) sits above
EFS_CLIENT_META_MB = 256 MB before any row is staged; stage_bytes_now() is
therefore always > cap, every evict_pass finds 64 evictable rows (the ecopy's
just-closed files), evict_one() takes table_lock + idx_mu + dirty_mu 64 times
per band, efs_export_compact() runs under the table lock once per wake, and
efs_client_stage_evict_kick() (ops.c:192, on every staging op) re-arms the
thread immediately because the last pass did evict something
(g_evict_idle_until is only set when evicted_total == 0). The old
efs-fuse-efs-mount.log line "staging table over EFS_CLIENT_META_MB (256 MB)
with nothing evictable; growing" is the same condition seen from the other
side (all pinned). The Sep 30 fix 5ea397fd made each evict_one cheap; it did
not change how often the pass runs, and under a 400-thread ecopy that is
back-to-back.

Cost outside the evictor's own core: every RPC path takes the client table
lock; 64 evict_one() per band + one compact per wake serialize against them.
The evicted rows are the files ecopy touches next (utimens/rename/verify of
a just-closed file), so each is re-fetched (GETATTR/GETCHUNKS) — extra server
round trips per op. Not separately measured here; see next steps.

2. Hot path #2 — close of any file walks every chunk index of the file,
   dirty or not
---------------------------------------------------------------------
dcache_steal_dirty.constprop.0 is 36.9 % of the last slice with a broken
callchain (0x746e756f6d2d = "-mount", a libfuse worker without frame
pointers). Its body is the slot chain walk under two mutexes; it does not
copy the 128 KiB itself (that is memmove). The caller that can issue it at
that rate is the per-close path:

  ll_flush → efs_fuse_flush_ino → efs_append_flush_report (efs_fuse.c:2339)
  → efs_wb_sync_ino + efs_dcache_flush_ino → dcache_flush_ino_pass
  (write.c:4623): nci = ceil(size / 128 KiB) from the staged row, then
  for ci in 0..nci: dcache_steal_dirty(ino, ci)  (two mutex pairs + chain
  walk each), and dcache_flush_all_slots(ino, 1) — 65536 slots — once nci
  > 65536 (a file ≥ 8 GiB; dcache_flush_all_slots.part.0 at 3.5 % says such
  a close happened in run 2).

efs_append_flush_report has no "is anything of this ino dirty" predicate
(the utimens path added one on Sep 30: efs_fuse.c:2383,
`efs_client_ino_is_dirty(ino) || efs_dcache_ino_pinned(ino)`); ll_flush runs
on every close(2), including read-only opens — an ecopy --verify of a tree
with GB-sized files pays S/128 KiB chain walks per verified file, and every
dup'd fd pays it again. The same walk is on ll_fsync and ll_setattr(size).

3. Probable contributor — dcache slot chains are long
-----------------------------------------------------
efs_dcache_yield_extra (write.c:3735) is a single dcache_find() under one
shard lock and a flag clear, yet it is 6.6 % of the whole profile and 8.0 %
of the middle slice — the same share as dcache_steal_dirty. Both are chain
walks over g_dcache.e[s] (65536 head slots). A flushed full-overwrite entry
keeps a body-less node in the chain ("names a published chunk", write.c:3769)
and the reclaim path zeroes ino/data of a clean node without unlinking it
(write.c:4521–4527); dcache_store() reuses only an empty HEAD, never an
empty chained node; chained nodes are freed only by dcache_drop_locked
(truncate, adopt shrink, wb PUT). Hypothesis: after hundreds of thousands of
distinct (ino, ci) the chains hold many dead nodes and every find is a
pointer chase over them. Not proven by this data — the verification is a
one-line gdb walk (below).

5. Next steps (in order; nothing here is implemented)
-----------------------------------------------------
N1. Decide D18 (ask — already pending in START-HERE). This review adds the
    cost: with the floor above the cap the evictor is 32–48 % of client
    cycles under ecopy and re-arms on every staging op. Choices to put to
    the user, unchanged: count the cap against rows + arenas + chunk
    arrays only (exclude the per-tab index floor), or set the cap from the
    tab floor at startup, or both. Not a knob. Until decided, a
    measurement that isolates its cost needs no code: run the same ecopy
    once with EFS_CLIENT_META_MB=4096 in client.sh's environment (cap above
    the floor → evictor idle) and compare ops-by-fs.txt for the two runs.

N2. Close-path predicate (mechanical, same rule as the utimens fix): in
    efs_append_flush_report skip efs_dcache_flush_ino + REPORT when the ino
    has no wb pending, is not in the dirty set and has no pinned dcache —
    the three sources named in the "nothing to flush" learning. Then
    ll_flush of a read-only or already-published file costs three lookups
    instead of size/128 KiB chain walks. Gate: posix jobs=1 200/201,
    posix2 63/63, concurrent_appends, mtime_repro.py rows (the
    write→futimens→close ordering must still flush). Confirm the caller
    first: perf record --call-graph dwarf -p <efs-fuse> for 30 s of an
    ecopy --verify (fp callchains from libfuse workers are broken, see
    the 0x746e756f6d2d frames) and read who issues dcache_steal_dirty.

N3. Measure dcache chain length before touching it (gdb attach to the live
    efs-fuse, ptrace_scope is 0):
      gdb -p $(pgrep -x efs-fuse) -batch -ex 'set $n=0' -ex 'set $m=0' \
        -ex 'set $i=0' -ex 'while $i<65536' -ex 'set $e=&g_dcache.e[$i]' \
        -ex 'set $l=0' -ex 'while $e' -ex 'set $l=$l+1' -ex 'set $e=$e->next' \
        -ex 'end' -ex 'set $n=$n+$l' -ex 'if $l>$m' -ex 'set $m=$l' -ex 'end' \
        -ex 'set $i=$i+1' -ex 'end' -ex 'p $n' -ex 'p $m'
    after an ecopy of the software tree, and how many of those nodes have
    data == NULL. If the mean is in the tens, the fix is mechanical (reuse
    or unlink dead chained nodes in dcache_store / the reclaim path) and
    is gated by the same suites as N2. If it is ~1, drop §3.

N4. Only after N1–N3: a server-side trace of one ecopy (roll with --strace
    on one follower, one leader) to split the remaining per-op time
    between the client and the Raft commit; the reference per-op numbers
    are 0.3–6 ms idle, so anything left above ~10 ms at 5 in flight is a
    client-side hold.
