2. The publish path cannot keep up with the PUT path (the real finding)
------------------------------------------------------------------------
D24 kicks a REPORT every 8192 landed PUTs (every ~1.7 s here). One
REPORT at a time (`report_mu`), the flush thread serial. Server view
(fcstor004 + fcstor005 `report-split` lines, both dual hosts of the
files' lanes; fcstor00{4,5}/ana-log.txt):

  04:02:52  nrec=8193   pack 832 ms  push 668 ms  finish 2583 ms  fail=wait/-13
  04:02:52  nrec=8193   pack 285 ms  skip=8193 (identical resend to the other host) OK
  04:02:53  nrec=30526  finish 96 ms                              fail=act/-13
  04:03:03  nrec=30526  pack 566 ms  push 6.3 s   finish 1.5 s    fail=wait/-13
  04:03:04  nrec=30526  skip=30526 OK
  04:03:06  nrec=57520  pack 198 ms  push 928 ms                  fail=push/-15 (NOT_PRIMARY)
  04:03:28  nrec=68061  pack 4.7 s   push 15.4 s  finish 2.0 s    fail=wait/-13 (skip=5930)
  04:03:31  nrec=68061  skip=68061 OK
  04:04:20  nrec=124407 pack 12.5 s  push 34.0 s  finish 2.3 s    fail=wait/-13
  04:04:35  nrec=124407 pack 15.3 s  skip=124407 OK
  04:06:36  nrec=322395 pack 42.9 s  push 77.0 s  finish 481 ms   fail=wait/-14 (STALE)
  04:06:49  nrec=2048   (the STALE replay)                        OK
  04:07:31  nrec=569882 pack 13.9 s  push 26.4 s                  OK   <- the last closes

Three multipliers, in order of size:
  (a) pack = one point get per record on the server: 100-133 us/rec
      under this load (42.9 s for 322 k). The KV had l0=100-170 L0
      segments during the write (fcstor004 `kv-compact: end ... l0=`
      lines; the Oct 1 steady state was 50-54) and a point get probes
      every L0 whose range covers the key -> D26/D12 is not only the GC's
      problem, it is the REPORT's.
  (b) `fail=wait/-13`: the host proposed and committed every record,
      then its apply-wait (finish_ms up to 2.6 s) hit the deadline and
      answered BUSY. The client cannot tell a BUSY-after-commit from a
      BUSY-before and resends the identical REPORT to the other dual
      host, which packs it again (another 0.3-15 s) and finds every
      record held (`skip=all`). Every REPORT in this run but the last
      paid pack twice. The apply lag is the compaction storm:
      `apply-sleep` x31 on fcstor004, x103 on fcstor005 in the window,
      L0+L1 merges of 340 MB taking 3-5 s.
  (c) while one REPORT is in flight (6-120 s) the 16 writers keep
      marking chunks dirty, so the next snapshot is bigger: 8 k -> 30 k
      -> 57 k -> 68 k -> 124 k -> 322 k -> 570 k records. Publish
      throughput was ~2.7 k rec/s (322 k in 120 s) against a PUT rate
      of ~5 k chunks/s, so the backlog grows for the whole write and
      the last close() pays it: 74.6 s for dat16. This is the W41
      (decided) + D24 shape: D24 bounds what ONE file's close sends
      only if REPORTs drain faster than PUTs land.

What is NOT in this run: no duplicate records (the dirty set dedupes
by (ino,ci); 569 882 = 16 files' tails), no lost data (the STALE round
committed 320 347 of 322 395, replayed 2048), no election storm
(one NOT_PRIMARY at 04:03:06).

4. W44 step a -- the idle-hour reading (D26's input)
------------------------------------------------------------------------
Leaders, 150 min of `gc-pass` lines (fcstor003 = group 0, fcstor006 =
group 2; fcstor00{3,6}/ana-log.txt):
  fcstor003: 5534 passes, one per ~1.6 s, ms 430-740,
             fkeys=1 026 406  ftomb=1 026 149  femit=257  (constant for
             2+ h before the dd) = 3450 s of GC time = 38 % of a core.
  fcstor006: 6478 passes, fkeys=596 739  ftomb=596 482  femit=257
             (constant) = 2510 s.
So the pass's COST is tombstones under the GC prefix (ftomb = fkeys -
257), not the L0 count: the frag scan walks ~1 M dead keys to reach 257
live records every 1.6 s. Note (user, 05:30Z): femit=257 means these
are NOT empty passes -- live records were found each time. A pending-GC
watermark (D26 i) skips only truly empty scans and does not help while
those records remain; it needs bounded scan progress beside it. perf agrees: `merge_scan` + `__memcmp_avx2_
movbe` + `kv_seg_iter_next` + `kv_msrc_advance` + pread = ~90 % of
efsd cycles on both leaders, callers 100 % `host_gc_thread ->
host_gc_frag_pass` (fcstor00{3,6}/flat.txt, callers-head.txt).
After the dd: a compaction dropped the tombstones (fkeys 12 289 on 003
at 04:08Z, 121 089 on 006 at 04:19Z), then they grew again (003:
171 009 at 04:24Z; 006: 336 642 with ftomb +1024 per pass = the real
backlog of the run's superseded objects draining at ~512 records per
1.4 s pass). `gc-frag group=0 scans=1 records=126 ms=428` repeating
identically at 04:24Z is CONSISTENT WITH a set whose fragment deletes
fail every pass (`host_gc_record` "retry next pass", no ack) -- but
identical counts alone do not prove it (W50): record the identities,
each delete's verdict and the committed GC_ACKs first. Raft log tail before the stop: 99.7 % GC_ACK on
both groups, 5-6 commits/s per group (fcstor00N/ana-raft-tail.txt) --
this is what keeps `preflight.sh` reporting "not idle (>5 entries/s)".
D26 reading: option (i) (pending-GC watermark) addresses only truly
empty passes; here it must be paired with bounded scan progress and the
W50 result, and maintained atomically with record insert/remove and
recovery. The L0 width is a separate cost that shows up in REPORT pack
(2a), not here.
