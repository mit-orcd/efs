Mechanism
---------
1. `write()` is client-buffered (W2). The data reaches the server as a
   PUBLISH inside the REPORT at fsync/close, i.e. AFTER the utimens RPC
   that ecopy issued between the write and the close.
2. `efs_client_setattr` (ops.c ~1030) sends SETATTR; the server's
   `host_utimens` (raft_host.c:9212) sets the row's mtime, bumps
   `mtime_gen` and fences the lanes ("so a REPORT cannot stamp now over
   the set time" — that comment covers a REPORT that was proposed
   *before* the utimens).
3. The later PUBLISH packs `p.now = now_ns()` and `p.mtime_gen =
   row.mtime_gen` (raft_host.c ~10869/10894, the *current* gen). Apply
   (meta_apply.c:3467): `ln.mtime_gen == mtime_gen` → `max_mtime =
   max(max_mtime, p->now)`; stat (meta_apply.c:4175): lane gen ≥ row gen
   → `mtime = max(base_mtime 2013, lane now)` = now. The server cannot
   tell that the bytes were written before the utimens: the publish
   carries the publish time, not the write time.
4. Client side, `efs_client_mtime_pin` keeps the local row at 2013 (that
   is why the stat right after `futimens` and after `fsync` shows 2013;
   the pin is cleared only by a later write, write.c:4698); after close
   the client answers with the server's reduced row, and that is the
   publish time. `EFS_INO_REC_F_TIMES` (protocol.h:667, "apply mtime/atime
   even if older … piggybacks them on the close REPORT") is set by the
   client (write.c:827) and **read by nothing on the server** (`grep
   EFS_INO_REC_F_TIMES src/server` is empty); `irecs[].mtime` is used
   only for the size (raft_host.c:11225). Also `MTIME_PIN_MAX` is 256
   pins, silently dropped when full (write.c:307) — with 400 ecopy
   threads that alone would lose pins, but the repro shows the bug with
   one pin.

Consequences
------------
- Any tool that sets times on the open fd before close (ecopy, cp -p via
  futimens? — cp uses utimensat after close; tar and rsync set after
  close; ecopy, GNU `install`, some archivers set before) gets mtime =
  close time on efs. ecopy's incremental mode then re-copies the whole
  tree every run.
- Not a data problem: sizes and contents verified; only mtime.

Fix (recommended; not implemented; not F1/F2)
---------------------------------------------
A. **Client: flush before a time-setting SETATTR.** In the FUSE setattr
   path, when the mask has MTIME (or ATIME) and the inode has dirty
   dcache data, run the same flush the close would run (REPORT →
   publishes applied, lanes stamped with "now" under the OLD `mtime_gen`),
   then send SETATTR (utimens bumps `mtime_gen`, fences the lanes, stat =
   set time). Ordering is then the POSIX order. No wire or server change.
   ecopy pays the flush at futimens instead of at close (the close REPORT
   is then empty and is skipped, write.c:837), so no extra RPC. This is
   what NFS/CIFS clients do (write-back flush on setattr). Gate:
   `mtime_repro.py` rows 1–2 print 2013, posix suite's
   `mtime_monotonic_many_writes` and the utimens tests unchanged, and
   a second ecopy of an already-copied tree copies 0 bytes.
B. Alternative, server side: make the REPORT apply honour
   `EFS_INO_REC_F_TIMES` — after the batch's publishes, apply the rec's
   mtime/atime as a utimens (bump `mtime_gen`, fence lanes, cross-group
   lanes via the other group as `host_utimens` already does). Fixes the
   fsync-between case's window too, but it is a second utimens path in
   the apply and a per-REPORT extra entry; A is smaller and sufficient.

Either way the `MTIME_PIN_MAX` 256 cap should fail loudly or grow; a
dropped pin is a silently wrong local mtime until the next refresh.
