1. What landed (src/client/write.c, client_internal.h, node_cache.c)

W41: the dirty set is per inode (hash of inode sets), each REPORT takes
a per-inode publish slot instead of the client-wide report_mu; D24's
report_landed_note REPORTs are built and sent by a 4-thread meta-flush
pool (EFS_META_FLUSH_POOL 4, queue 64) so a close never waits behind
another file's 8192-record REPORT. close(2) of a file with nothing
unpublished still returns at once (65237a59).

D23: when a REPORT commits a chunk's full-image object
(dcache_note_committed, hit = object_gen == gen, entry clean, have_base,
base_gen != UNCOND) the dcache body is handed to the rdcache
(dcache_body_to_rdcache under the slot lock, efs_rdcache_put_owned
after it). The dcache keeps no clean full-overwrite bodies any more;
reads of just-written data come from the rdcache (bounded, evicting)
instead of an unbounded clean dcache.

2. Five gate passes — three bugs in the D23 placement, one in dcache_store

2.1 Pass 1 (p1g765): the wedge gate (4 x 8 GiB dd + 300-file storm)
hung the client. gdb (deadlock-gdb-threads.txt): the hand-off ran
inside dcache_flush_keep under the slot mutex and efs_rdcache_put_owned
-> rdcache_map_gen takes g_client.idx_mu, while efs_client_set_chunk
(holding idx_mu) -> efs_dcache_yield_extra wanted the slot mutex. Lock
order is idx_mu -> slot, never slot -> idx_mu. Fix: split into a locked
half that detaches the body and an unlocked half that puts it.

2.2 Pass 2 (p1g768, posix 20261002-123204 deleted): basic_overwrite_
middle / content_random_overwrite_append EIO, four posix2 pwrite tests
EIO. traces/tr769-new-*: a span-only row (table gen 0) made
efs_rdcache_put_owned refuse the image, the entry was left body-less
with have_base=1, the next partial write built a zeros+range "full
image", the server answered FOLD_LIST STALE, and the replay looped
(stale-class committed=0 forever). traces/tr770-old-* is the same test
on the old build for comparison. Interim fix: hand off only full-image
PUTs.

2.3 Pass 3 (p1g772): peer_shared_pwrite still EIO. dcache_store_owned
used dcache_find (matches only nodes with a body), so a body-less node
of the same (ino,ci) got a SECOND node; put-record (dcache_find_meta)
then hit the stale first node ("identity from staging table (putid
miss)", fold built from the stale delta list). Fix: dcache_store and
dcache_store_owned look up with dcache_find_meta and refill the
existing node (dcache_fill/dcache_take reset the object fields).

2.4 Pass 4 (p1g775): peer_shared_pwrite / peer_overlap_pwrite_same_range
still EIO; server log apply publish rc=-14 why=2 (BASE_CAS) exp=0
base_n=1 x129. traces/tr776-*: after a PUT-time hand-off the STALE
replay had no body and no ranges (30 identical stale-class rounds, no
snap-replay). The replay needs the body AND the dirty ranges until the
REPORT commits. Final form: hand-off at commit time only
(dcache_note_committed); dcache_flush_keep / flush_slot_inner keep
sites restored to dcache_install_image.

2.5 Pass 5 (p1g778) green: posix 200/201 (mmap_write_read SKIP by
spec; results/posix/20261002-130142), posix2 63/63 PASS
(results/posix2/20261002-130227), CMP_OK on both written files after a
remount, md_latency mkdir 3.2 / create 1.7 / append 3.4 / stat 0.2 /
unlink 0.6 / rmdir 3.1 ms.

READ THIS ROW BEFORE QUOTING W41 AS A WIN: with four 8 GiB dd's in
flight the 300-file create/close storm's p99 went from 37 ms (old,
Oct 1 reference 51 ms) to 100–128 ms on the P1 build, same host, while
the dd walls improved 9.7 -> 8.3 s and the storm p50 improved. The
mechanism is not established. Consistent with the evidence: each small
close now sends its own REPORT proposal and it queues behind the pool's
8192-record batch applies on the server (apply_max 60–85 ms during
those batches, fcstor006 raft-obs 06:01–06:08Z); on the old build the
small file's records rode along in whichever client-wide REPORT was in
flight. Alternatives not excluded: the commit-time rdcache put taking
idx_mu (only for full images — the storm's files are 1-byte spans, the
dd's are UNCOND full overwrites, so neither should enter it), or the
four pool threads' RPCs occupying conn-pool slots. Recorded as W53 in
START-HERE (observation, user decision), not fixed here.

5. Found on the way, not P1

W52 (new): a REPORT after thousands of O_APPEND writes answers after
>30 s. raft_host.c host_resolve_caught_up runs one serial
host_propose_wait per OPEN reservation at/below the published size,
AFTER the report-split log line and before set_inode_rc — N appends =
N raft proposals before the reply. The client times out at 30 s
(inode-rpc: retry type=67 why=recv rc=-6 recv_ms=30312), resends the
byte-identical REPORT, the server packs it again (skip=all), dd reports
"fsync: I/O error". Seen on BOTH builds (fcstor004 report-split
nrec=1133 06:03:30Z then skip=1133 06:04:01Z old build; nrec=625 x3 at
06:06:45/07:15/07:46Z new build). The reported size lags (completed
prefix) and converges: before-app-g765 148443136 vs after-app-g765
81920000, both files complete afterwards. ~5 ms per O_APPEND write.
Not a W41 regression (anomaly c of pass 1 resolved).
