# K122: A late REPORT copy can publish a superseded object over a newer one

- State: OPEN
- Blocks alpha: yes
- Kind: client, metadata / publication under retry

## Summary

- Cause: By reading: a REPORT record is guarded by its PUT ticket only; after a rewrite the old ticket is settled asynchronously, and a late first copy that arrives before the settle publishes the old object.
- Owners: `src/server/raft_host.c` (`server_raft_host_report`), `src/meta/meta_apply/publish.c` (`publish_ticketed`), `src/meta/put_ticket.c`, `src/client/write.c` (ticket settle)
- Reproducer: not determined (no test): hold a REPORT on a member, let its repeats fail, rewrite the chunk and publish it, release the held copy before the old ticket is settled.
- Invariant: Once a newer object of a chunk is published, no REPORT of an older object of that chunk can be applied.
- Owed: A reproduction (the order needs the old ticket still unsettled); then a guard that does not depend on the settle, or a synchronous settle before the newer publish; only then may a REPORT join the K106 (a) cut.

## Item

K114 fix 1 review (Nov 11, by reading, not run): Task FZ added REPORT with a publication id to the reply-wait cut on the claim that session, publication id and a compare-and-swap identify a repeat. The review found that REPORT records apply through `publish_ticketed`, where the only durable guard of a record is the state of its PUT ticket; the publication receipt on the host is in memory, per host and evictable. Order: a chunk is written (object X1, ticket T1) and its REPORT is cut and the repeats fail; the client rewrites the chunk (X2), marks T1 done and publishes X2; T1's settle is asynchronous. A late first copy that reaches a leader before that settle finds T1 admitted and publishes X1 over X2: the older data wins. After the settle the ticket floor answers STALE. The same order exists on devel after the 30 s timeout, without any cut
