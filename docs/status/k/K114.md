# K114: Reply waits outside the K106 (a) cut still last the 30 s timeout

- State: OPEN
- Blocks alpha: yes
- Kind: availability with one member unresponsive

## Summary

- Cause: Partly fixed in wave 81 (truncate, APPEND, CREATE_RETAINED). Still 30 s: the dual-voter path (MKDIR on a 2-group cluster, seen in batch R), REPORT, and the read sites of fix 2 (not merged yet).
- Owners: `src/client/node_cache.c`, `src/client/inode_rpc.c` (`rpc_reply_wait_cut`)
- Reproducer: `tests/test_k114_false_cut.py` (truncate, append, create: the request returns in about 6.1 s and takes effect once); none for the kinds still uncovered.
- Invariant: While one member hangs no operation in flight waits the 30 s transport timeout or fails, for every request type and on every transport.
- Owed: Task GC: fix 2 (getchunks, unpinned query; review items open) and fix 3 (dual-voter path). Then readdir and the views; an identity for chmod, chown, utimens, XATTR, HOLD, FLOCK; REPORT after K122; RDMA.

## Item

Wave 79 merge (Nov 11), split from K106 when its part (a) was fixed for the covered waits: the cut of a reply wait on a halted member applies only where a retry on another member is known to be safe, which is reads and the four directory mutations that carry an op-id, on TCP connections that go through `rpc_send_recv_shard_once`. Not covered, and still waiting the 30 s transport timeout: mutations without an op-id (SETATTR, APPEND, HOLD, REPORT_CHUNKS, FLOCK, XATTR set and remove, CREATE_RETAINED), RDMA connections, `rpc_send_recv_dual_once`, the other receive sites in `src/client/inode_rpc.c`, and the PUT, read and data-commit receives. A powered-off or partitioned host is not covered either: the probe's connect times out, the verdict is failed and not silent, and the wait stays 30 s; the same holds for a request whose deadline is less than 5 s away

## Disposition

OPEN, blocks alpha: yes (Nov 12, wave 85): [batch R](../2026-11/batch-r-rdma-reruns-20261111.md) showed a gap fix 1 did not cover: a MKDIR is sent on the dual-voter path (`rpc_send_recv_dual_once`), which lost its hook call in wave 81 together with REPORT, so on a 2-group cluster it waits the whole 30 s (client log `inode-rpc: retry type=45 ... recv_ms=30000 wait_ms=30013`; the intel1 live test routes mkdir on the shard path and passed). Fix 2 (getchunks and the unpinned query snapshot, Task GC) was reviewed: no behaviour bug, three wrong statements in its page and test; it is held and merges with fix 3 (the dual-voter path). Was: OPEN, blocks alpha: yes (Nov 11, Task FZ, merged in wave 81, [fix 1](../2026-11/k114-fix1-safe-repeats-20261111.md)): three kinds joined the cut after apply-level tests of a repeat in three orders and a live false-cut test: SETATTR that is a truncate (mask SIZE or SIZE with MTIME, truncate receipt), APPEND (append receipt) and CREATE_RETAINED with probe 0 (directory op-id window). On intel1 the request returned in 6.06 to 6.13 s instead of 30 s. Task FZ also cut REPORT with a publication id; the independent review found that a REPORT record is guarded by its PUT ticket only, not by the publication id, and that a late first copy can meet a superseded ticket that is not settled yet (row K122), so the merge took REPORT out of the cut again. The review also found the older defect of row K121. Was: OPEN, blocks alpha: yes (Nov 11, wave 80, Task FY, [design study](../2026-11/k114-uncovered-waits-design-20261111.md), by reading, nothing run): devel already sends every request type again after a failed receive, so a cut changes the timing and adds the false cut of a slow member. Safe with an identity that exists: SETATTR truncate (truncate receipt), APPEND (receipt), CREATE_RETAINED (directory op-id window), REPORT with a publication id. Not safe: chmod, chown and utimens (the op-id on the wire is not recorded in apply), XATTR set and remove, and FLOCK, where a delayed repeat can undo a later change. No fix task is started yet. Was: OPEN, blocks alpha: yes (coordinator's ruling at the wave 79 merge: it is the rest of K106, whose invariant is inside the one-member-down promise; the user may overrule): no fix; the list comes from Task FR's page and two reviews, by reading ([K106 (a) page](../2026-11/k106a-inflight-wait-20261110.md); [ledger](../2026-11/ledger.md))
