## Item

Task FB (found while diagnosing K38, Nov 10): the leader's ReadIndex contact `broadcast_read_probe` sends an AppendEntries with `prev_index 0` on each read round (about 1.5 per second in the K38 runs). A follower that has compacted (`snap_idx > 0`, every follower after its first compaction) rejects it in `on_ae_req` with `why=prev-compacted`, so the probe is never an acknowledgement there; `on_ae_rep` treats the rejection as a log mismatch, sets `next_index` to `snap_idx + 1` and re-sends up to 128 entries or 1 MiB the follower already holds, or a snapshot when that index is below the leader's log floor (`src/raft/raft.c`). Present in passing runs too; it does not change a REPORT result

## Disposition

FIXED, blocks alpha: no (Nov 10, Task FG, merged in wave 72): `on_ae_req` answers a zero-prefix read probe as a leadership acknowledgement on a compacted follower, and a probe ack that proves nothing new no longer kicks a batch (`src/raft/raft.c`); three new `tests/test_raft.c` cases fail before and pass after; private live arm on node9900 26,368 to 83 follower rejections in a 30 s read window; the guard's effect on write throughput was not isolated ([evidence](../2026-11/k103-read-probe-20261110.md))
