# K120: A blocking FLOCK that is sent again queues a second waiter

- State: OPEN
- Blocks alpha: no
- Kind: client, metadata / file locks under retry

## Summary

- Cause: By reading: the server queues a blocking lock request as an unbounded wait; a request sent again after a failed receive (today after the 30 s transport timeout) queues a second waiter for the same owner.
- Owners: not determined (the FLOCK path in `src/client/inode_rpc.c` and the lock wait on the server; see the design page)
- Reproducer: not determined (no test).
- Invariant: A lock request that is sent again never leaves a second waiter that can be granted the lock after its requester gave up.
- Owed: Find out whether a waiter is removed when its connection closes; a test with a halted leader and a blocking lock; then the fix or a published limitation.

## Item

K114 design study (Nov 11, Task FY, by reading): FLOCK carries the session and the lock owner only. A non-blocking request or an unlock that is repeated is a no-op in log order, but a delayed duplicate can take a released lock again or drop a live one. A blocking request is queued on the server as an unbounded wait; when the client sends it again after a failed receive, which devel does for every request type after the 30 s transport timeout, a second waiter is queued. Whether a waiter is removed when its connection closes was not determined
