# K38: ior hard shared-file write returns EIO after a STALE REPORT (W161)

- State: VERIFY
- Blocks alpha: yes
- Kind: data correctness / error resolution, alpha blocker

## Summary

- Cause: A retained overlapping span on an unchanged view made the host answer OVERLAP every round until the REPORT budget ended in EIO; `span_refused` now sends it to rebase (wave 70).
- Owners: `src/client/write.c`, `span_refused`, `stale_retry_owned`, `publish.c`
- Reproducer: `tests/test_k38_swept_hint_live.py`; the orcd-mini `ior hard` run (O1).
- Invariant: An application write must not get EIO on a healthy cluster.
- Owed: The orcd-mini `ior hard` rerun (O1) on a candidate with the wave 70 fix, and the user's acceptance.

## Item

**W161** ior hard (8 ranks, one shared file) on orcd-mini node9901, devel `5a7463440`, RDMA, direct I/O: `write()` returned `EIO` once (1 of 4 runs; node9900 0 of 1; passed on `d94ca85bf`). A REPORT answered STALE (`report-split stale=1 rc=-14`); the client's same-identity resolution gave `outcome=partial rc=-14 first_rc=-13`, retained the error as background pressure, and fsync/flush kept returning the stale generation until the file was removed. Hard write throughput also fell from 47.9 to 16–21 MiB/s ([deploy](../2026-10/orcd-mini-deploy-5a7463440-20261025.md))
