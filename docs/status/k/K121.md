# K121: A mutation the caller gave up on can still be applied later

- State: OPEN
- Blocks alpha: yes
- Kind: client, metadata / late execution after a failed retry

## Summary

- Cause: By reading: when a request is cut or times out and its repeats fail, the caller gets an error, but the first copy can run later; a truncate captures its preconditions then and can shrink data written since.
- Owners: `src/server/raft_host.c` (truncate path, no session check), `src/meta/meta_apply/append.c` (truncate receipt), `src/client/inode_rpc.c` (retry loop)
- Reproducer: not determined (no test): hold a truncate on a member, let the repeats fail, write more to the file, release the held copy.
- Invariant: A request whose caller was told it failed never takes effect later, or the caller is told the outcome is unknown and the file is not changed behind acknowledged writes.
- Owed: A reproduction; then a way to retire the identity of a failed truncate (APPEND has abandon) and a session check on the truncate path; the same question for the directory ops with an op-id.

## Item

K114 fix 1 review (Nov 11, by reading, not run): a request is cut (or, before the cut existed, timed out after 30 s) and the client sends it again. If the repeats fail too, for example because the cut member is marked down for 30 s and no other member can lead yet, the caller gets an error. The first copy is still in the halted or slow member and runs when it resumes. For a truncate the preconditions are captured when the copy is executed, so it can shrink a file that the application has extended since with acknowledged writes. The truncate path has no session check, so the copy of a client that was fenced meanwhile is applied too (chmod has such a check). APPEND closes this with its abandon step; truncate has nothing like it, and no site deletes a truncate receipt row. The exposure is older than the cut: devel has sent every request type again after a failed receive for a long time. The cut makes the repeat earlier, which closes the window when the repeat succeeds and records the receipt

## Disposition

OPEN, blocks alpha: yes (coordinator's ruling at the wave 81 merge: acknowledged writes can be cut off by an operation the caller was told had failed, and a member that is halted and resumed is inside the one-member-down promise; found by reading and not reproduced, so the user may overrule): no fix ([K114 fix 1 page](../2026-11/k114-fix1-safe-repeats-20261111.md); [ledger](../2026-11/ledger.md))

## Finding on devel
