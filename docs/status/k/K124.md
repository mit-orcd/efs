# K124: TSan: unsynchronized retire counters (finisher against recovery thread)

- State: FIXED
- Blocks alpha: no
- Kind: data race on statistics counters (TSan lane)

## Summary

- Cause: `host_txn_retire` did plain `h->dec_retired++` and `h->dec_retire_fail++` with no lock; the finisher thread and the recovery thread both call it.
- Owners: `src/server/raft_host.c` (`host_txn_retire`)
- Reproducer: TSan entry `k96_status_slots_live` on nuc, one lane of four (Task V4 fix round); raw `~/efs-artifacts/taskV4-20261111-c/10-tsan-run1-fail.log` on nuc.
- Invariant: Counters written by more than one thread are atomic; the sanitizer lanes carry no report.
- Owed: Nothing.

## Item

Task V4's fix-round TSan lane on nuc (Nov 11) failed the entry `k96_status_slots_live` once in four runs with a ThreadSanitizer report on `h->dec_retired` in `host_txn_retire`. An independent review at the wave 85 merge confirmed the race by reading: the finisher (`host_fin_thread` to `host_fin_one`, after `fin_mu` is released) and the recovery thread (`host_txn_recover_one` and `host_txn_decision_sweep`, outside `rec_mu`) both reach `host_txn_retire`, and `host_bg_propose` releases `h->mu` before it returns, so no lock is held at the increment. Write against write on a statistics counter that the product never reads (`tests/test_txn_decision_sweep.py` reads it). Task V4's diff does not touch that code; the same increment is on devel.

## Disposition

FIXED, blocks alpha: no (Nov 12, wave 85, coordinator's ruling: a statistics counter, no product reader, no effect on behaviour; fixed at the merge with two relaxed atomic adds). FIXED and not VERIFIED: the report came once in four lanes, so one clean lane does not prove it; raw on nuc, `~/efs-artifacts/taskV4-20261111-c/`, `SHA256SUMS` hash `2d0195f5869d6c6f` ([ledger](../2026-11/ledger.md))

## Finding on devel

FIXED, blocks alpha: no (Nov 12, wave 85): the two retire counters are atomic ([ledger](../2026-11/ledger.md))
