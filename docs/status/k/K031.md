# K31: Devel RDMA clients lose larger replies

- State: FIXED
- Blocks alpha: unstated
- Kind: correctness / transport, alpha blocker

## Item

**Devel RDMA clients lose larger replies.** On orcd-mini, freshly formatted, devel `bf16436e8` daemons healthy (both groups led, peers in sync), every FUSE client over RDMA (node9900 and node9901, mlx5_0, segmented-v1) stalls: small replies arrive, but the first reply of a few hundred bytes (a 453-byte INODE_GETATTR reply to a 21-byte request, server counters show it sent) never reaches the client; each reconnect repeats it, so LOOKUP/GETATTR time out at 30 s and mkdir returns EIO. The same client over TCP against the same cluster works (stat, mkdir). The last good RDMA build here was `d94ca85bf`; candidate changes since then include K28 (`EFS_MAX_NODES` 16, larger structs), K5/W72 session fields, W133 declaration gate and K16. Every Oct 22–23 sub-session gate ran over TCP, and RDMA unit tests are NOTRUN on hosts without RDMA, so nothing caught it.
