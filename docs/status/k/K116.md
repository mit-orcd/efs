# K116: After a restart older folded L0 values win over a newer flush

- State: FIXED
- Blocks alpha: no
- Kind: kv / LSM manifest order at load

## Item

W123 ports review (Nov 10, fork session): an asynchronous fold of L0 files takes its output file number after it released the store mutex, so a memtable flush in that window gets a lower number although its data is newer. Publication keeps the flush ahead, but `manifest_load` in `src/kv/kv_lsm.c` sorted L0 by file number, so after a restart the older folded values and tombstones answered before the newer flushed ones: stale metadata after a restart. `tests/test_kv_fold_reopen.c` overlaps a real fold with a flush, kills the process and reopens: on devel `67fc3b4a1` it aborts because the store returns the older value. It needs a fold at the file cap that overlaps a flush; how often that happens on a cluster was not measured

## Disposition

FIXED, blocks alpha: no (Nov 11, W123 port `c88fa14ec`, merged in wave 79, [page](../2026-11/w123-ports-20261110.md)): the order recorded in the MANIFEST is the L0 order at load. An independent review traced every writer of the manifest and every reader of L0 order and found the fix complete; levels below L0 are not affected. A store that restarted on an older build after such an overlap keeps the wrong order (nothing can detect it); no such store is kept. Tests `tests/test_kv_fold_reopen.c` and `tests/test_kv_manifest_order.c` ([ledger](../2026-11/ledger.md))

## Finding on devel

FIXED, blocks alpha: no (Nov 11, wave 79): MANIFEST order is the L0 recency authority at load; the reopen test fails on devel `67fc3b4a1` and passes ([ledger](../2026-11/ledger.md))
