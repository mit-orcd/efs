# K113: Snapshot rejoin never completes under sustained load (import restarts)

- State: OPEN
- Blocks alpha: yes
- Kind: server / Raft snapshot rejoin under load

## Summary

- Cause: A rejoining member restarts its snapshot import for every newer snapshot and never finishes under sustained load (108 and 202 imports started, none completed in 300 s).
- Owners: `src/server/raft_host.c` (`host_snap_chunk`, `host_snap_import_pump`), `src/raft/raft.c` (`on_snap_req`, `efs_raft_snap_imported`)
- Reproducer: `tests/test_k22_snapshot_import.py` on devel plus the K109 fix (tree `1fc8e9211`, branch ref `wave76-fo`); it passes on devel, where K109 throttles the load.
- Invariant: A member that fell behind can rejoin under sustained load: a follower holding a complete image finishes importing it and does not restart for a newer one.
- Owed: A third fix round: an image must not be imported once the member has applied past it, and a member that became leader must not be left with the image; rounds 1 and 2 are on ref `wave77-fu`, not in devel.

## Item

Wave 76 merge gate (Nov 10, fstor007 and node9900, tree `1fc8e9211`: devel plus Task FO's K109 fix): `tests/test_k22_snapshot_import.py` failed on both hosts, `no InstallSnapshot on node 3 within the bound` (300 s). After the stopped member resumed it started a snapshot import 108 times (fstor007) and 202 times (node9900) and completed none. The leaders took a new snapshot every 1 to 2 s (166 and 177, 317 and 370 snapshots per leader in the run; the test sets a 1 MiB snapshot window), and every newer snapshot that arrives restarts the follower's import, whose opening alone took about 1.8 s for 1.8 million keys. The test passed in waves 74 and 75 only because, with one member stopped, every clean unmount of its load waited 15 s (K109), which throttled the load; with the K109 fix the load is many times higher. The defect itself is in devel without that fix: a member that must rejoin by snapshot never does while the leader produces snapshots faster than one import completes

## Disposition

OPEN, blocks alpha: yes (Nov 11, wave 79): a fix exists and is not in devel. Round 1 (Task FT) refuses a newer image while an import runs and lets the pump install the finished one; on fstor007 the K22 test failed 3 of 3 on the base and passed 3 of 3 with it. Round 2 (Task FU) repaired four review findings. The verification review of round 2 found no proven defect but two unsettled cases, both reached only by a delayed append: an import that is still queued while the member applies past its index is then written over the newer store before the install is refused, and a member that wins an election during an import keeps the image without installing it. The base wedged in the first case; the fix must drop such an image instead. Refs `wave77-fu` (fix) and `wave77-base` are kept; the K109 fix is held with them. Was: OPEN, blocks alpha: yes (coordinator's ruling at the wave 76 merge: a member that fell behind must be able to rejoin under sustained load, and at production caps a leader under a steady create load snapshots every few minutes while an import of ten million keys takes longer): not fixed; direction: a follower that holds a complete image finishes importing it and does not restart for a newer one.
