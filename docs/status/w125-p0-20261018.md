# W125 P0 — allocation and cost go/no-go for small-file packing — 2026-10-18

**Verdict: conditional GO for option (a) with singleton segments plus
background merge compaction.**
- **Space:** a packed singleton costs 8,749 bytes per node on XFS against
  71,241 today (8.1× less, measured). After merging into full segments it
  falls to about 175 bytes of segment space per 256 B file (modelled).
- **Throughput and close latency:** unchanged by construction, if
  publishing a singleton costs no more than today's close. That cost is
  the condition: at 1.5× of today's close, 16-worker throughput falls 16%;
  at 2×, 28%. It must be measured on the first working prototype before
  the port goes further.
- **Windows:** seal windows only hurt this workload. Every writer waits on
  its own close, so a window adds latency and coalesces nothing a
  directory-keyed cohort could use.
- **Metadata cost:** today is about 4.0 Raft entries per file. Packing adds
  one more per file (segment admission plus publication instead of one
  publication), +25%, unless the two are fused into one entry for
  singletons. Compaction's switch is amortised over hundreds of records;
  retiring the singletons must be batched (W124-style).

Plan: [W125 implementation plan](../backlog/small-file-packing-plan.md),
phase P0. Design: [W125](../backlog/small-file-packing-default.md).

## Workload and captures

`scripts/w125_p0_capture.py` replicates the user's `tiny_files.py`
`create_folder` logic:
- folder depth draw (up to 8), files named `file_NNNNNN.txt`;
- sizes uniform from 1 to 512 B (mean 256 B), built from 512-byte base64
  blocks;
- open (`O_CREAT|O_EXCL`), write, close, no fsync unless asked;
- one worker per folder at a time, 2 × workers folder tasks queued.

It records every file's open, write, fsync and close times per worker.

## Closed-loop model of option (a)

`scripts/w125_p0_model.py` replays each worker's captured file sequence.
- **Causality:** a worker's next file starts only when its close returns.
  Close waits until its segment seals, then pays one publication, sampled
  from that run's measured close times × `PUBLISH_SCALE`.
- **Seal conditions:** window, 512-record cap, 128 KiB byte cap, or an
  fsync, which seals its cohort at once.
- **Grouping keys:** `dir` = (publication group, folder); `session` =
  (publication group).
- **Compaction:** after the run, merging folds every segment under 8
  records into full segments.

**Sensitivity to publication cost** (r1, window 0):
- at 1.5×: 2,054 files/s, close p50 3.15 ms;

For r2 the figures are 463 and 397 files/s.

**Compaction copy volume:** about 256 B of payload per file. Merging is a
read and rewrite of tiny records, which is small next to the 8 KiB
singletons it frees.

## Metadata (Raft) cost

- **Today:** the cluster committed 681,338 entries for 170,000 files (and
  677 directories), about 4.0 per file. That covers create, the lease's
  open and close edges, and the data publication. Group 0 took 88% of them,
  an imbalance worth a separate look.
- **Packing, singleton per file:** segment admission plus publication, 2
  entries instead of today's 1 publication, so +1 per file (+25%), unless
  admission and publication are fused for singletons.
- **Merge:** admission and switch per merged segment, about 2 entries per
  ~400 records, negligible.
- **Retiring the merged singletons:** one entry per file if done one at a
  time (the model's conservative count, 3.0 per file in total). With
  W124-style batched retirement it is close to zero.

## Proposed P0 decisions (for review)

1. **Close contract:** option (a), close waits for publication, with **no
   seal window** (window 0): every file whose close arrives alone gets its
   own singleton segment. Windows are rejected for this workload: they add
   close latency and reduce throughput without useful coalescing.
2. **Lifetime grouping moves to compaction.** At write time the cohort is
   effectively the file. Rule 1 (pack files that die together) applies
   when singletons are merged: merge singletons from the same publication
   group, directory subtree and creation epoch, so that merged segments
   still empty together on tree deletes.
3. **Compaction is mainly merging.** Singletons dominate, so the first
   compaction policy is "merge segments under N records into full cold
   segments". Retirement of the merged sources is batched through W124's
   journal. Hole compaction (live share below *t*) follows the same path.
4. **Threshold:** the space win holds across the candidates (8.5× at
   ≤ 4 KiB down to 1.7× at 64 KiB). Proposed initial threshold: 16 KiB
   (4.25× as singletons). 32 and 64 KiB stay candidates once the prototype
   measures read amplification and metadata cost. This needs raising the
   archived 4 KiB record limit, a versioned format change (plan gap 8).
5. **Fuse admission and publication for singletons** to avoid +25%
   metadata per file. If that is not possible, accept +1 entry per file and
   record it.
6. **The first prototype measurement is the singleton publication cost
   against today's close.** It is the condition for GO. Throughput loss
   above about 10% at the user's workload is NO-GO for this close
   contract.

## Limitations

- The publication cost of a packed singleton is modelled from today's
  close, not measured. The archived code was not run.
- The merged-allocation figure counts segment space only. It excludes the
  per-record metadata, references and ledger, about 129 B per record in
  the archived format, which lives in the KV.
- One run per configuration; the workload is synthetic (the replicated
  `tiny_files.py`), without the user's concurrent md5 reader and crawler.
- The filesystem measurements are on node9901's `md0` XFS. orcd-mini's
  `/data1` is also XFS on a different device.

## Reproduce

On node9901, with the scripts from `scripts/`:

```sh
scripts/w125_p0_cluster.sh start REL /tmp/w125-p0/run 17670
python3 scripts/w125_p0_capture.py /tmp/w125-p0/run/mnt/r1 --workers 16 --max-files 100000 --out r1.csv
python3 scripts/w125_p0_capture.py /tmp/w125-p0/run/mnt/r2 --workers 1  --max-files 20000  --out r2.csv
python3 scripts/w125_p0_capture.py /tmp/w125-p0/run/mnt/r3 --workers 16 --max-files 50000 --fsync 10 --out r3.csv
python3 scripts/w125_p0_model.py r1.csv          # and r2, r3; --publish-scale 1.5 / 2.0
python3 scripts/w125_p0_alloc.py DIR --layout today  --file-bytes 69632
python3 scripts/w125_p0_alloc.py DIR --layout shared --file-bytes 8192
scripts/w125_p0_cluster.sh stop REL /tmp/w125-p0/run 17670
```

`REL` is a build of devel `65245d73f` (`efsd`, `efs-fuse`, `efs-mgmt`,
`scripts/client.sh`). Prerequisites: free ports 17671–17673, `mlx5_0`, the
private libfuse, and an XFS scratch filesystem. Remove the run directory
and the alloc directories afterwards.
