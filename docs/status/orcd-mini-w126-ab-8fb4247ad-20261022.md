# W126 on orcd-mini: deploy of `8fb4247ad` and A/B against `47ba6b590` — 2026-10-22

**Verdict (W126 gates):**
- **Lock-wait gate PASS:** leader LSM lock waits are 2–4× lower at
  matched points.
- **Create-rate gate FAIL (no measurable gain):** creates/s followed the
  run order (A 736, B 598, A' 551 at 0.9 M), not the build.

On this cluster, create throughput is bounded elsewhere: the leader's

## What was tested

- **`f36b17ea8`, step 1:** read-only peeks at writer-owned LSM state take
  `mu` only, not the exclusive `view_rw`. This covers the batch flag check,
  REPORT `l0_hot`, stats and the query revision reads.
- **`8fb4247ad`, step 3:** a memtable flush writes and fsyncs its L0 files,
  then the MANIFEST and the WAL reset, with the exclusive view yielded. Only
  `mu` is held during that time. The exclusive view is retaken only to
  publish the L0 slots and to clear the memtable. A flush of 100 ms or more
  logs `kv-flush: files= io_ms= manifest_ms= view_yielded=`.

## A/B method

Environment: orcd-mini, three efsd on node9901 (ports 17432–17434), RDMA
mlx5_0, direct I/O, quota 720 GiB per node; client on node9900. The cluster
held the user's `20m-tiny-files` (~5.67 M files) throughout. The W125 packer
was backfilling at 550–800 files/s, as it was during the original profile.

Each run was the user's exact command into a fresh directory:
`tiny_files.py --max-depth 2 --max-files-per-folder 1000000 --max-files
32000000 --workers 16`. Capture points fired when the writer's `syscw`
reached 0.9 M and 1.7 M; the writer makes one write per file. The order was:
- A: `8fb4247ad`, run `w126-ab2`, points r1 and r2;
- B: `47ba6b590`, run `w126-ab3`, points b1 and b2;
- A': `8fb4247ad`, run `w126-ab4`, point a1.

The leader's DWARF capture followed the node whose own raft-status said
`role=LEADER`.

| Point | Build | Creates/s | Leader LSM lock waits (share of switches) | `apply-sleep` per ~90 s (mean / max) |
| --- | --- | --- | --- | --- |
| r1, 0.9 M | `8fb4247ad` | 736 | 1.6% | 4,300 (44 / 288 ms) |
| b1, 0.9 M | `47ba6b590` | 598 | 13.6% | 2,715 (57 / 400 ms) |
| a1, 0.9 M | `8fb4247ad` | 551 | 6.0% | 3,365 (45 / 400 ms) |
| r2, 1.7 M | `8fb4247ad` | 595 | 5.4% | 3,209 (43 / 676 ms) |
| b2, 1.7 M | `47ba6b590` | 531 | 20.9% | 2,113 (50 / 330 ms) |

Reading:
- **LSM lock waits** are lower with W126 at both file counts: 1.6–6.0% vs
  13.6% at 0.9 M, and 5.4% vs 20.9% at 1.7 M. After the fix, the remaining
  LSM waits are mostly `kv_get_copy` gets and packer scans.
- **Create rate** declined in run order, A > B > A'. The drift from a
  cluster that keeps growing (about 8 → 12 M files over the runs) is larger than
  any build effect, so no throughput gain is shown.
- **Leader waits after the fix:** at r1, 421 of the apply thread's 1,102
  DWARF switches waited on `h->mu` in `host_pump`, and 15 on the LSM view.
  Proposals and REPORT dominate the `h->mu` waits, as before. Other leader
  waits are XFS log waits (`xlog_wait_on_iclog`, `__wait_for_common`) from
  Raft and GC fsyncs.
- **Flushes** log 26–37 L0 files with 117–160 ms of I/O per flush, with
  `view_yielded=1`. Readers no longer wait through that time.

## Other observations

- A first A/B attempt capped at `--max-files 3000000` was invalid. With
  1–1 M files per folder, it created only about 7 folders, so the 16
  workers ran out of work. Its rate (591 → 213/s) is a property of the test.
- In a small directory, creates take 1.07 ms p50 on `8fb4247ad`. In a
  directory past the split threshold they take 1.8 ms p50. The writer's
  ~75 ms per file therefore comes from queueing under load, not from per-op
  cost.

## Limitations and remaining work

- Single 3–30 s snapshots per point, one run per build, uncontrolled
  background packing and GC.
- W126 step 4 (bound how long a scan holds the shared view) is not done.
  The residual LSM waits (1.6–6%) do not justify it now.
- Create throughput on orcd-mini is now limited by the leader's `h->mu`
  ([plan](raft-host-mu-plan-20261016.md)) and fsync waits. W126 does not
  address these.
- The user's 32M-file run is stopped. To continue, `--resume` validates
  every existing file and refuses a zero-length file. The SIGKILL can have
  left up to 16 of them in folders that were being written.
