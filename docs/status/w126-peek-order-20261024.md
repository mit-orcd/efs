## Purpose

Peeks (`lsm_peek_lock`: the apply's failure-flag check, REPORT's
`efs_kv_lsm_l0_hot`, stats, segment counts, query-refresh revisions) took
`mu`. A writer (Raft apply, flush, the compactor's first `lsm_lock`, a
cond-wait return) takes `mu` and then waits on `view_rw` for in-flight
readers. While it waited, every peek waited on `mu` behind it, so a peek
lasted as long as the longest reader. Metadata latency on busy leaders
matters for W159 (metadata RPCs of 2–7 s on a loaded four-member fixture).

## Change

Commits `71f6ef24e` (fix and tests) and `680a7d0dd` (storm loop pacing,
test only) on `claude/devel-w126-peek-8a1155`, based on `merge-wave2`
`3e01ba95c`. Gated source: `680a7d0dd`. The build ID reads `unknown`
because `git archive` copies carry no `.git`; the source identity is the
commit. Files: `src/kv/kv_lsm_internal.h`,
`src/kv/kv_lsm.c`, `tests/test_kv_lsm.c`, `tests/leak_check.sh`.

- New non-recursive `peek_mu`. Lock order: `mu`, then `view_rw`, then
  `peek_mu`. A writer holds `peek_mu` exactly while it owns `view_rw`
  exclusively. Its outermost `lsm_lock` takes it after `view_rw`, and
  `lsm_unlock` drops it first.
- Peeks take only `peek_mu`. They no longer wait for a writer that holds
  `mu` but is still queued on `view_rw`. They wait only while a writer owns
  the view, which is when peeked state can change.
- `lsm_view_yield` (flush file I/O, W126 step 3) drops `peek_mu` with the
  view, and `lsm_view_reclaim` retakes `view_rw`, then `peek_mu`. Peeks
  therefore also run during the flush I/O. The yielded flush changes
  nothing a peek reads; it only advances `next_seq`, which no peek reads.
  The MANIFEST write and the WAL reset only read LSM state.
  `lsm_cond_wait`/`lsm_cond_timedwait` release and retake `peek_mu` the same
  way.
- A writer that owns the view already holds `peek_mu`, so its own peeks do
  not lock. A yielded owner locks `peek_mu` like any thread (per-owner
  `yielded` flag).
- A peek inside a read section is now safe (`view_rw` shared, then
  `peek_mu`; no `peek_mu` holder can be waiting for that reader), so its
  fail-fast abort is removed.
- Unchanged: writer preference on `view_rw`
  (`PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`), `mu` serialisation of
  writers, flush and compaction exclusivity, MANIFEST publication, and
  reclamation of segments after the last pin. Readers never take `mu` or
  `peek_mu`.

Options not taken:
- Publishing an immutable view (RCU or refcount) would touch every writer
  of the peeked fields.
- Taking `view_rw` before `mu` deadlocks against yield/reclaim and cond
  waits (K30 §3).

## Tests

`tests/test_kv_lsm.c`:
- `test_peek_beside_reader` (the K30 pinned case, now a liveness test) runs
  four modes. Mode 0 has no writer. Mode 1 has a plain `lsm_lock` queued on
  `view_rw` behind a parked reader while it holds `mu`. Mode 2 has a flush
  that yielded and now retakes the view behind the reader. Mode 3 has a
  writer parked in its yielded file-I/O window. In every mode the peeks must
  return within 5 s while the reader is parked and the writer has not got
  the view. The reader's callback also peeks (inside a read section). The
  writer peeks while yielded and while it owns the view. Each peek checks
  one consistent cut (`n_l0 == 0` iff `l0_bytes == 0`).
- `test_peeks_during_flush`: two peekers and one reader loop while the
  main thread writes 12 rounds of 64 rows and flushes each round, with the
  compactor stopped. Every peek must see a consistent cut, the reader must
  keep its row, and the peekers must advance across every flush.
- `test_peeks_during_compaction`: the same, with a compaction after each
  flush and the background compactor running (manifest swaps under the
  peeks). `EFS_ERR_BUSY`, meaning nothing left to merge, is accepted.
- `make leak-check` no longer sets `EFS_TEST_KV_SKIP_PEEK_LIVENESS`; the
  variable is gone.
