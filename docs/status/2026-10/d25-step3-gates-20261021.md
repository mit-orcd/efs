## What changed

| area | change |
| --- | --- |
| entry | `EFS_MD_CMD_TRUNCATE` with exactly 86 B (§1.2): kind, ino, inode_gen, expect_epoch, expect_base_size, size, mtime_ns, opid; every other length is still the eager entry |
| apply | `efs_meta_apply_truncate_lazy`: receipt lookup before preconditions; acknowledged identities STALE; preconditions STALE/BUSY/INVAL with nothing written; receipt encoded before any effect (full window → BUSY, never unrecorded); one batch: inode row, closed cursor, receipt, and for a shrink the pruned history entry and `TRUNC_PENDING` |
| history | format 2: `revision`, per-entry `done` lane bits; `efs_fence_history_append_pruned`; format 1 refused |
| KV | kinds 47 `TRUNCATE_RECEIPT` (inode shard, per session) and 48 `TRUNC_PENDING` (anchor shard), validated by `efs_meta_apply_check` |
| handler | `host_truncate_lazy`: ReadIndex capture, coherent lane EOF collect, classify, propose, STALE/BUSY retried under the same opid (16 tries) |
| wire | SETATTR SIZE carries the opid suffix; forwarding keeps it |
| client | SETATTR SIZE takes an opid and retries NET/NO_QUORUM/BUSY under it; with the flag set, no tail rewrite before SETATTR and the boundary chunk's map and caches are dropped |
| lagging lanes | append capture and its plan validator, and the utimens plan, adopt a lane behind the inode epoch instead of refusing it; the packer skips inodes with a fence history or a lagging lane 0 until masked packing (step 4) |
| masked base | REPORT refuses a full image CAS over a base masked in this chunk unless built from a view at the current epoch; the STALE replay no longer republishes its whole buffer over a masked base of its own object |
| faults | `EFS_FAULTS=1` only: refuse before propose, refuse at apply, commit then lose the reply once (delay in ms) |

## Findings

1. **g3 failure is a pre-existing client bug, reproduced on the baseline.**
   Shape (`D25_ONLY=repro`): B writes `[59346, 317424)`; A extends, then
   truncates to 0; B writes `[139501, 427895)`. Chunk 1 bytes
   `[131072, 139501)` must read zero and instead show B's earlier data.
   Client trace: B's cached chunk image has base `EFS_CHUNK_BASE_UNCOND`
   (B wrote the whole chunk itself); the partial write merges into that
   cached image and republishes it as an unconditional full overwrite, so
   the server accepts it over whatever the row is now. The unchanged
   release fails the same repro (eager path; there A and B even disagree).
   Lazy truncate does not cause it; it does not fix it either. A fix needs
   the client to tag such images with the inode epoch they are valid for
   and the server to refuse an older one; it is not in this commit.
2. Two masked-base paths were closed on the way (REPORT CAS check, STALE
   replay); neither turned out to be the g3 cause. They have no isolated
   unit test yet; the gate covers them only indirectly.

## Limits and remaining gates

- No sweep yet: rows past a shrink stay until step 4, `st_blocks`/`df`
  do not drop, and a file can reach the 32-entry history bound (BUSY until

- The decode refusal is a proposer verdict (PROTO), not yet the fatal
  apply stop §1.3 asks for.
- Receipt exhaustion and the acknowledged-duplicate case are covered by
  unit tests only (hard to drive through FUSE).
- One run per configuration; TCP only; no RDMA.

## Addendum — stale-cache republish fixed (October 22)

**Verdict: g0–g4 PASS (`step3g`); the repro passes on the eager and lazy
paths of the fixed tree and still fails on `47ba6b590`.** Source: the
commit that adds this addendum; the trees built for these runs match it
except docs.

### Fix

| part | change |
| --- | --- |
| server replies | getattr and truncate replies carry the inode's content epoch in the former always-zero `efs_inode.reserved_ino` slot (`content_epoch`, layout unchanged; the client table copies it) |
| client epoch table | `efs_client_epoch_note`/`_get`: last epoch per inode from getattr, SETATTR SIZE and every GETCHUNKS reply (also empty ones); leaf locks; a miss reads 0 |
| formation epoch | each dcache slot keeps `image_epoch`: the epoch when a whole-chunk image was written, or the view epoch of a base fetched by the STALE replay |
| tagging | an UNCOND whole image published without a fetched view carries `image_epoch` as its captured epoch; the server's existing captured-epoch check answers STALE once the inode moved on; the replay overlays only this client's ranges on the fresh (masked) base |
| absent-entry drop | the step-2 GETCHUNKS absence rule no longer drops an entry that is this client's own unreported PUT (putid or dcache object, the STALE classifier's own identity sources); dropping it made the classifier skip the chunk as "truncated away" and left the write unresolved |
| gate script | a refused clean unmount (unresolved writes) is a FAIL and is force-discarded; a run refuses to start over a live leftover mount |

`efs_meta_stat` is unchanged: it is a persisted query-catalog row
(`test_query_disk` row size 312), so the epoch is read from the row when
the reply is filled.

### Limits

- The epoch table is lossy (4096 slots); a miss tags epoch 0, which costs
  one STALE round trip on a file whose epoch is above 0, not correctness.
  Not measured under a many-file workload.
- The eager path now also STALEs an UNCOND image formed before a peer's
  truncate; that is the fix, and it adds a round trip only in that case.
- RDMA, fault injection beyond the truncate hooks, and multi-client
  stress are not covered by this run.
