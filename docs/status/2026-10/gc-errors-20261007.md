# Xorinox GC error investigation — Oct 7, 2026

Roadmap follow-up for W63 (GC observability), with W61/W62 retry semantics preserved.
Read-only investigation; no code changes or daemon restarts.

## Observations

The portal's two errors are both cumulative `reap_errors` on xefs3, deployed
build `cb5e86de`. xefs1 and xefs2 report zero errors. On all three nodes,
`delete_errors`, `sweep_errors`, `ack_errors`, `scan_errors`, and checksum
`mismatches` are zero in the inspected snapshot.

In xefs3 `/data1/efsd.log`, the first counter increment occurred between
16:35:05.683 and 16:35:21.690 UTC; the second between 16:39:05.788 and
16:39:21.792 UTC. These are observation windows, not exact failure timestamps.
The count stayed at two while GC continued. At 19:12:31.272 UTC xefs3 had
8,908 passes, 361,366 removed fragments and zero sampled pending/reap queues.
A later portal snapshot has 9,145 passes and still two errors. The currently
sampled leaders are xefs3/group 0 and xefs1/group 2; both report zero pending,
reap and orphan counts. xefs1's unsampled group-0 estimate of 159,124 is stale
follower telemetry, not evidence of a current leader backlog. Empty sampled
queues do not establish historical lost-ledger reconciliation.

## Code trace and limits

Inspected deployed `/tmp/efs/src/server/raft_host.c` and
`/tmp/efs/src/meta/meta_apply.c`, rather than assuming current development code
was deployed. `host_gc_propose` (deployed raft_host.c:5931) increments
`gc_reap_errors` on every non-OK result for either `ORPHAN_REAP` or `REAP_DONE`.
These are metadata/Raft proposal outcomes, not the fragment-unlink counter.

`host_gc_orphan_pass` discards the return after accounting for it; it emits no
operation/inode/return-code failure diagnostic. `host_gc_reap_pass` logs its
REAP_DONE proposal result only when `EFS_GC_DBG` is enabled. The captured log
contains no corresponding detailed reap failure. Consequently neither the
command nor the return code of these two events can be recovered from the
available evidence; an exact root cause remains unproven.

There is a concrete accounting problem: `efs_meta_apply_orphan_reclaim` calls
`efs_meta_apply_reclaim`, which intentionally returns `EFS_ERR_BUSY` for a
remaining lease or transaction conflict. Transport/apply waits can also return
non-OK outcomes. The current counter aggregates deferrals, retryable proposal
failures and hard failures. A legitimate BUSY therefore appears as a GC error.
Persistent orphan/reap records support later retries; the observed drainage is
consistent with recovery, but does not prove which two objects retried.
Do not weaken lease, transaction or generation checks to suppress the count.

## Required roadmap follow-up

- Split expected orphan deferrals (lease/transaction BUSY) from retryable
  proposal failures and hard metadata/storage failures. Classify at the layer
  that knows the reason; do not blanket-ignore all BUSY or non-OK results.
- Add bounded/rate-limited diagnostics for both reap commands: node/group,
  operation, inode/generation, numeric/symbolic return code, time and proposal
  phase; retain last failure and per-class counters in gc-status. Preserve
  existing retry records and durability semantics.
- Label portal totals as cumulative since daemon start and expose class/node,
  recent increments and last failure. Two historical attempts must not imply
  two currently broken objects or two failed physical deletes.
- Validate with fault injection: active lease/transaction defers safely and
  later reclaims; proposal failure retains retry work; a hard KV failure is
  visible; accounting distinguishes each case. Recheck xorinox after rollout.

The deployed age fields contain UINT64_MAX because GC writes realtime stamps
while status compares monotonic time. This is already fixed in current source
with `efs_iostats_now_us()` and documented in the GC checkpoint's telemetry-v2
follow-up; deployment remains pending. This is a separate diagnostic defect,
not evidence that GC stopped and not a demonstrated cause of the two errors.
