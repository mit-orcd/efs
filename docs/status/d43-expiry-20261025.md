## What changed

| Area | Now |
| --- | --- |
| Build | `src/meta/expiry.c` always linked; every `#if EFS_BUILD_EXPIRY` removed (`unifdef -DEFS_BUILD_EXPIRY=1`: only the D42 refusal and `(void)` stubs were in `#else` branches); `make test-expiry` removed; `efs-mgmt --help` lists `expiry-policy`, `expiry`, `expiry-status`, `expiry-clock`, `expiry-enable`, `expiry-id` in every build |
| Control | New cluster expiry policy: one versioned row on shard 1 (KV kind 56 `EXPIRY_SWITCH`: version 8 bytes, enabled 1 byte), Raft command `EXPIRY_SWITCH` (102, CAS on the version) and ReadIndex request (103), exactly like `QUERY_POLICY`. Absent row = version 0 = off. `efs-mgmt expiry-policy NODE:PORT cluster get` / `cluster set on\|off EXPECTED_VERSION` |
| Runtime effect | The replicas of shard 1's group update their cached flag when they apply the command; every other node at its next GC pass (one policy read per pass: the local applied row where it holds that group, otherwise the authority). No restart |
| Off | Creates take the ordinary path (no ancestor policy walk, no record); the GC worker returns after the flag check (no clock read, ReadIndex or index scan; `expiry_passes` does not move); expiry requests (folder policy, records, renew, enable, delete, clock reset) are refused with `rc=-16` and `efs-mgmt` says why |
| Deletion | A deletion re-reads the cluster policy from its authority (not the cache) and acts only while the deadline's source folder policy covers it: the folder is live with the recorded generation and its policy is enabled. The policy row rides the expiry transaction as a CAS (rewritten unchanged), so a concurrent disable either commits first and makes the deletion stale, or waits. The GC pass skips uncovered due rows before any request (local hint; budget counts only deletion attempts) |
| Environment | No variable or flag turns expiry on or off. `EFS_EXPIRY` stays in `removed_env[]`: efsd exits at startup with "EFS_EXPIRY was removed (D43): expiry follows the cluster expiry policy; turn it on or off at runtime with efs-mgmt expiry-policy NODE:PORT cluster set on\|off VERSION". The only other expiry reader is the fault-build clock hook `EFS_FAULT_EXPIRY_CLOCK_FILE` (`#if EFS_FAULTS`), which pauses deletion, never enables it |
| Unchanged | The D33 design: fixed birth deadlines from the nearest folder policy, renewal, hard-link refusal, rename keeps the deadline, clock-health pause, physical reclamation after last close. Opcodes 58–70 and KV kinds 42–44 were kept reserved by A7 and return unchanged |

Uniqueness: `tests/test_kv_kind_unique.py` (52 kinds, 86 Raft tags, 116

## Interpretation and limits

- **"Covered"** means: the cluster policy is on, and the folder policy the
  deadline was materialized from (`root`, `root_generation` in the record)
  is still enabled on a live folder of that generation. A deadline is fixed
  at birth and travels with the file on rename (D33), so a file renamed out
  of its folder keeps its deadline while that folder's policy stays enabled;
  the delete path does not walk the file's current ancestors.
- Turning the cluster policy on affects files created afterwards (within a
  GC pass on nodes outside shard 1's group); files created while off never
  get a deadline. Enabled, a regular-file create walks the ancestors for a
  policy and takes the cross-group transaction path, about 1.9x the create
  time measured here even with no folder policy anywhere. **Follow-up
  (done, not merged):** [creates keep the ordinary path until a folder
  policy is enabled](d43-expiry-fast-create-20261025.md).
- A folder policy row is not deleted when its folder is removed (as before
  D43); coverage ignores it because the folder is no longer live.
- Expiry stays operated through `efs-mgmt`; the `.efs` commands still
  reject expiry options and print "expiry unavailable" (their own surface).
