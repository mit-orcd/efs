# W124 parts 1–2 — batched journal-first reclaim on orcd-mini — 2026-10-18

**Verdict: PASS, with one open item** (the `posix_expiry` re-run below).

**Item:** [W124 fast delete](../backlog/fast-delete-reclaim.md), parts 1
(bounded, batched, node-local reclaim) and 2 (accounting). Parts 4 (slot
reuse) and 5 (subtree delete) stay deferred.

**No A/B against the old reaper.** The old per-inode path is removed, not
kept behind a switch, and the user asked only for proof that the new path
is correct.

**Results on orcd-mini, deployed as `de0c856b4f4c`:**
- **Backlog:** a 5.58 M-inode reclaim backlog per node drained in about
  18 minutes. The old reaper ran at 48–57 fragments/s.
- **Mixed workload:** write, read and delete ran from both client nodes
  while 2.7 M existing files were deleted. Every surviving byte checked
  out and there were no errors.
- **Full deletion:** every file was then deleted. Fragment files on every
  node went to 0, and a cold restart's inventory equals the running count
  (0) on all three nodes.

### Deploy notes

- **node9900 client:** it held writes that had already failed with
  "quota exceeded" during the earlier quota-full periods (04:54Z and
  16:17Z). A plain stop refused because of them, so it was stopped with
  `scripts/client.sh stop --force-discard`. The discarded bytes were never
  acknowledged.
- **Temporary quota for the first deploy:** efsd's startup safe maximum was
  713.8 GiB, with `/data1` 79% full. The deploy therefore started with
  `QUOTA=704G` in node9901's `devops/clusters/orcd-mini.env`, with a backup
  next to it. The final deploy restored `720G`; by then the safe maximum
  was 1,334 GiB.
- **Pre-deploy delete:** before deploying, the 100 GiB
  `big-files/001.dat` was deleted with the old build, as allowed by the
  user. The new build then finished that half-swept inode. Old GC records
  and whole-inode reclaim coexisted without error.

### Old backlog drain (first deploy, `5986e13d5`)

- **Rate:** about 18 minutes from start to an empty journal. Each node
  accepted and deleted 5,578,288 dead inodes, a peak of 7,030 per second
  (10 s samples).
- **Usage:** per node it fell from 704 GB (676 GiB) to 356 GB.
- **Errors:** none.
- **Journal cap:** it was reached during the drain (262,144 records),

### Ultimate test: mixed load on both clients during a bulk delete (`de0c856b4`)

**Method:**
- `scripts/orcd_mini_w124_mixed.py` ran on both client nodes at the same
  time for 900 s. Each run prefilled 20,000 files, then used 8 writer, 8
  reader and 8 deleter threads.
- File sizes were mostly 256 B–16 KiB, with 2% of 1–8 MiB.
- Every read was checked byte for byte.
- At the end each run verified that every surviving file is exact and that
  every deleted file is gone.

## Remaining gates and limitations

- Node power loss is not tested. SIGKILL keeps the page cache, so the
  deferred directory syncs and the checkpoint `syncfs` ordering are
  covered by reasoning and the unit tests, not by a power-cut test.
- The node fails closed on journal loss, and recovery fences every inode
  metadata proves dead. That recovery issues one ReadIndex per on-disk
  inode, so on a large root it is slow. It runs only after detected
  corruption.
- The leader still hands work to the deleters only after a full lane sweep.
  A 100 GiB file needs about 50 passes of 32 rounds.
