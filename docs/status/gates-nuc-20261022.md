## K1: bounded stop qualification

**Purpose:** K1 R4 (`12bfbe9e8`) has one 50 s shutdown deadline and writes
the exit record `log/efsd.exit`. `scripts/server.sh stop` returns 0 for an
orderly stop, 3 for a forced one and 4 when a barrier failed or the
outcome is unknown. This gate checks that on a live 3-daemon cluster.

**Command:** `scripts/gates_nuc_k01_stop.sh` (committed here; run 1 used
the same steps from an uncommitted copy). It uses
ports 18910–18912, `EFS_MD_RAFT_N=3`, TCP, 2 GiB quota and direct I/O
(the server.sh default), with stores under `$HOME/efs-gates-nuc/k01`.
Prerequisite: `make tests/shutdown_faults/efsd` (9 s). Run 1 took 68 s,
after K5 run 1 and alongside W148 attempt a1. Run 2 took 64 s, after the
campaign ended. The numbers below are from run 1; run 2's are in
brackets.

`server.sh` derives the node id from the address and port, which gives
84446. A 3-way Raft refuses it ("node-id 84446 out of 1..3"), so the
driver passes `--node-id 1|2|3` as extra efsd arguments, and efsd uses the
last one.

**(a) Idle daemons, orderly.** After `raft-mkfs`, 20 s idle, then
`server.sh stop <storage>` for n3, n2, n1:

| node | script rc | stop wall | record `elapsed_ms` | outcome | barriers |
| --- | --- | --- | --- | --- | --- |
| n3 | 0 | 548 ms [326] | 436 [230] | orderly, phase done, stores closed | put_sync, reclaim_journal, usage_flush all `done` |
| n2 | 0 | 404 ms [238] | 267 [157] | orderly | all `done` |
| n1 (last, leader) | 0 | 898 ms [254] | 746 [157] | orderly | all `done` |

Each printed `stopped, orderly (rc 0; put_sync done, reclaim_journal done,
usage_flush done)`, and every record had `deadline_ms=50000`.

**(b) Parked packer, forced.** n1 and n2 ran the normal build. n3 ran
`tests/shutdown_faults/efsd` with `EFS_FAULT_SHUTDOWN_PARK=packer
EFS_FAULT_SHUTDOWN_TOTAL_MS=6000`, the same arguments as (a) and
`--join`. It joined and replicated before the stop.

- `server.sh stop` for n3: **script rc 3**, wall 6140 ms [6098 ms]. Output:
  `stopped, forced, stores preserved (rc 3 after 6000 ms of 6000 ms; phase
  packer, worker packer thread; put_sync not_reached, reclaim_journal
  not_reached, usage_flush not_reached); not an orderly stop`.
- Record: `outcome=forced rc=3 phase=packer worker=packer thread
  elapsed_ms=6000 deadline_ms=6000 stores=preserved`, all barriers
  `not_reached`. efsd.log: `shutdown: deadline 6000 ms passed in phase
  packer with packer thread still live; … exiting without teardown, stores
  preserved (rc=3)`.
- Stores preserved: 16 store files before, 16 after, none missing [17/17].
  Log files and atomic-rename temporaries were not counted.
- Restart from the normal build on the preserved root:
  `server.sh A:18912 n3:2G A:18910 --node-id 3` returned 0 on the first
  try. The stop had removed the PID file, so start-up had nothing to
  refuse. n3 came back as FOLLOWER of both groups at commit=applied=57,
  level with the leader. **Serves:** an 8 MiB random file written through a
  FUSE mount on the cluster read back identical with `cmp`.
- The restarted n3's own stop: script rc 4, `durability barrier failed,
  stores preserved (rc 4; put_sync failed …)`. This is expected: after a
  forced stop the root is W71 recovery-uncertain. n2 and n1 then stopped
  orderly with rc 0 (238 ms and 235 ms) [208, 695].

**Verdict: PASS.** Orderly stops are rc 0 with every barrier done, in under
1 s. The parked worker was forced to rc 3 at the deadline (6000 ms of
6000 ms) with stores preserved. The stop script exited 3, and a restart
on the preserved stores served again.

**Probe-mount detach (harness, not K1):** in the first run the probe
mount's `client.sh stop` returned 1 ("client discovery requires root:
/proc/1684482") and left the mount attached. See
[the discovery change](#harness-and-script-changes). The mount was
detached afterwards with that change in place. In run 2 the variable was
set, and the probe mount's `client.sh stop` returned 0 and detached.

**devops `stop.sh` (not applied, devops repo untouched).** Before `stop.sh`
can rely on these codes it needs the following, taken from the K1 R4
hand-over patch:
- `nuc-efs/stop.sh` runs under `set -e`. It must stop every node first and
  remember each node's code, not abort at the first non-orderly one. Then
  it should print `stopped, NOT orderly: nN(rc R); stores preserved` and
  exit 3 if any node was forced, otherwise the first non-zero code.
- The fake daemon in `nuc-efs/test_daemon_ownership.py` must write an
  orderly exit record. Without one the new helper reports rc 4.
- efsd and `scripts/server_processes.py` must be deployed together. An
  older efsd writes no record, and its stop reads as unknown (rc 4).

**Limitations:** single host, TCP. Only the packer park was exercised; the
connection-handler park is covered by `tests/test_shutdown_stuck_worker.py`.
The open P2 T2 (forced-exit reporting can block on report I/O) is not
covered by this gate: here the report was written within 6000 ms.

## W148: modify-under-load rerun on the fixed build

**Purpose:** W148 (alpha K8) is a read that returned wrong bytes of the
correct size under the W125 modify workload. It was reproduced 3 times in
9 attempts on node9901 (RDMA, devel `7c510c60f`). It was fixed by
`7a3a6a18e`/`71ce4ff35` (`dcache_apply_init`: a partial load never
inherits an UNCOND base), which is in `163241584`. The rerun of the
campaign on the fixed build had not been done.

**Gate:** zero read mismatches across the campaign on the fixed build, and
the harness's checked stop reports `stopped clean`.

**Campaign:** 9 attempts, matching the reproducing campaign, each the same
as the original: `w125_modify_repro.sh REL OUT PORT 600 3000`, 4 writers, 4
verifying readers, 2 deleters, 4 modifiers, 600 s, `EFS_PACK_MIN_AGE_MS=3000`,
`--direct-io`, 3 daemons with `EFS_MD_RAFT_N=3`, one efs-fuse mount. The
differences from node9901: TCP on 127.0.0.1 instead of RDMA mlx5_0, and an
i5 laptop-class host with NVMe xfs.

**Command:** `scripts/gates_nuc_w148_campaign.sh 9` (committed here). It
sets `W125_TRANSPORT=tcp W125_ADDR=127.0.0.1 EFS_CLIENT_SKIP_FOREIGN=1`,
alternates ports 18920/18925 and gives each attempt its own run directory.

**Aborted first try (a1, not counted):** the first campaign started without
`EFS_CLIENT_SKIP_FOREIGN`, which would have made every checked stop report
forced. I killed its wrapper to restart it, and that took the screen
session and attempt a1's workload down with it at t≈560 s. Its last status
line at t=550 s showed `mismatch=0 errors=0 unsettled=0` (3025 files
written, 10217 reads). Its cluster was then stopped with the checked
`w125_p0_cluster.sh stop`, which reported `stopped clean`, and its store was
deleted. Attempt a1 did not reach final verification, so it is not
counted.

**Results (attempts b1–b9, 651–661 s each, about 98 min in total):**

| attempt | port | done | final line (excerpt) | errors | written / read |
| --- | --- | --- | --- | --- | --- |
| b1 | 18920 | FAIL, stop clean | `mismatch=2 verified_bad=0 errors=7` | 4 unlink EBUSY, 2 rename EBUSY, 1 rewrite EIO | 1025 / 3454 MiB |
| b2 | 18925 | FAIL, stop clean | `mismatch=0 verified_bad=1 errors=7` | 4 unlink EBUSY, 1 rewrite EIO, 2 write EIO | 869 / 2867 MiB |
| b3 | 18920 | **PASS**, stop clean, store deleted | all zero | — | 861 / 2709 MiB |
| b4 | 18925 | FAIL, stop clean | `mismatch=0 errors=2` | 2 rename EBUSY | 766 / 2553 MiB |
| b5 | 18920 | FAIL, stop clean | `mismatch=0 errors=2` | 2 unlink EBUSY | 824 / 2694 MiB |
| b6 | 18925 | **PASS**, stop clean, store deleted | all zero | — | 705 / 2017 MiB |
| b7 | 18920 | FAIL, stop clean | `mismatch=0 errors=1` | 1 write EIO | 697 / 2140 MiB |
| b8 | 18925 | **PASS**, stop clean, store deleted | all zero | — | 628 / 1869 MiB |
| b9 | 18920 | FAIL, stop clean | `mismatch=0 errors=2` | 2 unlink EBUSY | 566 / 1788 MiB |

`unsettled=0`, `missing=0` and `artifact_errors=0` in every attempt.
Throughput fell from attempt to attempt (1025 down to 566 MiB written).
The cause was not investigated.

**The three counted mismatches.** All three are the same shape, and none
is the W148 shape:

- b1 `w1/d016/f000216`, two local reads. The harness expected v1 (358,224
  bytes) and read 3,989,344 bytes. The bytes were identical on re-read, in
  the locked copy and in both captures. `w125_modify_inspect.py` reports
  `exact=[2]`: the file is exactly v2. The workload's v2 rewrite of this
  file had returned `[Errno 5] Input/output error`, so the model kept
  expecting v1.
- b2 `w2/d041/f000741`, final verification: expected v0, read 1,596,897
  bytes, `exact=[1]`. The v1 rewrite had returned EIO, and the file is
  exactly v1.

So the rewrite committed in full, but the application was told it failed.
Nothing read back was wrong bytes or a mix of versions.

The W148 signature from node9901 was an in-place overwrite of an old chunk
that came back as zeros plus only the overwrite's bytes, a state that
matches no version. It appeared in none of the 9 attempts.

**Common cause of the EIOs (b1, b2, b7).** fuse.log shows
`inode-rpc: retry type=67 … why=recv rc=-6 … recv_ms=30007`: one request
got no reply within the 30 s receive timeout. Next came `report-loop … busy=1 … rc=-13`
(opid-admission BUSY while the timed-out operation still holds its slot)
and `flush-meta: resource busy (efs_rc=-13)`, so close/fsync returned EIO.
In b2, n3 logs nothing from 04:18:55 to 04:19:18 except an AppendEntries
reject, then `kv-flush: files=139 io_ms=2266` with an L0 of 142.
Meanwhile n1 logs `report-split … rc=-14 fail=finish/-14`. The EBUSY
unlink/rename errors (b1, b2, b4, b5, b9) are `rename_at … rc=-13 after 2
tries` after a `type=87` receive retry. This is the same EBUSY class the K8
node9901 runs recorded (loop1 a4, trace a1, the mix stress run).

**Verdict: FAIL** by the gate's own criterion. The harness counted read
mismatches in 2 of 9 attempts, and only 3 of 9 attempts passed overall.
For W148 itself: the signature was not reproduced in 9 attempts. In the
same campaign size on the unfixed build, node9901 reproduced it 3 times.
Every read the harness flagged returned an exact committed version.
**Checked stop: `stopped clean` in 9 of 9** (unmount verified, every
daemon exit 0).

**New finding (not fixed here, needs a W item):** a REPORT/flush whose
first RPC timed out at 30 s and whose retry got opid-admission EBUSY is
reported to the application as EIO, although the first attempt committed.
This is a wrong error for a successful write: an ambiguous outcome
surfaced as a definite failure. The trigger was a server stall of about
20–30 s under this load on nuc (TCP, NVMe direct I/O, i5). The
`w125_concurrent.py` model also treats an EIO modify as not applied, so the
harness cannot tell this case from W148. A model that accepts "either the
old or the new version" after an EIO would separate the two.

**Limitations:** TCP and a slower host, not RDMA on node9901. With 0 of 9
on the fixed build against 3 of 9 on the unfixed one, the confidence comes
from the campaign size, not from a reproduction in both directions on this
host: the unfixed build was not run on nuc. The EBUSY and EIO errors make
6 of 9 attempts fail for reasons other than W148. Until those are
resolved, a clean W148 PASS at this gate needs either a host where they do
not occur or a harness model that accepts ambiguous outcomes.

## Harness and script changes

All on this branch. None changes product code or a default.

1. `scripts/w125_p0_cluster.sh`: `EFS_TRANSPORT=${W125_TRANSPORT:-rdma}`;
   `EFS_RDMA_DEV` is set (default mlx5_0) only when the transport is not
   tcp. The default is unchanged (RDMA). `tests/test_w125_harness.py` PASS
   on nuc.
2. `scripts/client_processes.py`: with `EFS_CLIENT_SKIP_FOREIGN=1`, for a
   non-root user, an `efs-fuse` process owned by another uid that cannot be
   inspected is skipped instead of failing discovery. Without the
   variable, discovery still refuses ("client discovery requires root").
   **Why:** nuc runs the user's client as user `efs` from an older build
   with the removed `efs-fuse NODE LABEL MOUNT` form
   (`./efs-fuse 127.0.0.1:17432 fs /data1/…/mnt`). The parser takes the
   label `fs` as a relative mount path and must read that process's
   `/proc/PID/cwd`, which a non-root user cannot do. Every `client.sh stop`
   by `maik` therefore refused (rc 1, mount kept). That breaks the W125
   checked stop and the K1 probe mount. `tests/test_client_processes.py`
   on nuc: fails without the variable (the same refusal; host-caused, not
   a regression), passes with it. `tests/test_client_stop.py` passes.
   Reviewer note: this touches a fail-closed operator path, but only
   behind the opt-in. Whether to keep it or drop it after the gate is the
   integrator's call.
3. New reproduction drivers: `scripts/gates_nuc_k01_stop.sh` and
   `scripts/gates_nuc_w148_campaign.sh`.
