# D25 step 4 — truncate sweep, history retirement, masked packing

October 22, 2026. Linked items: D25 / W43
([protocol](d25-logical-truncate-design-20261021.md) §4, §7 step 4, gates
g5–g8). **Verdict: g5–g8 PASS on a private node9901 cluster (`step4c`);
step-3 gates g0–g4 still PASS on the same tree (`step3h`, see Results).**
Lazy truncate stays off by default; step 5 (removing the eager path)
remains.

Branch `d25-logical-truncate`, the commit that adds this page, on top of
`0541d9f4f`. Trees on node9901: `/tmp/d25lt/src` (normal) and
`/tmp/d25lt/fault` (`EFS_FAULTS=1`), compared byte for byte with the

## What changed

| area | change |
| --- | --- |
| lane stamp | 88 B: `sweep_target`, `sweep_next_ci`, `swept_epoch` |
| chunk row | header 24 B: `base_clip` (0 = whole chunk); span clips reuse the span's `len` (readers copy only `[off, off+len)` of a span object); GETCHUNKS and writer views honour the base clip |
| `TRUNC_SWEEP` (80) | lane group: adopt the target, examine at most 256 rows from the cursor, change at most 64; dead base/span → GC record (packed base → ledger once per batch); partly visible → clip; empty row → delete; a key under a pending intent stops the cursor; end of lane → `swept_epoch` |
| `SWEEP_DONE` (81) / `RETIRE` (82) | inode group: done bits per history entry from observed `swept_epoch`; retire all entries ≤ T when done ⊇ active lanes; revision advances; last entry removes `TRUNC_PENDING`; an unlinked inode's pending key is dropped |
| activation | a newly activated lane is done for every existing entry, in the same batch |
| scheduler | GC pass on the inode's anchor group: up to 16 pending inodes and 64 proposals per pass; needs both groups local; `efs-mgmt gc-status` shows `trunc_pending` (gc-status reply version 5) |
| packing | candidates carry `base_visible` and clipped spans from the inode history and base clip; the packer copies only visible bytes; segment compaction zeroes a record's clipped tail; packed record epoch stays the newest source-part epoch |
| faults | `EFS_FAULTS=1`: hold the sweep while a file exists (pending count stays live) |

Unit (node9901): `test_meta_apply` (new `test_trunc_sweep`: dead row

Earlier runs on the way are not evidence: `step4a` read `gc-status`
through an `efs-mgmt` that silently rejected the new reply version, so its
sweep waits and space check were vacuous; `step4b` had a fault hook that
froze the pending count while held. Both were fixed before `step4c`.

## Limits

- The scheduler needs a node hosting both groups (true for these
  clusters); it does not yet forward lane reads.
- Throughput is bounded by 64 proposals per GC pass and 64 changed rows per
  sweep entry; a 2 GiB file drained in about 9 s here. Large files take
  proportionally longer; not measured above 2 GiB.
- Delayed BOOTSTRAP after retirement and a sweep stopped by a pending
  transaction intent are covered by design and unit logic, not by a
  cluster gate.
- The `PACK_SWITCH` delayed across shrink, sweep and retirement is argued
  in protocol §4.6; the cluster gate exercises truncation and repacking of
  packed files, not a forced SWITCH delay.
- TCP only; one run per configuration.
