## Bug found and fixed in P7

In a 4-node cluster each metadata group has three voters, but the packer
placed segment fragments on the first three cluster nodes. A non-voter
cannot check a PUT_SEGMENT (or a segment's reclaim) against the object, so
the copy failed, the packer admitted and cancelled the same segment every
pass, and retirement never completed. Segments now go only to live voters
of their group, and retirement asks only each segment's placement nodes
(`ce2005d80`). Found by the expiry gate's 4-node fixture.

## Open: expiry gate under leader loss

The expiry gate kills and restarts metadata leaders and storage members
while files are written and fsynced. With the packer active it fails
intermittently; without packing activity it passes:

| Build and setting | Runs | Result |
| --- | --- | --- |
| base `d9cee1ffd` | 3 | 3 PASS |
| branch, packer idle (minimum age 1 h) | 3 | 3 PASS |
| branch before the placement fix, packer active | 2 | 2 FAIL (fsync EIO; packer stuck re-admitting) |
| branch after the placement fix, packer active | 7 | 3 PASS, 3 fsync EIO after a leader kill (`expiry after actual metadata leader loss` and the following create), 1 `peer_pwrite_then_peer_truncate` size mismatch in the embedded two-client run |

- In the failing runs the group leaders' packers had just selected one
  eligible candidate and attempted a segment, but nothing switched; the
  client then reported `efs-fuse fsync: network error (efs_rc=-6)` a few
  seconds after the killed node rejoined.
- A 30 s packer back-off after a failed copy (`62846550b`) did not change
  the outcome. The two-client truncate case passes 30/30 in isolation on
  both builds.
- Root cause not found. Next: instrumented runs (client fsync step,
  peer-pool cooldowns, packer proposals during the election), and whether
  files still open for writing can look eligible (no lease row yet).
- **orcd-mini must wait until this is understood.**
