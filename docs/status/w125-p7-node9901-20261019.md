## Bug found and fixed in P7

In a 4-node cluster each metadata group has three voters, but the packer
placed segment fragments on the first three cluster nodes. A non-voter
cannot check a PUT_SEGMENT (or a segment's reclaim) against the object, so
the copy failed, the packer admitted and cancelled the same segment every
pass, and retirement never completed. Segments now go only to live voters
of their group, and retirement asks only each segment's placement nodes
(`ce2005d80`). Found by the expiry gate's 4-node fixture.

## Expiry gate under leader loss (fixed)

The expiry gate kills and restarts metadata leaders and storage members
while files are written and fsynced. With the packer active it failed
intermittently:

| Build and setting | Runs | Result |
| --- | --- | --- |
| base `d9cee1ffd` | 3 | 3 PASS |
| branch, packer idle (minimum age 1 h) | 3 | 3 PASS |
| branch before the placement fix, packer active | 2 | 2 FAIL (fsync EIO; packer stuck re-admitting) |
| branch after the placement fix, packer active (`ce2005d80`, `62846550b`, instrumented runs) | 13 | 8 PASS, 4 fsync EIO after a leader kill, 1 `peer_pwrite_then_peer_truncate` size mismatch in the embedded two-client run |
| `e6771854e` (COMMIT reprobe), packer active | 8 | **8 PASS** |

**Root cause (client, present in base too).** Instrumented run
(client connection and COMMIT logging, env-gated, not committed):

- node 2 was restarted at 17:15:04 and rejoined at 17:15:17.6;
- at 17:15:14.9 an `INODE_LOOKUP` retry burst hit node 2 while it still
  refused connects; four failures put it in the client's 30 s down cooldown;
- at 17:15:20.6, after node 2 was back, an fsync's COMMIT (sent to every
  node) got no connection to node 2 on both attempts at once
  (`commit_rc=-6`): the background reprobe only starts on a checkout and
  had not yet run.

Base has the same COMMIT, cooldown and reprobe code; packing activity
changes the timing enough to hit the window. Fix (`e6771854e`): when the
checkout returns no connection, COMMIT probes the node with a plain TCP
connect, ends the cooldown if it answers and retries; a node still down
fails the fsync as before. `test_data_commit` covers both cases.
Packer-side checks found nothing wrong: candidate files in the failing
run had no lease row because they were closed (age about 3 s), and no
failed switch was logged.

The single two-client truncate mismatch did not recur (30/30 in
isolation on both builds earlier, and in all 8 runs on `e6771854e`).
