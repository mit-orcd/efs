## What the kill hit

`efsd --join` initializes a fresh store in `member_store_open`:
`owner.lock` (flock), then `boot.bin` (counter 0) by write-temp, fsync,
rename, fsync-directory, then `identity.bin` (state `joining`, a new 64-bit
token) the same way. Only then does it advance the boot counter
(`member_store_boot`, counter ≥ 1) and send its first HELLO. A store with
`boot.bin` and no `identity.bin` was refused on every later start:

```text
member store refused: store .../n4/mdraft has a boot counter but was never initialized (interrupted initialization); format it fresh
store: put sync root=.../n4 startup abandoned before serving; previous durability record restored
```

That is Task A's refusal (its report paraphrased the first line).

**Sweep on the base** (`repro.py` below, product `./efsd`, a fresh
three-member cluster per trial, member 4 SIGKILLed after the delay, the
same `--join` 3 s later). The joiner's store after the kill, the
membership count after the kill and after the retry:

| Delay (killed at) | Store after the kill | Members after kill → retry |
| --- | --- | --- |
| 24 ms (25) | no `mdraft/` | 3 → 4 |
| 28, 32 ms (33, 35) | `.boot.bin.tmp` only | 3 → 4 |
| **36 ms (40)** | **`boot.bin` (counter 0), no `identity.bin`** | **3 → 3, retry refused** |
| 40 ms (45) | `identity.bin` `joining` | 3 → 4 |
| **44 ms (46)** | **`boot.bin` (counter 0), no `identity.bin`** | **3 → 3, retry refused** |
| 48 ms (51) | `.boot.bin.tmp` only | 3 → 4 |
| 52, 50, 75, 100 ms | `identity.bin` `joining`, no HELLO answered | 3 → 4 |
| 150, 200, 300, 500 ms | `identity.bin` `joining`; the seed logged `joining store ... is pending; adding it` (150, 300, 500 ms committed member 4 while the joiner was dead) | 3 or 4 → 4 |
| 1000 ms | `identity.bin` `joining` | 4 → 4 |

So on the base the refused window is between the two renames, a few
milliseconds of fsync (xfs). Every other pre-commit state already retried:
a `joining` identity resends its token, and the seed either commits it now
or hands it the record it committed while the joiner was down (the same
id, test step 4 of `test_k33_growth.py`). No membership line mentions
member 4 in the refused trials: the cluster never heard of the store.

A second window showed in the sweep on the first fix (`d9186e38a`, the
40 ms trial killed at 71 ms on the loaded host): efsd checks each storage
root with an O_DIRECT probe page `data/.efs-direct-io-probe.<pid>` before
the root has its marker or the member store exists. Killed there, the page
stays, and the next start refused the root:

```text
storage: .../n4 has fragment data but no root marker; its format is unknown and this build reads only root format 1 (fragment record format 2: I25 identity-bound records); refusing
storage: incompatible, busy or corrupt root; refusing startup
```

## Fix

`boot.bin` at counter 0 proves `member_store_boot` never ran, so
`member_store_open` never returned and the token minted in that start
never left the process: no seed, joiner or record can name the store.
Such a store (no `identity.bin`, counter 0, no `kv/` or `log/`) now
initializes again with a new token and the same command proceeds; as a
joiner it is added at `count + 1` (the id the cluster assigns). The same
holds for an interrupted seed start (a new cluster identity, which nobody
knew). Everything else stays refused:

| Store | Outcome |
| --- | --- |
| nothing, or only `owner.lock`/`.boot.bin.tmp` | initialize (unchanged) |
| `boot.bin` at counter 0, no `identity.bin` (a `.identity.bin.tmp` may remain) | **initialize again (new)** |
| `boot.bin` above 0 or unreadable, no `identity.bin` | refused: `has a boot counter but no member identity (it started before and lost identity.bin, or its boot counter is unreadable); format it fresh` |
| Raft/KV data without `identity.bin` | refused (unchanged: another build's store) |
| `identity.bin` `joining` | retries its join with its token (unchanged) |
| `identity.bin` seed/promised/formed | starts as that node; a cluster whose record holds the id or endpoint under another token refuses it (unchanged: `can never be a member`) |

A root without a marker whose `data/` holds only such probe pages
(`.efs-direct-io-probe.` followed by digits) removes them and is a new
root (`server_storage_roots_init`); any other entry is still refused as
data of an unknown format.

The table is the comment above `member_store_open`
(`src/server/member_store.c`); `member_store.h` says the same.

Two fault points (`EFS_FAULT_MEMBER_EXIT`, `EFS_FAULTS` builds only,
`tests/faults/efsd`) make both pre-commit windows deterministic:
`before-identity` (in `member_store_open`, reached through
`member_store_fault_exit`, which efsd sets to `server_test_member_exit`)
and `before-hello` (efsd, a joining identity persisted, no HELLO sent).
No new environment variable; the
[A6 inventory](a6-settings-inventory-20261024.md) row names the points
(`env_inventory.py --check` PASS).

## Limitations and remaining

- Loopback on one host only; A13 on real hosts (3 → 4 → 5 under load,
  seed loss) is the parent's live gate.
- A13's kill is timing-only; which window a run hits depends on the
  host. The deterministic coverage of each pre-commit window is
  `test_k33_join_retry.py`.
- Not changed: a first start with several storage roots killed between
  writing two root markers is refused on retry (`k of n roots are new`);
  the A13 layouts use one root. Fail-closed, not covered here.
- `test_k33_growth.py`, `test_k33_autoid.py` and `test_k33_interrupt.py`
  were run alone at `d9186e38a`; at `bfd0abdf6` they ran in the gate.
- Not changed: a joining store's pending addition stays queued on the
  members after the joiner dies, so the cluster may commit it while the
  joiner is down (the retry then learns the same id). A wiped store
  restarted at that endpoint before the queued addition commits is not
  covered here.
