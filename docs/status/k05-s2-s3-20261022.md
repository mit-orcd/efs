## Changes

1. `468513a96` meta (S2). `session_owner_capture` in `src/meta/append_plan.c`
   reads the local session row once and authorizes the request from those
   exact bytes, with the `efs_session_accept` rules, before that image is
   prepared. Applied to every session-owned executor with the two-read
   pattern: `efs_meta_execute_mtime_owned` (the finding),
   `efs_meta_execute_append_owned`, `efs_meta_finish_append_batch_owned`
   and the session-owned branch of `efs_meta_retire_append_barriers`. The
   last two returned STALE/BUSY for a fenced capture (the host turned STALE
   into a retry); they now refuse FENCED or UNREGISTERED.
   `efs_session_prepare_owner` validates its own second read the same way.
   `efs_session_prepare_namespace` is unchanged: it runs inside one
   serialized apply, and its version guard cannot see a local fence (only
   transaction resolve bumps that version), so reordering would prove nothing.
2. `42c631852` client (S3). Every access to `session_started` and
   `session_fenced` in `src/client/inode_rpc.c` is an `__atomic` builtin:
   acquire loads, release store for started, acquire-release exchange for
   fenced (exactly one fencer logs). `opid_mu` no longer guards them.

## Tests

- `tests/test_session_owned_capture.c` (new, in `make test`). Real session
  rows in a memory KV; a barrier KV runs the injection on the second read of
  the session row, between the check and the capture.
  - Fence between check and capture: mtime, APPEND reservation, APPEND
    completion and `efs_session_prepare_owner` return FENCED with no prepare
    and no inode, lane, append, intent or guard change.
  - Row removed between them: UNREGISTERED, same checks.
  - Fence after capture, before the owner PREPARE: the exact-image CAS fails
    (STALE), only the owner prepare ran, inode unchanged; the retry is FENCED.
  - Fence after the owner PREPARE: the fence is BUSY while the established
    transaction commits; afterwards it lands and the next request is FENCED.
  - Linked against devel's `append_plan.c`, the test fails at the first case
    (`rc=0`, want FENCED). With the fix it passes.
- `scripts/reviews/k05_mtime_fence_capture.py` (the review's wrapper
  reproducer) now asserts the fixed outcome (FENCED, no executor, no
  prepare) and runs in `make test`.
- `tests/test_session_latch_tsan.py` (new, in `make test`). It runs the
  production latch functions with six checkers racing mount start and three
  fencers racing each other, 200 native rounds and 60 under
  ThreadSanitizer. No checker returns OK after FENCED, all end fenced, one
  fence log per round, no TSan report. A negative control rebuilds the
  reviewed plain store and requires TSan to report the race (it does). The
  test also fails on any non-atomic use of either field. Fails rather than
  skips when TSan cannot build or run.
