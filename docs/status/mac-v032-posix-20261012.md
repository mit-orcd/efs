## Investigation and rejected candidates

An eight-image same-group log-envelope candidate based on ac8cf2d7 was privately
built with identity `ac8cf2d7-cohort1`. Framing, ordering, refusal, sanitizer and
real-KV replay tests passed. However, CRC-framed scans of all three active Raft
logs found **zero tag-58 entries**: it was not exercised by these live workloads.
It did not close the native gate and was removed from the working tree.

A submission-only forwarding prototype also passed isolated adapter/sanitizer
checks, but was not deployed or committed. Both live metadata groups were led by
node 1, so changing remote forwarding did not address this local-path run.
No speculative protocol or persisted-format change is retained.

An isolated listing diagnostic passed in 10.6 seconds while strace captured
`fsync`/`fdatasync` on the seed. Over the 25-second trace, including post-test
cleanup/background activity:

| File | Calls | Mean ms | p50 ms | p95 ms | Max ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Raft log | 571 | 14.81 | 15.51 | 25.67 | 42.88 |
| KV WAL | 574 | 11.83 | 10.25 | 23.09 | 37.59 |

GC death-page writes and directory syncs were also active. Different inode death
bits legitimately rewrite the same checksum-protected page; the implementation
already avoids rewriting an already-set bit. These observations support a
local durability-I/O contention hypothesis, not a proven redundant-barrier fix.
Timing under strace is diagnostic, not an uninstrumented acceptance result.
Seed VM had 2.9 GiB available, no swap use, about 9.1 GiB free on `/data1`, and
19–25% I/O wait in short samples. Host filesystem had 713 GiB free.

Before POSIX execution, during the initial restart, the seed VM suffered a kernel
XFS inode-GC page fault (`get_freepointer`/`xfs_extent_busy_insert_list`, kernel
6.19.14-108.fc42.aarch64). Drained mounts and retained stores; rebooted only that VM.
No EFS causality established. No subsequent kernel incident observed.

To reproduce the fresh-store control, start from a verified identical release
build on all three Mac nodes. Choose a unique private directory and first run
`CLUSTER=mac NODE_QUOTA=8G ./cluster.sh stop`. On each node create that directory
owned by `efs`, then run the following service with node-specific ID/address
(1/.11, 2/.12, 3/.13); nodes 2/3 add `--join 192.168.2.11:17432`:

```
sudo systemd-run --unit=efsd --collect --uid=efs --gid=efs -p WorkingDirectory=/tmp/efs -E EFS_MD_RAFT_N=3 -E EFS_TRANSPORT=tcp -E EFS_COMMANDS_SERVER=0 -E EFS_PACKED_WRITES=0 /tmp/efs/efsd --node-id <id> --addr <ip> --port 17432 --storage <unique-private-root> --quota 3G --no-direct-io
```

Wait for listeners, invoke `/tmp/efs/efs-mgmt raft-mkfs 192.168.2.11:17432` once
on the seed, then `CLUSTER=mac EFS_RPC_PROF=0 ./gw-up.sh --remount` and the native
command above. After all workers/cleanup exit, drain gateway with
`sudo -n -u efs /tmp/efs/scripts/client.sh stop /mnt/efs`, stop `efsd` on each
node, and run `CLUSTER=mac NODE_QUOTA=8G ./cluster.sh start` to restore installed
`/data1` stores. Never use `wipe` or force-discard. Do not run the private and
installed services concurrently on the same port. Check free space before
allocating the private 3 GiB/node quota. Private directories may be retained
outside Git for diagnosis; they are not release deployment destinations.
