# W125 P1 early measurement — singleton publication cost on the archived packing code — 2026-10-18

**Verdict: the P0 GO condition FAILS for the archived implementation.** The
condition was that a packed singleton's publication costs no more than
today's close.
- **Close, single writer:** 3.53 ms for a packed singleton against
  0.65 ms unpacked, 5.4×.
- **Throughput:** 165 files/s against 568 for the single writer (−71%), and
  557 files/s against 2,564 for 16 workers (−78%).
- **Metadata:** 9.9 Raft entries per file against 4.0.
- **Space:** a clear win, 19× less fragment space than unpacked (221 MB
  against 4,178 MB per node for 60,000 files).

**Decision (user, 2026-10-18): option 2, background packing after close.**
The W125 [design](../backlog/small-file-packing-default.md) and
[plan](../backlog/small-file-packing-plan.md) are revised: one write path
(today's), an always-on packer, no switch.

Plan: [W125 implementation plan](../backlog/small-file-packing-plan.md).
Basis: [W125 P0](w125-p0-20261018.md), whose decision rule calls a
throughput loss above about 10% at the user's workload a NO-GO for this
close contract.

## Why this was measured on the archive

The P1 port (selective; a full revert of `5ded11179` conflicts in 42 files)
would take a while before the first end-to-end packed write. The archived
code at `archive/packing-containers-20261016` is a complete packing system
(client opt-in `EFS_PACKED_WRITES=1`, default files engine on the daemons),
so it measures the cost of the archived design today.

## Results

| Configuration | r1 files/s | r1 close p50 / p99 | r2 files/s | r2 close p50 / p99 | Fragment files on n1 (size) | Fragment bytes on n1 | Raft entries per file |
| --- | --- | --- | --- | --- | --- | --- | --- |
| U: unpacked (`base`) | 2,564 | 1.82 / 7.91 ms | 568 | 0.65 / 1.18 ms | 60,000 (69,632 B) | 4,178 MB | 4.0 |
| P10: packed, 10 ms deadline (`base`) | 618 | 12.75 / 25.38 ms | 59 | 13.78 / 16.92 ms | 14,004 (8,192 B) | 115 MB | 9.5 |
| P0: packed, seal at once (`d0`) | 557 | 4.29 / 17.40 ms | 165 | 3.53 / 5.74 ms | 27,038 (8,192 B) | 221 MB | 9.9 |

- **Coalescing:** concurrent writers still share segments with seal at
  once: 60,000 files in 27,038 segments, 2.2 per segment. With the 10 ms
  deadline it was 4.3 per segment.
- **Directories:** packed runs still create about two directories per file
  (137,029 on n1 for P0), so the inode scaffolding is created for packed
  files too.
- **Raft entries:** commit indices of both groups after both runs, divided
  by 60,000 files.

**Phase breakdown of one packed singleton close** (r2, 2,000 files,
`EFS_PACK_PROF=1`, archived writer's own profiler, mean per call):

| Phase | Calls per file | Mean |
| --- | --- | --- |
| Fragment PUT | 3 (apparently one after another) | 518 µs |
| Admission | 1 | 387 µs |
| Publication (load) | 1 | 459 µs |

That is about 2.4 ms profiled out of about 3.5 ms per close. The remainder
is sealing, queueing and the publication acknowledgement.

## Why packed close is structurally slower

- **Unpacked:** fragment data is sent asynchronously before close (async
  PUT), so close waits for one publication.
- **Packed singleton:** the segment can only be written once it is sealed,
  at close. Close then waits for the fragment PUTs, admission and
  publication in sequence.
- **Rough lower bound with the archived protocol tightened:**
  - parallel fragment PUTs, about 0.5 ms;
  - one fused admission and publication entry, about 0.5 ms.

  That is about 1.0 ms against 0.65 ms. In the P0 closed-loop model, about
  −18% single-writer throughput, still above the 10% bound, before the
  extra Raft load.

## Options

1. **Tighten and re-measure** under the same contract: parallel PUTs, fused
   admission and publication, fewer Raft entries per file (9.9 against
   4.0), no inode scaffolding for packed files. Likely still about 1.5×
   today's close, so a NO-GO by the P0 rule unless the rule is relaxed.
2. **Background packing (pack after close).**
   - Files are written exactly as today (fast close, async PUT). A
     background packer then rewrites closed small files into packed
     segments (lifetime-grouped by directory subtree and creation epoch)
     and retires their per-file fragments through W124's batched reclaim.
   - Close latency and throughput stay unchanged. Space falls from today's
     cost to the packed cost after a delay.
   - It extends "singletons plus merge compaction": today's per-file
     fragments become the singletons.
   - Trade-offs:
     - temporary space at today's cost until packed;
     - extra write traffic, but roughly 256 B of payload per file;
     - the current write path for small files stays. That conflicts with
       the user's "no unpacked small-file path" rule (W125 landing gate)
       and needs an explicit decision.
3. **Change the close contract (option b):** close returns before the
   segment is published. That needs defined cross-client visibility, error
   reporting and fsync semantics (P0 deferred this as a much larger
   change).
4. **Stop W125** and keep only W124. Today's 69,632 B per small file
   remains.

## Limitations

- The archive predates devel's later fixes (`h->mu` steps, W124 reclaim,
  cooldown fixes); devel's unpacked path may now be faster.
- One run per configuration; synthetic workload; node9901 only.
- "Raft entries per file" includes everything the workload commits
  (creates, lease edges, publications); only the per-file difference
  matters.

## Reproduce

On node9901:
1. Build the two variants from `git archive archive/packing-containers-20261016`.
   For `d0`, change `src/client/pack_write.c` `PACK_DELAY_NS` to `1ULL`.
   Build `make efsd efs-fuse efs-mgmt` with the private libfuse
   `FUSE_LIBS`.
2. Run `archrun.sh` (copy in the raw folder below). It runs U, P10 and P0,
   each on a fresh cluster, with r1 and r2, store snapshots and Raft
   commits.
3. For the profile, start a cluster from `d0` with
   `EFS_PACKED_WRITES=1 EFS_PACK_PROF=1`, run 2,000 files with one worker,
   and aggregate the `PACK-PROF` lines in `fuse.log`.

Clean up `/tmp/w125-arch` afterwards.
