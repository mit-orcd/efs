## Change

**K14 publication (server, `src/server/raft_host.c`).**

- Consecutive W77 units of one FileID in a REPORT now publish as one
  transaction, called a set (`host_pub_set_len`, `host_pub_unit_commit`,
  `host_pub_units_publish`). The set's PREPAREs share one K29 `TXN_BATCH`
  entry per group.
- **Why this keeps the contract:** publishing a superset all-or-nothing
  keeps every unit's contract. Each unit is still all-or-nothing, and a
  reader still sees one state of it. Stages, the FileID pin, DECIDE,
  RESOLVE and RETIRE are unchanged.
- **Set limits:**
  - no chunk appears twice in a set;
  - at most `HOST_PUB_SET_MAX` (512) stages;
  - at most `EFS_PUB_STAGE_RESOLVE_MAX` (64) stages per lane shard, so one
    RESOLVE applies them all;
  - a different FileID ends the set.
- **Losing a set:**
  - A set lost to a STALE member is republished unit by unit, so only the
    losing unit is retried, as before K32.
  - A BUSY member stops the set with BUSY.
- **Transaction id:** a set's txid also hashes its unit count and the first
  chunk of its last unit. A lone unit keeps its old txid, so a re-sent
  REPORT joins the same decision.
- **New counters:** `raft-obs-w77` reports `pub_sets` and `pub_set_splits`.

**K13 tickets (client and server).**

- **New Raft commands:** `EFS_MD_CMD_PUT_TICKET_ADMIT_BATCH` (90) and
  `EFS_MD_CMD_PUT_TICKET_SETTLE_BATCH` (91), with the new limit
  `EFS_PUT_TICKET_BATCH_MAX` (32). Frame: `[tag][n:2][ticket:216]*n`,
  2–32 tickets of one Raft group and one mount session.
- **Apply:**
  - each ticket is admitted exactly as its own ADMIT would be;
  - settle runs each stream in sequence order and stops that stream at its
    first ticket that cannot retire;
  - the verdict is OK, while IO and NOMEM retry the entry;
  - malformed frames are refused before proposal (INVAL) and at apply
    (UNSUPPORTED); a ticket of another group gets INVAL.
- **RPC reply:** a bitmask of the tickets that are ADMITTED or retired, read
  from the applied state. When the reply was lost, a fresh ReadIndex proves
  the state first. Session refusal fails the whole reply, as it does for
  the single form.
- **Admission:**
  - The client group-commits admissions per Raft group
    (`src/client/put_ticket_owner.c`).
  - The sending thread waits, at most `EFS_PUT_ADMIT_LINGER_US` (1 ms), for
    the running chunk jobs of its own `put_pool_run` cohort. One write's
    eight admissions therefore become one entry per group, and tickets
    queued while a batch is in flight ride the next one.
  - A ticket whose bit is clear, a failed batch and a lone ticket all take
    the unchanged single ADMIT. Admission is idempotent, so its verdicts and
    retries stay exact.
- **Settle:** the settle pass packs whole streams of one group into
  SETTLE_BATCH entries; a stream alone keeps the single SETTLE.
- **Unique numbers:** `tests/test_kv_kind_unique.py` passes. Tags 90 and 91
  were the next free values. This change adds no KV kind and no wire
  message type.

The I24 paragraph of `docs/how-it-works/architecture.md` now says that
several writes of one file may share one transaction.

## Entry counts (deterministic, `make test`)

`tests/test_k32_entry_count.py` (new, in `make test`, under a second) has
two parts.

- **Part A** runs the production publication code with the proposal and
  wait layer replaced by a counter that decodes every entry. The code is
  `host_pub_units_publish`, `host_pub_set_len`, `host_pub_unit_commit`, the
  K29 batch builder, `host_txn_commit` and the abort path. "Before" is the
  same slice with the K32 change undone: one transaction per unit, one
  entry per PREPARE (the shape of `cb970ca7c`).
- **Part B** runs the production ticket ledger with counted RPCs. "Before"
  disables admission batching and settle packing in the slice.
- **Workload:** one file, 64 sequential 1 MiB writes (8 chunks of 128 KiB,
  one W77 unit each), U units per REPORT. Each write is one cohort of 8
  chunk jobs on 8 threads, and a settle pass runs every P writes.

| Path (per 1 MiB write) | Before | After |
| --- | ---: | ---: |
| K14 publication, U = 1 | 13.0 | 6.0 |
| K14 publication, U = 8 | 13.0 | 0.75 |
| K14 publication, U = 64 | 13.0 | 0.156 |
| K13 admission | 8.0 | 2.0 |
| K13 settle, P = 32 | 2.0 | 0.25 |
| K13 settle, P = 8 | 8.0 | 0.25 |
| **Total, U = 8, P = 32** | **23.0** | **3.0** |
| Total, U = 64, P = 32 | 23.0 | 2.41 |
| Total, U = 1, P = 32 | 23.0 | 8.25 |

**Where the after counts come from:**

- **Before, per unit:** 8 stage PREPAREs plus the pin (9 entries), DECIDE,
  one RESOLVE per group, RETIRE: 13 entries.
- **After, per set:** about 6 entries: one PREPARE entry per group
  (96 commands each), DECIDE, one RESOLVE per group, RETIRE. At U = 64 that
  is 10 entries per 64 writes.
- **Admission:** one ADMIT_BATCH per group per write, which is the minimum
  for one write whose chunks span both groups. Concurrent writers on one
  mount share batches, but this deterministic test does not count that.

The modelled "before" of 23.0 agrees with the 21.8 measured on orcd-mini.

**Assertions:** the after counts are asserted exactly. The publication path
must stay at or below 2 entries per write for U ≥ 4. The test also checks
that:

- every chunk is staged once per set, with one pin, one DECIDE and one
  RETIRE;
- a STALE member aborts the set and republishes it unit by unit (two ABORT
  decisions, one unit lost, `pub_set_splits` 1);
- a BUSY member stops the set;
- sets break at another FileID and at a repeated chunk;
- the per-lane cap is 64.

## Limitations and remaining gates

- **NOTRUN, for the parent session:**
  - ior easy write on orcd-mini (RDMA, direct I/O), using the table method
    of [the regression page](k32-write-regression-20261023.md): Raft
    commits before and after one ior write, plus `raft-obs-w77`
    `pub_units/pub_sets` for the real units per transaction. The K32 gate
    is ior easy write at or above about 1.2 GiB/s.
  - The K14 torn-read gate over RDMA and on orcd-mini, and long live runs.
- **The real counts depend on two client cadences, not on this change:**
  - The client's 10 ms background publication bounds the units per
    transaction for a streaming writer. At U = 1 the publication path is
    still 6 entries per write.
  - Admission stays at one entry per group per write for a lone writer;
    concurrent writers on one mount share batches.
- **Remaining per-transaction cost:** about 6 entries. DECIDE, RESOLVE and
  RETIRE are still separate entries; folding DECIDE into the coordinator
  group's RESOLVE entry would change the transaction core and is not part
  of this fix.
- **Coverage:** the deterministic test counts proposals in a slice of the
  production code, not a running cluster. The cluster gate runs the
  merged path end to end, but over TCP on one host.
