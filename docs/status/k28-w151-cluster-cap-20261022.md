# K28 / W151 — cluster cap 16, packed segments on the data ring

**Purpose.** Lift the four-node cap so a cluster of 5 or more nodes works for
data placement, membership and clients, while each metadata group keeps
exactly three voters (decision [D38](decisions.md)), and move packed
small-file segments from the group's voters to the data ring across all N
nodes (D38 sub-item). Alpha 1.0 register row
[K28](alpha-1.0-2plus1-checklist.md) / [W151](work-queue.md); prerequisite of
A3 (qualify at least one topology of minimum 5).

**Verdict.** PASS for the scoped gates: unit tests and the full `make test`
on efs1. **NOTRUN: the live 5-node cluster gate** (parent session), RDMA, any
POSIX or load suite. Not merged into devel. Fresh format; no compatibility
with older builds (wire structs and the persisted membership file change size).

## Change

Branch `devel-k28`, based on devel `1bf4bd45f`.

Part 1 (commit `ba9f41dc2`), cluster cap:
- `EFS_MAX_NODES` is **16** (`include/efs/common.h`), not the spec's 64.
  Node-id masks are `uint32_t` built as `(1u << EFS_MAX_NODES) - 1` (pack
  ledger, publication, put ticket, Raft voters), so the cap must stay below
  32; and each `struct efs_node` is about 4.2 KiB, so a node table is about
  68 KiB at 16 but about 270 KiB at 64, both on the wire (HELLO_ACK,
  LIST_NODES_REPLY) and as copies on 1 MiB server thread stacks. A static
  assertion keeps the cap in 3..31.
- `EFS_RAFT_MAX_PEERS` equals `EFS_MAX_NODES` (was 7). Raft id is node id − 1,
  so every member is an addressable peer; operator reconfiguration may place
  a voter on any member. `EFS_RAFT_STATUS_PEERS` follows.
- **Voter rule** (`efs_md_group_voters`, `include/efs/raft.h`): n ≤ 3, every
  node votes in both groups; n ≥ 4, three consecutive nodes starting at the
  group's ordinal, shard group on nodes 1, 2, 3 and SHARD2 on nodes 2, 3, 4.
  This is the four-node layout unchanged; nodes 5..n host no metadata group
  and serve data and clients only.
- `EFS_MD_RAFT_N` is checked against 3..16; unset keeps the default 4
  (deployments set it to the member count).
- Server copies of the node table moved from the stack to the heap
  (`EFS_NODE_TABLE`, freed on scope exit, allocation failure refuses):
  membership gossip, save/load/rejoin, GC batches, the storage fence and the
  packer pass.
- Audit of the other uses: placement, capacity, the client connection and
  liveness tables, `leader_hint`/`primary_id` bounds, mgmt and bench tables
  are sized or bounded by the cap and need no other change. A GC segment
  batch shifted by `id − 1` before checking `id ≠ 0`; the check now comes first.

Part 2 (the commit after `ba9f41dc2` that adds this summary), packed segments on the data ring:
- `efs_pack_destinations` (`src/common/placement.c`): three distinct live
  members (ids 1..16, not marked down, self always live) chosen by the data
  ring keyed by segment id; fewer than three refuses. The packer uses it per
  segment instead of the voter filter; `o->nodes[]` stays the authority for
  readers, GC and reclaim. Packing space pressure now reads every member's
  quota usage.
- Remote linearizable pack-object read: `server_raft_host_pack_object` keeps
  the local ReadIndex path on a hosting node and otherwise sends
  `EFS_MSG_PACK_OBJECT_READ` (173/174) to the routed leader, then each other
  voter. A voter answers only if it hosts the group, after its ReadIndex.
  Transport errors, refusals, a wrong echo or an undecodable object end in
  BUSY, so `PUT_SEGMENT` is refused and segment reclaim stays BUSY; NOT_FOUND
  comes only from a voter's read.
- Nothing else assumes a segment node is a voter: GC segment batches, segment
  reads (`GET_SEGMENT`) and compaction go by `o->nodes[]` and membership.

## Reproduction

```bash
git archive devel-k28 | ssh efs1 'mkdir -p ~/build/devel-k28 && tar -xm -C ~/build/devel-k28'
ssh efs1 'cd ~/build/devel-k28 && make -j4 && TMPDIR=/data1/tmp make test'
```

Expected: `make test` exits 0; the log contains `test_placement: OK`,
`test_wire: OK` and the `pack object remote read ... PASS` line. Cleanup:
delete `~/build/devel-k28`. Raw logs stayed on the VM and were deleted.

## Limitations and remaining gates

- Live 5-node gate (A3): NOTRUN, parent session.
- Metadata stays on nodes 1–4 for any n; a node loss among 1–4 still needs
  operator reconfiguration to move a voter (unchanged from four nodes).
- 16, not 64: raising further needs 64-bit node masks on the wire and in the
  ledger, and smaller node-table entries.
- The remote read adds one RPC per PUT_SEGMENT and per reclaimed segment on
  non-voter nodes; its cost at scale is not measured.
