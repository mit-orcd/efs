## Changes

1. `efs-mgmt raft-step-down <node:port> <group> [target-node-id]` (messages
   171/172, `server_raft_host_step_down`). Without a target, the node steps down
   (`efs_raft_step_down`). With a target, leadership transfers (`efs_raft_transfer`).
   It uses the declared connection like the other mgmt commands. Operator and
   test tooling only.
2. W64 fix in `src/server/raft_host.c`. `host_resize_decide` now hands a
   failed or unconfirmed DECIDE **ABORT** to the finisher in a new
   `HOST_FIN_ABORT` mode. The finisher re-proposes ABORT at the group's current
   leader and RESOLVEs every participant. Before, only BUSY was handed off. The
   finisher then only waited for a decision, so a NOT_PRIMARY ABORT left the
   PREPAREs for the recovery scan (`HOST_REC_AGE_NS` 5 s plus pass cadence).
   ABORT is requested only before any COMMIT proposal. DECIDE is decide-once and
   idempotent for the same verdict, so racing recovery is safe. A COMMIT is
   never converted. A BUSY COMMIT keeps the existing read-only finish.
3. `tests/test_fin_abort_handoff.py` covers both changed functions with the
   actual source. It checks the hand-off on NOT_PRIMARY, BUSY and IO, and no
   hand-off on PROTO, STALE or success. COMMIT is never handed to ABORT. ABORT
   survives a scripted ~1 s election and resolves every participant in under
   2 s. A recovery-decided ABORT is idempotent, a COMMIT decision is respected,
   STALE stops, and a leaderless deadline drops to recovery. It fails on the
   old source at its first assertion.
4. `tests/live/append_failover.py` is the live gate for both items. It starts a
   private three-daemon TCP cluster, runs N writers on one shared O_APPEND file
   with unique keyed 4 KiB records, and optionally runs a step-down or kill
   loop. It checks the final fsync bound and the client REPORT receive retries.
   Warm, peer and cold reads must contain every acknowledged record exactly
   once, no unacknowledged record, no hole or foreign block, and keep
   per-writer order.

## W52 results

The bound is the client REPORT receive limit,
`EFS_IO_TIMEOUT_MS` (30 s) + 0.5 ms per record (`efs_client_rpc_report`).
The gate allows no type-67 receive retry and a final fsync of 30 s or less.
Before: the item's original evidence shows REPORT exceeding 30 s on the old
build (`report-split nrec=1133`, client `recv_ms=30312`). No new before run
completed.

| Run | Host / build | Parameters | Outcome |
| --- | --- | --- | --- |
| smoke | efs3, base `7c510c60f` | 400 records, 4 writers, buffered, TCP | PASS: exact once warm/peer/cold, final fsync max 2.31 s, 0 REPORT retries |
| 20k attempt 1 | efs3, base `7c510c60f` | 20,000, 4 writers, buffered | stopped at 1,640 records after 3,033 s (not a gate result) |
| smoke | node9901, `85602ccf2`+K15 | 400, 4 writers, step-down every 10 s | PASS: final fsync max 0.12 s |
| 20k attempt 2 | node9901, `85602ccf2`+K15 | 20,000, 4 writers, buffered | stopped by direction at 6,535 records after 390 s: 0 REPORT retries, 0 server completion retries, no RPC slow-logged |
| baseline 20k | node9901, `2f92f2f46` | same | did not start: old client needs an export label (harness `--client-label` added afterwards) |

Attempt 1 findings on the 4 vCPU efs3 VM, at 58–80 % iowait:

- The rate fell from 1.57 to about 0.3 records/s within 40 minutes.
- Each write took about one REPORT (type 67) and one APPEND_RESERVE
  (type 71). Their p50 latency rose from 1.1 to 1.5 s.
- One APPEND_RESERVE exceeded the 30 s receive bound (20:59:39Z). It overlaps
  a coordinated transaction recovered at age 12.7 s (`decide-abort rc=-13`)
  and a 13.8 s GC stage.
- From 20:56Z the K22 session's private cluster shared the VM disk.

This is W97/D30-class persistence latency, not shape-A completion cost. With
the current client, appends publish every 32 writes or 1 s, and foreign
writers hand off per write. So no REPORT carries thousands of reservations,
and the W52 trigger is now bounded by the client. The per-REPORT reservation
count was not instrumented.

## W64 results

Matched step-down gate, efs3, base `7c510c60f` **without** the fix. Four
writers wrote 600 records while both groups' leaders stepped down every 20 s
(50 events over 650 s).

- **Integrity PASS.** All 596 acknowledged records are present exactly once
  warm, on the peer and cold, in order. The 4 failed writes are not visible,
  and there are no holes.
- **Availability FAIL.** Four writes returned EBUSY (errno 16). REPORT
  completion returned BUSY for 5–7 s after each step-down: 30 BUSY and 12
  NOT_PRIMARY server retries. The client's 8 s budget expired twice.
- **Cause.** Interrupted append reservation transactions, with 10–11
  participants, stayed PREPARED until `txn-recover ... age=7.0–7.4s -> ABORT`.
  This led to the fix above.

The matched after-fix gate never ran. The pairs planned on node9901 were step-down
(8,000 records, interval 4 s) and kill (8,000 records, interval 12 s, 3 s down),
each without and with the fix. The queue was stopped by direction before them.
The only after-fix live failover evidence is the 400-record node9901 smoke,
which had a single step-down event. **W64 failover acceptance is NOTRUN.**

### K5 / W72 boundary

These runs left no hole. Still, a reservation whose RPC outcome is unknown
can commit on the server while the client gives up and returns an error. That
OPEN reservation is owned by a still-live, fixed-epoch mount identity. Nothing
completes or retires it until session cleanup, and the frontier cannot pass it.
K5 must provide three things:

- a durable production session per mount with epoch registration;
- fencing or expiry of that session, so `raft-session cleanup-appends` can
  retire its OPEN reservations after a leader change;
- a client rule that an abandoned reserve under a live session either replays
  with the same identity or is explicitly abandoned under that session.

The same failover gate with an injected lost reserve reply is then the
acceptance test.

## Reproduce

Prerequisites: a Linux host with FUSE, `EFS_MD_RAFT_N=3` (set by the harness),
free ports PORT+1..PORT+3, and an empty root directory on a filesystem with more
than 20 % free. On node9901, also set
`LD_LIBRARY_PATH=/data1/efs/deps/libfuse/lib64` and build with
`PKG_CONFIG_PATH=/data1/efs/deps/libfuse/lib64/pkgconfig`.

```
make efsd efs-fuse efs-mgmt
python3 tests/live/append_failover.py --rel . --root /tmp/k15/w52 --port 18300 --records 20000 --writers 4
python3 tests/live/append_failover.py --rel . --root /tmp/k15/sd --records 8000 --writers 4 --failover step-down --interval 4 --first-event 3
python3 tests/live/append_failover.py --rel . --root /tmp/k15/kill --records 8000 --writers 4 --failover kill --interval 12 --first-event 5 --down 3
```

Add `--direct` for direct I/O. Pass `--client-label default` to the baseline
(`2f92f2f46`) client. The JSON report lands in ROOT/report.json and the exit
status is 0 only on PASS. Cleanup: the harness stops its daemons and clients.
Remove ROOT with `edelete --force --delete`.
