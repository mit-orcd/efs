## 1. K32 entry count: the test was wrong

**Diagnosis.** Part B of the test runs the production K13 ticket owner
(`src/client/put_ticket_owner.c`) with eight job threads per write and
counts the admission RPCs. The sender of each Raft group's ADMIT_BATCH
waits for the rest of its cohort, **bounded** by `EFS_PUT_ADMIT_LINGER_US`
(1 ms). Under eight concurrent commands on eight CPUs a job thread can stay
descheduled past 1 ms after the start barrier. The sender then sends the
three tickets it has, and the late ticket, alone in its group, takes the
single ADMIT: one extra entry for that write, `65+64` instead of `64+64`,
and the derived `per_write` above 3.0. Those are exactly the two failing
asserts (base, 40 failures: 28 on the admit count, 12 on `per_write`).

**Decision: the product behaves as designed; the test asserted more than
the contract promises.** The contract (`client_internal.h`,
`put_ticket_owner.c`) is a bounded linger with an exact fallback. A late
member costs one extra entry and nothing else, because admission is
idempotent and the single ADMIT keeps its verdicts and retries. Making the
cohort deterministic would mean an unbounded wait. A member can be late
for real reasons (a session admit RPC, the ledger-full retry loop that
sleeps 20 ms per attempt), and every write would then stall behind its
slowest chunk. The 1 ms bound exists so that it does not.

**Change.**

- `EFS_PUT_ADMIT_LINGER_US` can be overridden at compile time
  (`#ifndef`). Product builds are unchanged at 1000 µs (no Makefile sets
  it).
- `tests/test_k32_entry_count.py` Part B and `tests/test_put_ticket_owner.py`
  (same exact-count pattern, `batch_admits==2`) compile a 20 s linger. The
  sender's wait then ends when all eight members have queued, not on the
  timer, so the exact K32 targets (`64+64` admissions, `8+8` settles,
  3.0 entries per 1 MiB write) hold however the threads are scheduled, and
  the runs take no longer.
- A new Part B run keeps the production 1 ms linger and stalls one member
  per write for 100 ms. That member must be admitted alone by the single
  ADMIT (the sender did not wait for it) and every ticket must be admitted.
  This proves the bound and the fallback that the counted runs no longer
  exercise.
- `scripts/k32_load_check.sh TREE [K32_RUNS] [OWNER_RUNS]` appends a
  throwaway target to a scratch tree's Makefile and runs it through
  `scripts/make_test_summary.sh` at `EFS_TEST_JOBS=8`.

## 2. W149: fault variables in normal builds

K24 (`19555889f`, merged Oct 22) already did the move: the hook is
`EFS_FAULT_COMPACT_DIE` inside `#if EFS_FAULTS` in `src/kv/kv_compact.c`,
and `test_kv_lsm`'s use moved to `tests/faults/test_kv_compact_crash`, whose
Makefile rule compiles its own `kv_compact.c` with `-DEFS_FAULTS=1`. The
work-queue row was stale. What was missing was the clear message: a
normal build ignored the variable silently, so a fault run on the wrong
build could pass without its fault.

- `efs_faults_env_ignored(prog)` (`src/common/common.c`) prints one stderr
  line for each `EFS_FAULT_*` variable, and for the removed
  `EFS_KV_COMPACT_DIE`, found in the environment:
  `efsd: EFS_FAULT_COMPACT_DIE ignored: this build has no fault hooks (build
  with EFS_FAULTS=1 for fault tests)`. The value is not printed.
- `efsd` and `efs-fuse` call it at startup under `#if !EFS_FAULTS`. The gate
  is decided per binary, so `tests/shutdown_faults/efsd` (compiled with
  `-DEFS_FAULTS=1` against a plain `libefs.a`) prints nothing.
- Ignore rather than refuse: a refusal would stop every daemon that a
  harness starts with a fault variable left in its environment, and the
  variable has no effect in a normal build either way.
- `tests/test_faults_env_ignored.py` (in `make test`) checks the call sites
  and that the hook stays only inside `kv_compact.c`'s `EFS_FAULTS` block.
  It runs the helper with a clean environment (no output) and with
  `EFS_FAULT_COMPACT_DIE`, `EFS_KV_COMPACT_DIE`, `EFS_FAULT_DRAIN_FILE`,
  `EFS_FAULTS` and `EFS_KV_COMPACT_DIEX` set (exactly the first three
  named). A plain `./efsd` on nuc with two such variables printed both
  lines before its argument error. `docs/using/power-user.md` records the
  notice.

## 3. W140: K2's allow-list, and the one gap

**Checked.** `EFS_MD_CMD_APPLIED` (`include/efs/meta_cmd.h`) lists 56
tags. They include K32's `PUT_TICKET_ADMIT_BATCH` 90 and
`PUT_TICKET_SETTLE_BATCH` 91, K33's `MEMBERS` 92 and D31's
`PUT_TICKET_DRAIN` 250. `tests/test_submit_unknown_tag.py` derives
everything from the table, so these were covered without edits:

- the dispatcher handles exactly the table's tags;
- the 256-value predicate holds;
- every `efs_raft_propose` call is inside `host_propose_impl`, behind
  `host_tag_refused`;
- tag 200 is refused before a real Raft log.

`tests/test_kv_kind_unique.py`: 80 distinct Raft tags.

**Gap found and fixed.** The gate looked only at byte 0. `TXN_BATCH`
(88, in the table) carries its commands' tags inside the frame. The submit
RPC's generic path proposes any remaining command, and a forwarded
TXN_BATCH is legitimate (`host_propose` on a follower goes to
`host_remote_cmd`). So a TXN_BATCH with an inner tag 200, an inner PUBLISH,
mixed inner tags, a bad count, a cut or trailing frame, or an
out-of-range shard was committed. `apply_txn_batch_cmd` returns
`EFS_ERR_UNSUPPORTED` for each of these, which halts the group (W127):
the W140 failure through one level of nesting. Now:

- `txn_batch_frame_check` (`src/server/raft_host.c`) is the apply's frame
  check, factored out.
- `host_tag_refused` runs it for TXN_BATCH and refuses such a frame with
  `EFS_ERR_PROTO`, through the same rate-limited line.
- A frame naming another group's shard is a verdict at apply (`INVAL`, not
  a halt), so it passes the gate as before.
- `tests/test_submit_unknown_tag.py` checks each refused case and that a
  well-formed batch passes. `tests/test_txn_batch_apply.py` compiles the
  shared check.

**Remaining.**

- The W140 cluster gate (tag 200 to group 0 through the RPC answers PROTO;
  log and applied index unchanged; the group keeps serving) is **NOTRUN**.
  It belongs to the parent session.
- **Follow-up, not numbered here:** a payload problem, not a tag problem.
  Several handlers of *allowed* tags also return `EFS_ERR_UNSUPPORTED` for
  a malformed payload (for example an `EXPIRY_POLICY` whose length is not
  46). Submitted through the RPC, such a payload would also halt a group.
  A per-tag shape check at the gate, or a non-halting verdict for
  RPC-submitted payloads, needs its own item. W133 already limits who may
  submit.
