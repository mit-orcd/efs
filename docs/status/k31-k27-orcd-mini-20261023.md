## K31: devel RDMA clients lost every reply after the daemon fork

**Symptom.** orcd-mini freshly formatted on devel `bf16436e8`: daemons
healthy (both groups led, peers in sync), but every FUSE client over RDMA
stalled. Small replies arrived, the first larger one (a 453-byte
INODE_GETATTR reply, 485 bytes on the wire) never did; each reconnect
repeated it; LOOKUP/GETATTR timed out at 30 s and `mkdir` returned EIO. The
same client over TCP against the same cluster worked.

**Evidence (run1, raw files on node9901, see below).**
- RDMA counters: the server's connection shows the reply sent
  (`data_tx=1/485 app_tx=1/453`), the client's shows nothing received
  (`data_rx=0/0`). On the first connection three small replies arrived and
  the fourth did not.
- HCA counters of mlx5_0 before, during and after: no error counter moved
  (`resp_local_length_error`, `out_of_buffer`, `rnr_nak_retry_err`,
  `req_cqe_error` and the rest all 0 delta). The frame was delivered into
  the client's receive CQ; the client never consumed it.
- Client log order: RDMA transport up and `session uuid=... epoch=1` at
  14:24:39.751–.752, `efs-fuse daemon pid=...` at .755.

**Cause.** K5 (`1a6493590`, W72 mount session) moved
`efs_client_session_start()` before efs-fuse's daemon `fork()`. Over RDMA
that first RPC initialises the device and starts its shared receive-CQ
poller thread (`dev_shared_cq_start`). `fork()` keeps only the calling
thread: the serving daemon inherited a device marked `poller_started` and no
poller, so completions accumulated in the CQ and were never pushed to a
connection. The three early replies were consumed by the parent's poller
before the fork. TCP has no poller, so TCP mounts and every Oct 22–23 gate
(all TCP) passed; RDMA unit tests are NOTRUN on hosts without RDMA. The
partial bisect before analysis bounded it to the K22/K5 merges
(`c516e58e2` good, `ccd354d41` bad), consistent with this.

**Fix (`24e58fb1d`).**
- `efs_fuse_main_mt`: the session starts after `fork()`/`setsid()`, before
  the FUSE session is created; a failure exits through the cleanup path and
  the waiting parent reports it.
- `dev_shared_cq_start`: records the poller's pid; use from another process
  is refused with one log line (fail closed) instead of a silent hang.
- `tests/test_rdma_fork_poller.py` (fast `make test`): order and guard;
  fails on the pre-fix sources (negative control run).

**Verification.** A private three-daemon RDMA cluster on node9901 (ports
17781–17783, `/tmp`), RDMA client: stat, mkdir, ls, 1 MB write and readback
— FAIL on `bf16436e8`, PASS with the fix. `make test-all` on xorinox: every
command passes except `test_session_latch_tsan.py` and `test_apply_ring.py`,
which cannot link because xorinox has no libtsan (host limitation, also seen
by the W154 session). Live orcd-mini: below.
