## Step 1: the import path as it was

| Stage | Where | What it did |
|---|---|---|
| chunks | `host_snap_chunk`, `src/server/raft_host.c` (pump thread) | The leader's InstallSnapshot chunks are written to `snap-<g>-<incl>.part` in `mdraft`; the last chunk is fsynced and the import is queued (`SNAP_IMP_QUEUED`); the chunk returns `BUSY` and the leader retries it. |
| prepare | `host_snap_import_pass` (GC thread) | Flushes the memtable, exports a pinned view of the group to `snap-<g>-import-local.kvx` (streamed, sorted, unique), then calls `efs_kv_group_import_prepare(incoming .part, local export)`. |
| apply | `snap_import_poll` (pump thread) | One `HOST_SNAP_SLICE` (1024 keys) of the prepared diff per pump cycle through `efs_kv_batch`, with `snap_batch` set; the ack (OK) is returned only when the cursor reaches the end. `host_apply` of that group answers `BUSY` for the whole import (`import_block`), and queries are refused while `import_state != IDLE` (`host_query_capable`). |

Who calls what: `efs_kv_group_import_prepare` had exactly one caller, `host_snap_import_pass`; its result is stored in `host_group.import_diff` (plus `import_hold_a/b`) and consumed only by `snap_import_poll`; `snap_import_free_diff` frees it (done, cancel, newer snapshot). Tests call only the older in-memory `efs_kv_group_import`.

**Where the memory was allocated and when it was freed.** The apply was already batched; the prepare was not bounded. `read_whole` read both images whole into the heap (incoming and local), `parse_image` built one 40-byte `efs_kv_item` per record for each, `qsort_r` sorted them, and `diff` was a third array of up to `n + ln` items whose keys and values point into the two file buffers. The two item arrays were freed at the end of prepare, but the two file buffers (`hold_a`, `hold_b`) and the diff array stayed resident until the last slice was acknowledged (or the import was cancelled). So the peak was image(incoming) + image(local) + 40 B x (n + ln) x 2, and the held remainder was images + diff, a function of the image sizes, not only of the diff.

**What makes the import atomic today, and what a crash leaves.** Nothing makes it atomic. Each slice is one `efs_kv_batch` (atomic by itself); the diff as a whole is not. The node-local Raft cursor key (`\xff\xffraft`+group) is outside every group image (shard prefix above 4095), so it is not written by the import and still names the last entry applied before the snapshot; the import state (`import_state`, the diff) lives in memory only. A crash after k slices leaves the group's keyspace as a mix of the old rows, the rows of slices 1..k, and the rows the later slices would have written. On restart the member's Raft state still says it is behind the leader's log floor, so the leader sends the snapshot again; the new import diffs the incoming image against a fresh export of what is in the KV then, so it converges to the leader's keys whatever the mix was. While the mix exists the member is not in a state the protocol treats as caught up: it votes and campaigns on its log (old), and a read is proven by a ReadIndex that needs the local apply to reach the leader's commit, which cannot happen before the snapshot is installed. That is the same after this change; the design below does not change crash semantics, it only changes how much memory the importer holds.

## Step 3: design

The smallest bounded design needs no wire or on-disk change. Both images are already sorted by key and free of duplicates: the leader's image and the local one are both written by `efs_kv_lsm_view_export` (a heap merge in `kv_key_cmp` order, which is the order `cmp_bytes` uses, newest segment wins, one record per key). The diff is therefore a merge of two forward readers; nothing needs to be sorted or held.

* `efs_kv_import_open` (GC thread) opens both files, then reads each once from front to back through a 256 KiB window before any write: framing, tag, lengths within the file and within the LSM key and value limits (64 KiB and 16 MiB), key in the group, no bytes after the last record, strictly ascending keys, and for the incoming image the reserved-kind refusal and the PACK_V2 reader barrier (`import_reader_barrier`, now `import_barrier_item` per record). A malformed or unsorted image is refused (`EFS_ERR_PROTO`) with nothing written; the old code sorted an unsorted image instead, which no producer of these files emits.
* `efs_kv_import_step` (pump thread, one per cycle) merges the two readers forward, copies the next diff records into a batch arena and applies them with `efs_kv_batch`. A batch ends at 1024 keys, 1 MiB of key and value bytes, or 16384 records merged (so a long run of equal keys does not hold the pump). If `efs_kv_batch` fails the same batch is applied again by the next step; a read error is sticky (a half-built batch cannot be resumed).
* Memory is two read windows (256 KiB each, grown only to fit one record, at most 16.06 MiB), one batch arena (1 MiB plus one record) and 1024 item headers: constant in both the image and the diff size. For records of 4 KiB or less it is under 1.7 MiB (1.3% of the 128 MiB key-value budget); with the largest possible record it is under 50 MiB. This memory is separate from, and additive to, the memtable and L0 accounting the budget covers; the budget and every cap are unchanged.
* The two files stay open for the life of the import. The GC thread unlinks the local export right after open (a crash then leaves no file); the incoming `.part` is unlinked at the end as before.
* Crash or leader change in the middle: unchanged semantics, as analysed above. A cancel (a newer snapshot starts at offset 0) closes the importer and discards the remaining diff, as it discarded the array before. A restart loses the importer and the next InstallSnapshot starts a new one from a fresh local export. No durable "import in progress" marker was added: the member's Raft state, not its KV, decides whether it is caught up.
* Cost: the images are read twice (once to validate, once to merge) instead of once; both are sequential reads.

## Review follow-up (coordinator review of `2dde38d18`, six items)

Code in `7c74a50e9` and `21d0b5b96`. All line numbers are `raft_host.c` at `21d0b5b96` unless a file is named.

**1. A failed importer looped forever on a one-chunk image (fixed).** `snap_import_poll` put a failed importer back to DONE and returned its sticky error; the leader resends a one-chunk image from offset 0 with `done=1`, which `host_snap_chunk` (line 3994) sends to `snap_import_poll` before the offset-0 cancel, so the dead importer answered every resend and `import_block` stayed set. A step error other than `EFS_ERR_BUSY` now discards the importer, returns the state to IDLE, clears `import_block` and invalidates the GC watermarks (the FAIL path's own steps); BUSY keeps the importer for a retry of the same batch. The resend then queues a fresh import. Test: `tests/test_snap_import_host.c` (the real `host_snap_chunk`, `host_snap_import_pass` and `snap_import_poll` from `raft_host.c`, compiled into the test like `tests/decoders/apply.c`, over LSM stores): an 800 KB single-chunk image is cut after open, the step fails, the test requires IDLE, no importer and `import_block` clear, then the resend converges to exactly the image. Without the fix it stops at "the failed importer is discarded" (`scripts/evidence/fn/fn_fails_before.sh`, variant a). The comments in `kv_snap.h`, `kv_snap.c` and `test_failed_batch` now say what the host does: the importer keeps a batch the KV refused and a further step applies it; the host steps again only on BUSY and discards on anything else.

**2. The Raft snapshot record could become durable before the last import batch (real; fixed).** Read, not assumed: the pump takes the KV WAL hold at 8900, runs `drain_inbox` at 8902 and releases (the fsync) at 9020. `kv_wal_append` does not fsync while `hold > 0` (`src/kv/kv_wal.c:290`). The chunk handler runs inside `drain_inbox` (`raft.c:2244`, `r->snap_chunk`); when the last step returns OK the same call goes on to `snap_installed` (`raft.c:2268`), which saves the config and then the snapshot record (`raft.c:2110`; `disk_save_snap` appends a `RAFT_REC_SNAP` at `src/raft/raft_disk.c:511`), and `raft_log_append` fsyncs it at once unless the disk's own sync hold or a batch defer is active (`src/raft/raft_log.c:300-304`); the pump takes neither around `drain_inbox`. So the record could be on disk with the last batch only in the KV WAL's unsynced tail; a crash would leave a Raft state that says "installed" over a KV missing its last keys. The existing primitives did not fit: `efs_kv_lsm_sync_prefix` needs a prefix that only `efs_kv_lsm_sync_detach` yields, and detach gives up the pump's hold. A new `efs_kv_lsm_sync_now` (`kv_wal_sync_now`: fsync everything appended so far, under any hold; the hold stays owned) is called at line 3907 on the step that returns done, before the chunk is acknowledged; a failure there is a step error, so the importer is discarded and the install repeats. Test: the host test takes `efs_kv_lsm_sync_hold` as the pump does, drives the import to OK, then asks `efs_kv_lsm_sync_covered` for the WAL's frontier, which must be durable. This asserts the durable frontier at the exact instant `snap_installed` would run instead of injecting a failure between the two points: the ack is the only thing that orders them and the frontier at that instant is what a crash there would leave, so the check is the same property without a fault hook. Without the fix it stops at "every import batch is fsynced before the ack" (variant b). The reverse window (batches durable, record not) is the mix case already analysed above and is healed by the re-install.

**4. `import_block` after a cancelled run whose open succeeded (fixed).** `host_snap_import_pass` stored the importer only if the generation and state still matched; when a newer InstallSnapshot had cancelled the RUN while `efs_kv_import_open` ran (cancel of RUN leaves `import_block` to the GC thread), the success path closed the importer and went on without clearing it, so `host_apply` of the group returned BUSY until some later import cleared it. It is cleared there now. Test: a link-time wrap of `efs_kv_import_open` cancels the import from inside its open; the test requires IDLE, no importer and `import_block` clear, and then that the next InstallSnapshot converges. Without the fix: "a cancelled run whose open succeeded leaves applies unblocked" (variant c).

**5. Can an apply land after the local export? (fixed for applies; writers outside the apply path argued, not individually audited).** `import_block` is set by the GC thread without `h->mu` (line 11441 onward, before the flush and export) and `host_apply` tests it only on entry (line 3560). So an apply already past that test could write after the export, where the diff could never correct it (a key it creates that the image lacks would survive). That was a real window. Every apply is made by `apply_committed` in the Raft core, reached from `efs_raft_propose`, `efs_raft_change`, `efs_raft_read_begin`, the message handlers and the tick; `src/raft/raft.c` contains no mutex (`grep -c pthread_mutex` is 0), so the host serialises every core call under `h->mu` (its own comments say so at lines 1330, 3052, 5560, 5598 and 5956; a handler under `h->mu` uses `efs_raft_note_durable`, which applies nothing, line 5905), and `host_apply` runs only there. This is read from those comments and call sites, not enforced by an assertion. The pass now takes and drops `h->mu` once after setting `import_block` and before the flush and export: any apply that began before the block was visible has finished, and any later one sees it and returns BUSY. Test: the host test wraps `pthread_mutex_lock` and `efs_kv_lsm_flush` and requires that `h->mu` was taken between the block and the flush; without the barrier it stops at "the pass waits out a running apply" (variant d). Deadlock check: the pass holds no lock at that point (`snap_mu` is released; the rule "never taken under h->mu from the GC thread" in `struct efs_raft_host` concerns taking `snap_mu` under `h->mu`, not this), the pump never waits for the GC thread while holding `h->mu` (it answers BUSY and polls), and the GC thread is joined without `h->mu` held (line 14168). The i-after runs above, with the real pump and both groups importing, finished with both INSTALLED; that is the liveness evidence.

Handler-thread writes: the comment above the pump's hold (line 8870 area) mentions handler-thread KV writes of session and lock rows. Those rows are group state (shards 1 to 4095), so a write to them outside the apply path would diverge the replicas whether or not an import runs; the locks (`efs_lock_grant`/`release`), session (`efs_session_*`) and lease writers are called from `apply_lock_cmd` and `apply_session_cmd`, and a grep of every state-writing function of `src/meta/*.c` against `src/server/*.c` finds callers only in `apply_*` functions and in `host_*` helpers that run the proposer-side transaction on top of Raft proposals (`host_append_*`, `host_close_append_step`, `host_regular_mtime`, `host_mkdir_alloc_reserve`, the GC-thread `host_put_*_pass`, `host_pack_session_cleanup`). Those helpers were not traced one by one; the node-local rows (`\xff\xffraft`, shard > 4095) are outside the images by construction. A writer of group keys outside Raft would be an existing replication bug; it is not excluded by a test here. Owed: that per-writer audit, or a write-path assertion under the import.

## Not verified

* **Production scale.** The largest diff here is 390 k keys per group (36 MiB image); Task EZ's S2 diffs were 20.7 M to 31.3 M keys at the 128 MiB budget and production caps on three hosts. Owed: Task EZ's S2 method with member 3's RSS checked against its bound through the drain, and the 26-minute plateau gone. The one-time per-key cost matters there: the images are now read twice and the merge runs on the pump, 16,384 records per cycle; the time to install 30 M keys was not measured.
* **Where the peak sits.** After the change the import-window peak is flat at about 29 MiB in these runs, but the release burst (28 to 76 MiB before any import) and the memtable (up to the 128 MiB budget) are separate, bounded components that were not reduced and are not part of this fix.
* **Crash and leader change at cluster level.** Atomicity was analysed (above) and exercised in the unit test and in one daemon `SIGKILL` mid-apply of both groups (member re-installed and caught up to its leaders' commit index). Not exercised: a leader change during the import, repeated kills, a kill while the images are still being validated, and a key-by-key comparison of the restarted member's KV with the leader's. The claim that a half-imported member cannot vote or be read as caught up rests on the Raft state (log and ReadIndex), read in the code, not on a test of that property.
* A record larger than 4 KiB raises the bound (largest possible record: about 49 MiB); no such image was tested.
* The `k37_segment_rebuild` TSan failure was not rerun on devel.
* **Writers outside the apply path** (follow-up item 5): the `h->mu` barrier closes the window for applies. That no other thread writes group keys during the export is argued from the replicated-state rule and a caller grep, not audited writer by writer and not asserted at run time.
* **Longest step**: reported as measured (no better than before; one 54.5 ms step); the cause was not isolated, and no distribution of step times was kept, only the maximum per group.
* **Crash between the last batch and the snapshot record** is covered by an observation of the durable frontier at the ack, not by a kill at that point in a running daemon.
