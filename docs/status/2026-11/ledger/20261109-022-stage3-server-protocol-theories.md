# Stage 3 theories: server side and protocol level

[Stage 3 theories: server side and protocol level](../stage3-server-protocol-theories-20261109.md): **theories only, no code, no run, no K row, blocks alpha: no** (Nov 9, devel `9bb50fe79`). A code review asked for by the user, entered in section P of the checklist as P3-G to P3-K. Reading of the existing measurements: the daemons are idle on the measured workloads (9 of 192 cores for 1,649 creates/s, leader samples 63 % in the kernel, about 20 context switches per file), so throughput is set by the latency of one consensus round and by the sequential rounds per operation. P3-G: a round wakes a sleeping thread eight times (pump, per-peer sender, follower connection, follower pump and back) and the pump never spins; refuted if `EFS_WRITE_PROF` shows `persist` above `commit_apply`. P3-H: up to five consensus rounds per tiny file, W94 measured about +20 % per round removed; the content-bound ticket lets admission and publication share an entry, which needs the user's scope decision. P3-I: read-only opens take and return a replicated lease. P3-J: Task U's single-ADMIT follow-up, combined at the leader. P3-K: the 200 ms `syncfs` barrier writes back buffered KV compaction output, a candidate cause of the p99 tails. Left out with numbers: per-group owners, apply, memtable, RDMA poller, formats, a clock-based read lease.
