# K42 reopened: `append-reap-owed` (Task FP)

[K42 reopened: `append-reap-owed` (Task FP)](../k42-append-reap-owed-20261110.md): **cause found and reproduced on devel, fixed with regression tests; 20 of 20 clean stops on a private 4-member TCP cluster with the reaper stopped; the RDMA multi-host gate is still owed, K42 stays OPEN until the coordinator rules** (Nov 10, branch `claude/kind-agnesi-20633e` on devel `7cd0a2637`, code `ce2c61998`; not merged, not pushed; the K42 row and the counts line are not edited). The step that retires a revoked session's append rows answered a certified BUSY `append-reap-owed` for every row on an inode that was already gone, and the client only polled it every 50 ms for the whole 20 s budget: only `REAP_MULTI` removes those rows and its only driver is the group leader's GC pass (512 markers per pass, one queue for every dead inode, idle passes wait 1 s), so nothing bounded the wait. Reproduced on devel by stopping the reaper (`EFS_FAULT_GC_DISABLE`), appending to and unlinking files, then a clean unmount: 0 of 20 exit 0, cleanup 20.07 to 20.12 s, client reason `append-reap-owed` 9 times and `uncertified-busy` 11 times (all 197 server steps sampled were the same wait). `retire_dead` in `src/meta/append_plan.c` now deletes the session's own receipt and reservations of the dead inode (up to 11 rows) in one guarded transaction, so the stop no longer depends on the reaper; other sessions' rows stay with it. After: 20 of 20, cleanup 1.56 to 1.61 s; 10 of 10 with the reaper running; `e2_peer_stop_loop.py` 3 x 20 of 20; `make test`, the three `tests_for` components, TSan (31 run) and ASan (59 run) PASS on intel1; new `tests/test_k42_reap_owed.py` (fails on devel in 25 s) and `dead_inode_retired` in `tests/test_append_cleanup.c`. Findings left: the append cleanup costs one three-phase transaction per inode (about 63 ms per dead file, 21 ms live), so about 300 inodes on one shard exhaust the 20 s budget (the live-inode path fails earlier, at 200 to 300 files); the client loses the certified reason at the deadline when a final `NOT_PRIMARY` resets it; `EFS_META_APPEND_WAIT_GONE` is now dead server-side.
