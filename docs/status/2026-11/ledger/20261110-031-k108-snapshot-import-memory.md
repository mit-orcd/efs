# K108: snapshot import builds the whole diff in memory (Task FN)

[K108: snapshot import builds the whole diff in memory (Task FN)](../k108-snapshot-import-memory-20261110.md): **FIX on a branch, small-scale PASS, production-scale check owed** (Nov 10, branch `claude/sleepy-solomon-4b29a7` on devel `cff8eb424`, code commits `a7ff25741`, `7c74a50e9`, `21d0b5b96`; not merged, not pushed), K108 (drafted as K120 on Task EZ's branch), blocks alpha: yes, row and counts line untouched. The importer read both snapshot images whole and held them with the diff until the last slice was acknowledged; it is now a streaming merge of the two sorted images (`efs_kv_import_open` validates both before any write, `efs_kv_import_step` applies one batch of at most 1024 keys / 1 MiB per pump cycle), so the heap is two 256 KiB windows plus one batch (1.6 MiB logged) whatever the image or diff size, with no wire or on-disk change and no cap, budget or timeout touched. On intel2 (three private members, member 3 stopped then released into InstallSnapshot, 2 MiB memtable so the memtable fill does not hide the importer) the import-window peak RSS was 58, 77 and 138 MiB before for diffs of 80 k, 184 k and 390 k keys per group and 31, 28 and 29 MiB after; a new unit test holds a 7,000-key diff over 24 MiB images under 2 MiB of heap (devel: 48 MiB). Crash semantics are unchanged (nothing is atomic; a restarted member is re-sent the snapshot and the new import diffs against what is in the KV): a unit test cuts an import after three batches and the restart converges, and a daemon killed mid-import re-installed and caught up. The coordinator's review of `2dde38d18` found six points, all settled on the page: a failed importer is now always discarded (a one-chunk image used to loop on the dead importer), the last batch is fsynced before the Raft snapshot record can be saved (the pump's WAL hold deferred it), the import pass waits out a running apply before its export, a cancelled run no longer leaves applies blocked, install time is unchanged (5, 10 and 20 s for 80 k, 184 k and 390 k keys; about 25 min at 30 M keys, set by the 50 ms retry period) and the longest step is not better (17 ms typical, up to 54.5 ms), with new unit shapes and a host-level test. Owed: a per-writer audit that nothing but applies writes group keys during the export; Task EZ's S2 production-scale method with the RSS bound checked through drain, and a key-by-key comparison of a killed-and-restarted member with its leader.
