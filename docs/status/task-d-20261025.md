## Checks and schedule

The endurance schedule uses actual elapsed time, not operation count:

| Event | Schedule | Required checks before another event |
| --- | --- | --- |
| Orderly member return | Every 600 s, shuffled round-robin among the initial five | Exactly one member stopped; protection, chunks and segments clean within 300 s; live-session orphan counts sampled, not prematurely collected |
| Daemon SIGKILL and return | Once per hour, 120 s before the hour | K36 verified, no uncertain/error root, no unresolved recovery work or unrecoverable reference, plus full protection within 300 s |
| Client SIGKILL and remount | Once per hour, 60 s before the hour | Victim mount's application operations drain first; peer continues writing; operator revoke of the exact killed session, remount and protection checks |
| Sixth member | 4,500 s, in hour two | Every member agrees on the six identities/endpoints |
| Seventh member | 8,100 s, in hour three | Every member agrees on the seven identities/endpoints |
| Exact manifest/append check | Every 900 s and at the end | Both clients exact; no digest learned from suspect readback |
| Status and sync-status | Nominal 30 s sampling, commands bounded | Raw protection, degraded chunks/segments, orphan counts, leadership and recovery state retained |
| RSS | Every 10 s, independent of status queries | `scripts/rss_plateau.py` on each quiet interval; no silently skipped short interval in the final verdict |
| Foreground metadata | Each writer iteration | stat/readdir child within 10 s outside churn; data operations within 60 s; churn operations bounded at 180 s |

Events execute serially. Late events never introduce simultaneous outages.
The run fails if it ends with an event unexecuted. On the first failure no
further churn is launched; owned processes are torn down and logs retained.

compressing all 33 endurance events into overlapping time windows: clean

incorrect requirement that active sessions' orphan tickets disappear before
revocation. These are
**test defects**, not demonstrated EFS product defects. Each has deterministic
coverage. All unsuccessful runs are retained rather than relabelled green.

The second run's first returning member had five nodes up, zero degraded
chunks/segments, zero unrecoverable segments and full protection, while two
orphan records remained. That is permitted by D31: collection requires a
revocation proof, not time passing. The corrected oracle preserves that
condition, fences only the exact killed mount UUID through the existing
`raft-session fence` operator facility, and at the end closes/revokes both
writers, remounts fresh readers, requires orphan pending=0 within 300 s and
verifies the full manifest again. It never clears a record or invents expiry.
See [D31's crashed-client limitation](k13-d31-drain-20261024.md)
and `src/meta/put_orphan.c`'s revocation checks. The negative controls require
nonzero/unknown orphan counts to fail after revocation, but permit live-session
pending records during ongoing writes.

The third run exposed a real race in the harness guard, not in EFS: it read
the owned-PID registry between native child birth and registration of the
returning node, then found that legitimate child in `/proc`. Starts, stops
and restarts now serialize with the guard's ownership snapshot and scan.
No path-based whitelist was added. A deterministic threaded regression
holds a spawn between native child birth and registration and proves the
observer waits; unrelated jobs are still refused.
