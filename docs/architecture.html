efs · master architecture · target: extremfs

A parallel filesystem that scales with the raw hardware

The specification the system is built against. Goal, failure model, consistency model, invariants, and the target design — with the current design drawn next to it. markdown source · increment plan

Naming intent. The bar is that efs earns the name extremfs: throughput tracks the aggregate hardware (NVMe + NIC), not a software serialization point. Every decision below is checked against that bar — a component is wrong if it serializes work the hardware could have done in parallel.

Two binding constraints. 232 on 4 nodes forces metadata out of RAM and onto NVMe, paged rather than serialized whole. The scaling bar forces the write path — not just reads — to parallelize across nodes and clients, including many writers to the same file.

2 · What we have today

One monolithic in-RAM table. Every flush serializes the whole table to find what changed, erasure-codes it into pages, and commits a root with two-phase commit. Leadership is “lowest live node id from each node's own local view.”

thinks is alive no term · no vote · no fence → split-brain EVERY BUG BELOW IS A FAILURE MODE OF THIS MODEL dual-writer root · extras-loss-on-adopt · catchup-vs-GC · peers pinned at old gen · rebuild drops unflushed ops

RAM is the wall blocks 2³²

The whole table lives in RAM on every server. Measured 1.9–3.4 KB/inode; the inode region alone at 232 is ~2 TB before overhead.

Flush degrades with size O(table)

incr=0 on 100% of growth flushes; ser=350ms/flush at 10M. Eviction faults slabs straight back in — it accomplishes nothing.

No consensus split-brain

Primary is a pure function of unreplicated local liveness. Two primaries are possible. The old root-2PC's commit point was an under-replicated coordinator.

Absent ≠ unavailable data loss

A failed slab fault returned ENOENT, so CREATE minted a second inode for a live object. The system cannot tell “not there” from “couldn't read it.”

3 · Where we're taking it

Three planes. Data: client-direct RDMA, 2+1 EC, immutable chunk generations. Metadata: 4096 virtual shards, one Raft group per shard, applied to an on-disk ordered KV. Control: membership + placement + safe reconfiguration.

One shard's write path

Metadata placement — the decisive decision

The dentry index stores a small projection, not a second copy of the mutable inode. One authoritative inode row; many dentries may point at it (hardlinks).

(parent_ino, name) -> (ino, generation, type)     // dentry: routing + handle check
(ino)              -> authoritative inode_row      // the ONLY mutable copy
Dentries live on the parent's shard, so create/unlink/readdir in a directory are single-shard and readdir is one range scan. Mutable attributes live only in the inode row, so chmod/chown/mtime/nlink can never diverge between two indexes. A huge directory past a threshold spreads its dentries by hash(parent,name) — the escape valve that keeps a 500M-entry dir off one leader, at the cost of a scatter/merge readdir for exactly those rare dirs.

Shards spread; leaders spread

One Raft group per shard, RF=3. A majority of 3 is any 2, so one node can die and the group keeps writing. Leaders spread across nodes, so metadata write throughput scales with node count — no single metadata primary to saturate. Leadership is real: elected by majority vote in a term, fenced by term — I1–I4 by construction.

3a · The extremfs property — a hot file does not serialize

The make-or-break case for “scale with raw hardware”: many parallel writers to the same file. If every pwrite Raft-mutated one inode row for size/mtime, a million writers would funnel through one shard leader while the data path sat idle. The design avoids that.

Chunk metadata is sharded too the load-bearing fix

If all chunk-map keys lived on inode_shard(ino), a million writers would still funnel through one Raft leader (Raft serializes the group's log). So chunk_meta_shard = hash(ino, chunk_index) & 0xFFF — one file's chunk publications spread across many leaders. Data and metadata both distribute.

Size = sharded high-water lanes

MAX() commuting removes the ordering dependency but not the physical serialization point. So size lives in L distributed lanes, each an idempotent MAX on its own shard; stat() takes the max over the current epoch's lanes. Truncate bumps the content epoch, invalidating all old lanes at once.

Sub-chunk RMW = generation CAS

Build candidate G+1 from committed base G, publish with CAS(expected=G); on conflict refetch, reapply the byte-range, retry. Disjoint byte-ranges both land. No whole-file lock.

O_APPEND — the only accepted hotspot

EOF allocation must serialize; that is semantic and unavoidable. It is the only same-file serialization the design accepts.

4 · Why the theory holds up

Raft-per-shard over an embedded KV is not a new mechanism. The claim is stronger than novelty: the design is a consequence of the constraints, and the argument is a derivation, not an analogy. A copy-cat cites a working system and imitates it; a derivation starts from what must be true and shows which shapes survive.

The constraints are forces, not preferences

ConstraintForce it exertsDesign it eliminates

The constraints do not mathematically force “Raft + ordered KV” — Multi-Paxos, Viewstamped Replication, B-tree/LSM/custom page stores satisfy the same forces. The honest statement: the constraints strongly favor a partitioned replicated state machine with persistent, paged applied state; efs chooses Raft and an ordered embedded KV because they satisfy that with proven, understandable primitives and minimal new protocol invention. That Ceph and CockroachDB landed in the same place is convergent evolution — the same forces act on any strongly-consistent, horizontally-scaled, fault-tolerant store, so independent systems solve the same equations. Convergence is evidence the derivation is correct, not that it was copied.

Safety = inherited theorems + explicit composition obligations

  • Core shard-replication safety is inherited from Raft when implemented to its assumptions (election restriction, log matching, commit rules, safe reconfiguration). Leader completeness (I2) is Raft's theorem — not majority intersection alone.
  • Quorum durability (I10/I11): a majority-acked write survives any failure that leaves a majority; with RF=3 that is exactly one node. The old root/snapshot 2PC did not provide this — its commit point was an under-replicated coordinator — and the bug history is the system repeatedly discovering that.
  • EFS-specific composition is not covered by Raft's proof. RPC dedup, KV persistence ordering, cross-shard transactions, FUSE cache coherence, EC generation publication, chunk RMW, reconfiguration, and the orphan lifecycle remain explicit proof / model / simulation obligations — exactly what the simulator is for.

What is genuinely ours — stated precisely

Every primitive here has existed — Raft, distributed metadata, RDMA, EC, immutable generations, ordered KV, directory sharding, deterministic simulation. Several systems get close to individual parts: WEKA (fully distributed data+metadata, no MDS tier, hash placement), DAOS (NVMe-native, distributed transactions, EC, versioned writes — but its POSIX layer still lacks hardlinks and distributed flock), VAST (transactional metadata + EC, but shared-everything DASE, not shared-nothing Raft shards), CephFS (client-direct data, but authority in a distinct MDS tier). IndexFS/GIGA+ precede threshold-spread dirs; FoundationDB is the canonical simulator. We claim none of these as inventions.

The claim is the composition and the governing principle. We have not found a public system presenting this exact architecture as one open POSIX filesystem: POSIX + no MDS tier + metadata authority on ordinary storage nodes + Raft only for small metadata + client-direct RDMA + immutable EC generations + no invented serialization + simulation-first + small-cluster simplicity. And the principle that ties it together: never serialize work that the semantics and the hardware allow to happen in parallel.

Metadata on a log, data on immutable-generation EC

Strong consensus where correctness is cheap (small metadata), EC where bandwidth matters (bulk data). Most systems pick one consistency substrate for both; efs uses the one that fits each cost model.

A hot-file path that does not serialize

Disjoint chunks publish to different metadata shards; size is sharded high-water lanes; sub-chunk RMW is generation CAS. A million writers to one file parallelize. Only semantically- required serialization (O_APPEND EOF, overlapping ranges, truncate, rename) is serialized.

The namespace is the database

Metadata is already a distributed ordered KV, so du/find/lifecycle are queries, not traversals — no crawler, no catalog bolted on, no cron forest.

Minimalist operations

3 nodes → efs init → efs mount → done; 64 nodes, same architecture. No MDS tier, no special node types, no kernel module, no twenty-component deployment.
Thesis in one line: the constraints force the family, Raft + KV are the proven primitives within it, and the part that is ours — the composition, the never-serialize-what-can-run-parallel principle, and the namespace-as-database minimalism — is where the design earns an identity. The principle is falsifiable: if a workload the hardware could parallelize is found to serialize in efs, that is a bug against it.
On the name. “extremfs” collides phonetically with XtreemFS (existing open-source DFS; trademark registered by Quobyte), and “EFS” is overwhelmingly Amazon Elastic File System. The idea is the identity; the public name should be distinctive and searchable, and is left open pending a trademark/search check. This document uses “efs” as a working name only.

6 · Invariants — the test oracle

A bug is a violation of one of these. The simulator checks them after every step; fsck checks them on disk. Invariants are stated over the committed, externally-visible projection; cross-shard intents are internal and governed by I17/I18.

Replication & leadership (Raft's actual safety properties)

I1 · election uniqueness — at most one server is elected leader for a shard in a given term.
I2 · leader completeness — every later elected leader contains every previously committed entry (Raft's theorem, not majority-intersection alone).
I3 · term fencing — a node observing a higher term immediately stops exercising old-term leader authority.
I4 · quorum acknowledgement — no mutation is acknowledged unless committed under the shard's current authoritative config. “No dual owner” = commit authority, not local belief.

Metadata state

I5 · name uniqueness — one visible name maps to at most one inode.
I6 · no visible dangling dentry — every committed visible dentry resolves to a valid inode.
I7 · nlink — nlink equals the number of committed visible links.
I8 · no resurrection — a committed removal is never reverted by replay/recovery/rebuild/stale clients.
I9 · absent ≠ unavailable — failure to establish authoritative read state never returns ENOENT. (the Sep 1 dangling-dentry class)
I10 · metadata durability — an acknowledged committed op survives any single-node failure.
I16 · request idempotency — replaying a mutation with the same op-ID cannot apply its effect twice.
I17 · transaction atomic visibility — a cross-shard transaction is visible as committed everywhere or nowhere.
I18 · safe reconfiguration — no config transition permits two disjoint authoritative quorums for the same history.
I19 · open-unlinked lifetime — an nlink=0 inode stays valid for pre-existing authorized open handles; never reclaimed/reused while valid.

Data

I11 · EC durability — a published chunk generation has ≥ 2 reconstructable fragments on distinct failure domains.
I12 · chunk consistency — every returned chunk is one valid committed generation and a legal serialization of committed byte-range writes.
I13 · generation coherence — reconstruction never mixes fragment generations.
I14 · publish-after-durability — metadata cannot publish G before G satisfies EC durability.
I15 · orphan-generation safety — unpublished generations are reclaimable without changing committed state.
I20 · stale-writer fencing — a stale client/node cannot overwrite or publish over a newer committed chunk generation.

Liveness (bounded, testable)

L1–L8 — shards eventually elect leaders; committed ops eventually apply everywhere; intact and empty replicas eventually catch up; prepared transactions eventually COMMIT/ABORT; orphans and unpublished generations eventually reclaim; reconfiguration eventually converges once failures stop.

7 · The simulator — build first, architecture-independent

A deterministic discrete-event simulator: N servers + M clients in one process. A seeded PRNG drives message order, drops, delays, duplicates, partitions, crashes, and clock steps. The real metadata state machine runs inside it against a simulated network and disk.

A cluster scenario runs in milliseconds; a failure replays exactly from its seed; you explore millions of interleavings overnight, each step checked against the invariants — so a bug is a seed + a named violated invariant, not a log line on a live cluster. The hardware cluster stops being the correctness oracle and becomes the performance harness.

The generator must produce: lost/duplicated client RPCs, restart with same vs empty disk, delayed packets from a prior incarnation, leader crash at every point around commit/apply/reply, snapshot creation during writes, interrupted snapshot transfer, membership-transition interruption at every step, coordinator/participant crash in every transaction phase, client crash between fragment PUT and metadata publish, and stale placement-map / stale chunk-generation clients. Complete operation histories are recorded and checked by an independent linearizability / transaction-history checker, not only handwritten invariants (the FoundationDB methodology). Scope: metadata layer only; the RDMA data path stays with the perf harnesses.

7a · Shortening the code → signal cycle

The bottleneck is not writing code — it is how long a change takes to prove itself. Today that proof is a 13-node wipe + rsync + rebuild + ssh orchestration, and the signal is poor. The strategy: push each class of bug to the cheapest layer that can catch it, and fill the deterministic gap the simulator occupies.

LayerAnswersCostCatches
unit (make test)is this function rightmslogic, encode/decode, pack/unpack
simulatoris the protocol right under any interleaving / failuremsmessage-ordering, leader/fencing, recovery, the §6 invariants

The simulator is the only missing layer that is both fast and deterministic. Unit tests can't see a message race; the cluster can't reproduce one. Building it first converts the slowest, noisiest, least reproducible part of the cycle (distributed correctness on hardware) into the fastest and most repeatable — and it becomes the regression gate for every migration step after.
  • Correctness moves down, performance stays up. The cluster stops being the correctness oracle; posix/posix2 confirm semantics; the cluster confirms speed.
  • Deterministic over flaky. Forced collisions (threading.Barrier) instead of fork-and-pray — no more “passes isolated, fails under load.”
  • Fail fast, not timeout. A violated invariant aborts at the step; saturation (timeout) is reported separately from correctness (assertion).
  • Live attach over rebuild-and-reprobe. ptrace is open on all 15 hosts — gdb -p on a wedged efsd answers in seconds.
  • Invariants as executable checks (simulator assertions + fsck), not prose.

8 · Migration — gated, never a big bang

The simulator comes first because it pays for itself against the current code and becomes the regression gate for every step after. Each step is gated; the system stays runnable throughout. Detailed steps live in the scaling roadmap.
