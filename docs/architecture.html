A parallel filesystem that scales with the raw hardware

The plan the system is built against: what we build, what may break, what must always be true, and how we get there. start here / next task · normative spec · why these choices · failure math · data protocol · transactions · directories · sessions & locks · performance · verification · development · increment plan

The bar. efs earns the name extremfs only if speed tracks the hardware you add — never a software bottleneck. Every decision below is checked against that bar.

The few words we use

WordPlain meaning
shardOne slice of the metadata. The inode space is cut into 4096 slices, each managed on its own.
RaftA proven protocol that lets a small group of machines keep one identical, ordered log — even when some crash.
leaderThe one machine in charge of a shard at a time, elected by majority. Only it accepts writes.
majorityMore than half of a group. An operation counts only after a majority has saved it — so it survives any minority of losses.

committedSaved by a majority. Never lost, never undone.

idempotentSafe to retry: twice has the same effect as once.
linearizable readA read that always sees the latest committed state — never stale.

serialization pointOne thing everything must wait in line for — a lock, one leader, one thread. The enemy.

0 · Governing principles

Four principles decide every hard case below.

PrincipleWhat it decides
P1 · Never serialize what may run in parallel Operations wait for each other only where POSIX semantics demand it (append-EOF, same bytes, truncate, rename) — never because two ops share a file or directory.
P2 · Keep together what must be saved together; spread the rest Place data so the common operation is one entry on one shard — before reaching for any multi-shard protocol.
P3 · Make stale work harmless, not impossible Version numbers everywhere. A stale actor may still do work; it can never make that work visible.
P4 · The fast path never crosses cores, memory domains, or locks it doesn't need Paper scaling fails if each node leaves half its hardware idle. Ordinary operations run on the local core, asynchronous, deep-queued, no cross-core lock (§3c).

Flash-only is a decision, not an omission — and the design spends it. Random access is cheap (no seek), queues are deep, latency is microseconds. That is what makes write() = durable affordable, and what the P4 execution model stands on — a spinning disk could not run it at all. No SMR, no rotational tricks, no track alignment: entire problem classes deleted. The scaling claims do not transfer to disks.

Two constraints bind everything. 232 on 4 nodes forces metadata out of RAM onto NVMe, paged. The scaling bar forces writes — not just reads — to spread, including many writers to the same file.

The scaling bar, measurable. When operations don't semantically conflict, throughput must grow with the cluster's total NIC, NVMe, CPU, and memory bandwidth (adjusted for protection). If a benchmark stops early and the answer is software — a lock, one leader, one thread, one log — that is by definition an EFS bug.

Failure tolerance is a configured promise, not a constant

f = how many machines may die permanently at once with no data loss (max 3). The headline rule is wonderfully simple: the promise needs N ≥ max(2f+1, k+f) — then losing any f machines leaves a metadata majority and ≥k data fragments, so the system stays authoritative automatically. No quorum override, no disaster mode:

N nodesmax f (automatic)metadata copiesdata ECpromise
3132+1lose 1: no loss, stays authoritative
4132+1lose 1: no loss, stays authoritative
5252+2lose 2: no loss, stays authoritative
6252+2lose 2: no loss, stays authoritative
≥ 7372+3 (or wider k: 4+3 = 1.75×)lose 3: no loss, stays authoritative
f=3 needs 7 nodes, not 5 or 6. On 5 nodes the majority is 3 — and the 3 dead machines could be exactly that majority. There is no N = 2f mode. After a permanent majority loss, no rule over the surviving logs can reconstruct what was committed — that information died with the majority, and splicing survivor logs can invent a history no leader ever authorized. Permanent majority loss is disaster territory (an operator procedure over surviving state), not an efs operating mode. Changing f is an online operation with an explicit transition state: effective_f only becomes target_f after replicas are added, every data stripe is re-striped as new immutable generations under the new coding profile, and the result is verified — the promise changes at that commit, not when the operator asks. The order of those steps matters. Switch the required profile first, before the re-striping sweep starts: otherwise a live writer can publish a fresh copy of a chunk in the old, weaker layout just behind the sweep, and the cluster ends up promising a level of protection its newest data doesn't have. Switching first means anything written from then on is already in the new layout, so the sweep is chasing a list that can only get shorter.

And "switched" has to mean every place that enforces it has been told. Deciding centrally that the new layout is in force changes nothing at the thousands of places that actually approve writes; one that hasn't heard yet will keep approving the old layout, and the sweep is back to chasing a growing list. So the switch is a barrier: push the new layout everywhere, wait for every one of them to confirm it durably, and only then start sweeping. This is the same mistake as assuming a dead client is fenced everywhere just because the decision was recorded somewhere.

Going the other way is not the same steps in reverse. Raising the protection level works because the weaker promise stays in force while stronger copies pile up — every moment along the way is at least as safe as advertised. Lowering it has to drop the promise first; writing weaker copies while still advertising the stronger promise would make the promise false for the length of the migration.

A node coming back does not repay what was lost. If a copy was written while one machine was down, that machine returning doesn't give it the copy it missed — only rebuilding does. So a stripe written short counts against the protection budget until it has actually been rebuilt, not until the machine is back. Otherwise a second failure can take out a file after what looks like only one failure. And "that machine is down" is a decision the cluster makes and records, never a guess a client makes from a slow reply — you cannot tell slow from dead by waiting.

3 · Where we're taking it

Three planes. Data: client-direct RDMA, k+f EC, versioned chunks. Metadata: 4096 shards, one Raft group each, applied to an ordered KV on NVMe. Control: membership, placement, safe re-shuffling.

One shard's write path

Where each piece of metadata lives — the decisive decision

The name index stores a small pointer, not a second copy of the inode. One authoritative inode row; many names may point at it (hardlinks).

(directory, name) -> (ino, generation, type)     // small pointer: routing + staleness check
(ino)             -> the full inode row           // the ONLY changeable copy
Names live on the parent directory's shard: create/unlink/readdir in a directory touch one shard, and readdir is one ordered scan. Mutable attributes live only in the inode row — chmod/mtime/nlink can never disagree between two copies. Two deliberate exceptions: write-generated size and times live in the file's write lanes, and a spread-out directory's own mtime/ctime live on the shards holding its entries (§3a, §3b).
The CREATE co-location rule (P2, load-bearing) — files stay local, directories scatter. Names on the parent's shard only make CREATE cheap if the new inode lands on the same shard. But "child inherits the parent's shard" has a fatal consequence: a whole directory tree would funnel into one Raft leader until each directory grew hot enough to spread. So the rule splits by kind: a new file shares its directory's shard — name + inode row in one Raft entry (inode numbers are handed out per shard, so co-location is only a question of which range the number is drawn from; inode_shard() stays a plain function of the inode number and never needs an exception). A new directory is placed on its own hash shard: inode_shard(new dir) = hash(parent, name, salt) & 0xFFF. MKDIR pays one two-shard transaction and buys an independently scalable subtree for its whole lifetime — /projectA/* and /projectB/* live on different shards from birth. Directory creation is rare; the parallelism it buys is permanent. Bounded side effect: a normal directory's files stay on its shard forever (the inode number encodes the shard), so the spread threshold caps that stranded set at thousands of rows, never millions.
Spreading triggers on pressure, not just size. A normal directory deliberately serializes creates on one leader — together is the right common case. The trigger is entries > threshold or sustained op pressure: a 100-entry directory with 100k clients never crosses the size threshold but still melts its leader. Spread is one-way.

Spreading a hot directory is a versioned layout change, not a flag. A 100M-entry directory cannot be re-partitioned atomically, and lookups must work during the move: 
LOCAL → SPLITTING(epoch e) → HASHED(epoch e)
SPLITTING: new writes → hash(parent,name) shards
           reads → check hashed, then the not-yet-moved local range
           a migrator moves names idempotently, in batches
           a mutation of a not-yet-moved name → dominating hashed TOMBSTONE
HASHED:    the owner Raft-commits the new layout; the old local range is GC'd
The epoch lets clients cache the layout and detect staleness; idempotent moves make a crash mid-split harmless. The tombstone closes the resurrection race: the hashed side always wins, so a name unlinked mid-split can never be copied back to life by the migrator (I8).
Moving a directory needs more than a look before you leap. You may not move a directory inside itself, and the obvious check — walk up from the destination and make sure the directory you're moving isn't already up there — is not enough when two moves happen at once: 
start:   /a  and  /b  are siblings
move /a into /b   — checks: b is not inside a.   Fine.
move /b into /a   — checks: a is not inside b.   Fine.
both go through → a and b are now inside each other, and nobody can reach either
Each move checked a picture of the tree that was true when it looked and false by the time it finished. The fix is to make the whole chain of parents part of the deal: every directory records who its parent is and a counter that ticks whenever it is moved, the move collects that chain at those counter values, and the commit is refused if anything in the chain moved meanwhile. One of the two moves then loses and retries. It costs a walk to the root — fine, because moving a directory is rare.

Shards spread; leaders spread

One Raft group per shard, copies = 2f+1, always on distinct machines. A majority keeps writing through any minority of losses, and is sized so committed entries survive f permanent losses. Leaders land on different machines, so metadata write throughput grows with node count. Leadership is real: elected by vote, fenced by term — rules I1–I4 hold by construction.

3a · The extremfs property — a hot file does not serialize

The make-or-break case: many parallel writers to the same file. If every write updated one inode row through one Raft group, a million writers would wait in one line while the data path sat idle.

Chunk metadata is sharded — into 64 fixed lanes the load-bearing fix

One file's chunk records on one shard = one leader's line. But 4096 lanes per file would make stat() ask the whole cluster. So every file gets exactly 64 lanes: lane = chunk % 64, and lane n sits on shard (inode_shard + n·stride) & 0xFFF with an odd per-file stride. An odd stride over a power-of-two shard count is a shuffle, so the 64 lanes are guaranteed 64 different shards — plain hashing would sometimes put two lanes on one shard and quietly give the file fewer leaders than it asked for. Lane 0 is the file's own inode shard, so a small file has no fan-out at all. Why fixed and not "derived": the lane number decides where a chunk record lives, so changing it would move nearly every record of the file. A number you can never change is not a tuning knob — better to fix it and let a file use as many lanes as it needs.

Lanes are switched on, not sized up

The inode row keeps a 64-bit map of which lanes this file has ever used. The first write into a new lane also sets that bit — so a one-chunk file has one active lane and stat() is a single read, while a huge hot file ends up with 64 active lanes and 64 independent leaders. Setting bits costs at most 64 touches of the inode row over the file's whole life, not one per write, and a big write sets every bit it needs at once.

Size + write times live with the lane P2

A lane's shard carries the chunk record plus that lane's size high-water and write mtime and ctime. An extending write commits one Raft entry: { publish G ; MAX(size) ; MAX(mtime) ; MAX(ctime) } — atomic; a crash can never leave published bytes invisible or a visible hole (I21). A million writers never touch the inode row. ctime matters here: a write updates it too, and sending that one field to the inode row would have marched every writer back to the leader we just escaped.

stat() = a distributed snapshot (double collect)

The epoch check alone only covers truncate-vs-stat — concurrent extending writers on different lanes could still assemble a size the file never had. So every lane carries a counter (lane_seq): read the inode row → collect the active lanes (seq, size, mtime, ctime) → collect the seqs again → re-check the epoch. If nothing moved, the lane vector provably existed at one instant and the MAX is a correct answer; else retry. Bounded retries, then a rare read-only transaction over the active lanes as the escape hatch. One read for a small file, at most 130 for the hottest. An explicit utimens bumps mtime_gen, so an old lane time can never resurrect. The same shape does double duty: a read that spans several chunks collects the chunk-map versions, fetches the data, and re-checks the versions — otherwise a slow reader could pick up chunk A before someone's write lands and chunk B after it, and hand back a mix that never existed. That is also why the read-ahead windows are prefetch and not a cache: a prefetched map is only good inside the one read that fetched it.

Checking version numbers is not quite enough, and the gap is subtle. A writer's changes are staged on every shard it touches before the deciding moment, so those shards look the same immediately before and immediately after the decision. A reader can therefore ask lane A "is this change final yet?", hear "not yet" and use the old value, and — after the change becomes final — ask lane B, hear "yes" and use the new value. Half of one indivisible write. So a collect also remembers every change it was told was undecided and asks again at the end; if any of them became final while it was reading, it starts over. A decision only ever happens once and never reverses, so anything it already saw as decided is safe to trust.

Sub-chunk writes = versioned compare-and-swap — with an honest envelope

Build a fresh, uniquely named candidate from the committed version; publish only-if-that-version-is-still-current; on conflict, re-read and retry. Why unique names matter: if the new version were just "the old number plus one", two writers reading the same version would both write different data under the same name — and every copy in the system is supposed to be write-once. Unique names mean the loser's copy is simply an unused leftover. Disjoint byte ranges both land. Declared envelope: a 4K write in a 128K chunk pays ~80× amplification; same-chunk 4K writes contend. efs targets HPC-sized I/O; immutable delta objects are the designed escape hatch, built only if benchmarks demand it.

O_APPEND = parallel data, serialized order and visible frontier

Reserving the end of the file is one Raft entry on the inode's shard — append order is serial by meaning. But the reservation must look at the real end of the file. A private "next append offset" counter would never notice an ordinary write to offset 1 GiB, which lands on a lane, and the next append would happily return offset 0 and overwrite the file. So the reservation reads the active lanes' end-of-file the same way stat() does and only commits if none of them moved meanwhile; an extending write bumps its lane's counter and makes a racing reservation retry. Ordinary writers pay nothing. The reserved range is then written through the ordinary parallel path. But visibility must follow reservation order: B's bytes at offset 100 only mean anything because A's reservation came first, so the visible EOF is a frontier that advances over contiguous resolved reservations — B waits for A's resolution, never for its data rate.

The protection has to last until the append is done, not just until it picks an offset. If an append has claimed bytes 100–200 and is still writing them, an ordinary write that pushes the end of the file out to 400 leaves a picture no ordering of the two can explain. So while any append is still outstanding, the lanes hold a barrier: a write that would push the end of the file past what the appends have claimed has to get in line behind them. Writes that stay inside the file, or inside the claimed region — which includes the appends' own data — are untouched, so this costs ordinary writers nothing. It is set up once when appends start and taken down once when they finish, not per append.

A client claims exactly the number of bytes it is about to write (it already has the whole buffer in hand), so a short append can only come from a failure. Every claim ends one of three ways: it completes; the client is alive and its write failed, so it says so itself and the range becomes committed zeros; or the client is gone and the session protocol does that on its behalf. The middle case matters — otherwise one live client's failed append would stall everyone behind it until somebody killed the client. No returned write is ever lost.

Publications are batched at the Raft layer

128 KiB chunks at 100 GB/s = ~800k publications a second — one transaction per chunk would make metadata the ceiling. Meaning stays per-chunk; saving is batched: many publications per Raft proposal, one group commit covers the batch.
One write call publishes atomically; the data movement does not serialize. POSIX makes regular-file reads and writes atomic against each other, so a concurrent reader may never see a mix of old and new chunks from one in-flight pwrite(fd, 4 MiB). The design: all 32 chunks are written in parallel as immutable candidates, per-lane publication intents are prepared, and one durable commit decision makes them all visible together — physical work parallel (P1), only the final visibility decision atomic. Many writers to disjoint chunks still run fully in parallel (their transactions touch disjoint keys). An explicit relaxed mode (mount option, MPI-IO-style apps that synchronize themselves) publishes chunk by chunk; it is documented as weaker than POSIX and is never the default. Honest FUSE note — an unresolved contract, stated openly: POSIX requires atomicity at the syscall, but with async direct-I/O the kernel may split one large syscall into several FUSE requests with no syscall tag. So the atomic unit is one FUSE write request, max_write is sized so the writes that matter arrive as one request, and efs does not claim full POSIX write atomicity above that boundary until this is solved (kernel operation grouping, deliberate short-writes, a syscall transaction ID, or a strict mode that disables the splitting are the investigation paths). A kernel-interface limitation, not a protocol gap.

3b · POSIX composition — protocols, not intentions

The boundary problems between subsystems — each with a specified mechanism, not an intention.

Cross-shard transactions: concurrency control, not just atomic commit

PREPARE is conditional: it fails if another live transaction holds a conflicting intent or the key changed since read. An intent is the key's lock. Nobody ever waits while holding an intent (no-wait), so deadlock cannot form; a conflict aborts and retries with randomized backoff. The coordinator is dispersed by hash(txid) across the participants — a hot file's write transactions never funnel into one shard — and write-publication prepares run in parallel; rare namespace transactions prepare in one fixed order to minimize retries.

Not everything a transaction touches is a lock. Two writers publishing different chunks that happen to share a lane also both bump that lane's "largest size seen". If that counter were treated as a lock, the two would collide over nothing — and the queue we just removed from the inode would reappear on the lane. So a transaction separates keys it owns exclusively (the chunk record, a name, an inode row) from running maxima it merely contributes to (lane size and times). Maxima are carried along and folded in at the end; they never block anyone. But "not a lock" must not mean "not visible". A maximum counts from the moment its transaction is decided, which can be well before the tidy-up that folds it into the stored value — otherwise a stat() could report a size older than a write that has already returned to the application. So pending contributions are kept where a reader will find them, and reading a lane means "the stored value, plus anything already committed but not yet folded in". And when a reader meets an in-flight transaction it must find out the answer: committed → new value, aborted → old value, undecided → old value — but "I couldn't reach anyone to ask" is an error, never "it isn't there".

A third kind: things a transaction needs to stay true while it finishes. Several operations depend on something they looked at rather than something they change — an append needs the end of the file to hold still, a directory rename needs the chain of parent directories not to be re-parented under it, a rmdir needs the directory to stay empty. Re-checking a version at the last second is not enough, because the change can land in the gap between that check and the decision. So a transaction can place a guard: a note that says "this must not change until I am done". Guards are shared — any number of readers can guard the same thing — and only a change to the guarded state conflicts with them.

rmdir shows why a version check could never have worked. "This directory is empty" is a claim about entries that do not exist, and a file created in the meantime has no version to compare against — it simply appears:

rmdir : shard 17 holds nothing        → "empty"
create: puts foo on shard 17
rmdir : commits on what it saw earlier → a directory deleted with a file in it

So each shard keeps a small counter that ticks on every change to that directory's entries, including new ones, and rmdir guards those counters. Now the create and the rmdir genuinely collide, and one of them loses. The alternative — an exact running count of entries — would put every create in the directory back through one place, which is the whole thing spreading exists to avoid.

Client sessions: who is dead is decided by consensus, not by a timer

Locks, open-unlinked files, append reservations, and duplicate suppression all hinge on "the client died" — but a network partition looks exactly like a death. So every client runs under a session (client_uuid, session_epoch), committed via Raft on a sharded session authority. Heartbeat loss only decides when to try replacing a session; consensus decides which session is authoritative.

Ending a session is a barrier, not an announcement. Writing down "the new session is epoch 12" does not stop anyone: a shard that hasn't heard the news, and is going by what it last saw, will happily keep accepting work from the dead client. So each session records which shards have ever acted for it, and replacement runs in three steps: freeze that list, tell every shard on it to stop honouring the old epoch and wait for each to say done, and only then declare the new session live. Nothing that assumes the old client is gone — releasing its locks, dropping its open files, settling its append reservations — happens before that last step. A shard we cannot reach makes the new session wait; that is the right trade, and it costs nothing in practice, since a shard nobody can reach cannot serve the old client either. Registering a shard happens once per shard per session, never on the I/O path.

Once the barrier completes, the old session is fenced everywhere: its locks drop, its open references retire, its pending append reservations resolve as committed zero holes, and its retries are still recognized as duplicates — from a bounded record (a watermark plus a small window), not a permanent row per operation. That record is thrown away when the client says it got the answer, not after a timer. Nothing in the failure model puts a limit on how late a message can arrive, so a clock can never prove a straggler is gone; the client reports how far its replies have got, and anything below that line is safe to forget — and that line has to be unbroken, since replies arrive out of order and "the highest reply I've seen" would let reply 100 authorize throwing away reply 99 while 99 is still being retried. Keeping the actual answer matters, not just "this finished": if an append's reply is lost, the retry has to get back the same offset, or it grabs a second piece of the file and leaves a permanent gap. A client that has been fenced can never report anything again, so waiting for its line to move would keep its records forever; instead, once the fencing barrier is done, everything from that old session is dropped at once and any straggling request is turned away on its session number alone. A partitioned-but-alive client can lose its session — an availability sacrifice, never a safety one. Storage targets never check sessions: an orphan fragment written by a fenced client is harmless, because only metadata can make it visible (P3). Open files are tracked as one open lease per (file, session) on the inode's shard — committed at the session's first open, dropped at its last close or on fencing — so an unlinked file is reclaimed exactly when no name and no open lease remain (I19), once per session per file, never per I/O.

Distributed POSIX locking

fcntl/flock records live on the inode's shard — one lock authority per file, mutated through Raft. Serializing lock management is accepted: the application asked for coordination. Dead clients' locks are reclaimed through the session protocol. Linux has three lock families but only two groups that can block each other, and it is easy to get this backwards: classic fcntl and OFD fcntl locks are the same kind of byte-range lock and do block each other — even inside one process using one handle — while flock is off on its own and never blocks either of them. Who owns a lock is a separate question from what it blocks, and getting it wrong breaks ordinary programs: a classic fcntl lock belongs to the process, while flock and OFD locks belong to the open file itself — so copies of that handle, including ones a child process inherits, share the lock rather than fighting over it. Advisory locks never fence the data path.

All of this is filed under the file's incarnation number, not its inode number. Inode numbers get reused; a late-arriving "close" or "unlock" for the file that used to have that number must not release something belonging to the file that has it now.

A blocking lock request just waits at the file's lock authority and is answered when it is granted — first come, first served, no polling, no timers. If that authority's leader fails over, the client re-asks under the same request id, so a grant that landed just before the failover is found, not double-granted. If the waiting client dies instead, the fencing barrier cancels its wait. Unlocking part of a range splits the record, adjacent pieces merge back, and a per-file record cap turns abuse into ENOLCK. Deadlock detection covers cycles inside one file — that authority sees all of those. Cycles spanning several files are not detected: POSIX allows that (it says a deadlock error is optional), even Linux only checks classic fcntl, and no wait is ever stuck — a signal interrupts it and fencing tears it down.

File-data cache coherence: direct-I/O, correctness first

Fresh metadata is defeated if B's kernel cache serves stale data after A's committed write. Decision: bypass the kernel page cache for file data (direct-I/O) — data visibility is then exactly as strong as metadata visibility, with no coherence protocol to get wrong. Leases may come later, only if they measurably pay.

Times only move forward — because we make them easy to miss

Saying "only an explicit request can set a time backwards" quietly assumes the machine's clock only moves forward, and it doesn't — clocks get corrected, sometimes backwards. Everywhere else this design refuses to trust clocks, so it can't start here. Implicit updates (writes, chmod, and so on) therefore take whichever is later, the stored time or now, so a clock correction can't drag a file's timestamps back. The trade is that just after a backwards correction a file's time can read slightly ahead of the wall clock until it catches up: a deliberate choice suited to HPC, not bit-exact clock behaviour.

mmap: decided, not implied

Coherent cross-client MAP_SHARED is a hard coherence problem: unsupported initially (mmap'd writes rejected or write-through, same-client visibility, documented). MAP_PRIVATE is unaffected.

readdir concurrency contract — explicitly weak

As POSIX allows: every returned name existed sometime during the scan; no name twice; telldir cookies survive a leader change (the KV state is scanned, not the leader). No point-in-time snapshot — a concurrent create may or may not appear.

Timestamps: exact semantics, no inode bottleneck

A write updates two of POSIX's three times — mtime and ctime — so both live in the lanes, not the inode row; else every write would queue on the inode's shard for the sake of one field. Explicit changes set the inode row's base_mtime/base_ctime; stat() takes the MAX of the base and the lane values under the epoch check. POSIX's distinction is kept exactly: chmod changes ctime, not mtime. Only one operation needs a version guard, and it is not chmod. A guard is only ever needed for a time that can be set backwards, and only utimens can do that. Everything else — writes, chmod, chown, link, truncate — only ever moves a time forward, so taking the MAX is already right. Guard ctime as well and you create the bug you were trying to avoid: a chmod would bump the version, the last write's mtime would be filtered out as stale, and mtime would jump backwards. So utimens bumps mtime_gen, only lane mtimes are filtered, and ctime is a plain MAX. atime is a decision, not an omission: a true access time would turn every read into a write, so noatime is the default — reads do not touch atime at all, exactly as Linux noatime means — relatime is a mount option paid for off the read path, and strict per-read atime is deliberately not offered.

A directory's times must spread with it easy to miss

POSIX updates the containing directory's mtime/ctime every time an entry is created or removed. So a spread-out directory whose creates land on 60 shards, but whose timestamp lives on its home shard, still sends every create back to that one shard — the spread would be defeated by a timestamp. Fix: a hashed directory keeps its own running mtime/ctime on each shard that holds its entries, so a create is one entry on one shard, and stat() on the directory takes the MAX over the shards actually used.

That only works if "the shards actually used" is a small number. If a directory's entries could scatter over all 4096 shards, then reading its timestamp would mean asking 4096 places. So a spread directory uses 64 shards, picked the same way a file's 64 lanes are, and remembers which of them it has used in a 64-bit marker on the directory itself. Different directories get different sets, so a million directories still cover the whole cluster. Two details follow from that: the very first entry to land on a new shard has to note it on the directory (at most 64 times in the directory's life — the one case where a create does touch the directory's own shard), and setting a directory's time backwards needs the same version-number trick a file's does.

Truncate is a content-epoch bump — and the bump has to be delivered. Bumping the epoch invalidates the lanes' size and time marks in one stroke and causes any write still in flight under the old epoch to be refused at commit (I22). A write under epoch E is ordered before the bump to E+1, and a stale epoch-E publication is harmless (P3). But the lane leaders are the ones who have to refuse those writes, and ordinary writes must never talk to the inode's shard — so writing the new epoch on the inode row alone would fence nobody. Truncate pays instead: it fences the inode row plus the file's active lanes — at most 65 places, for an operation that stops the whole file anyway. And it must delete the records past the new end, not just ignore them. Shorten a file to zero, leave the old chunk records lying around, then write 4K into one of those chunks: the write picks up the old chunk as its starting point and 124K of supposedly-deleted data comes back. So the same fence deletes them — cheaply, because the store is sorted and a lane holds every 64th chunk in order, so it is one range delete per lane, not one per chunk: 64 operations to shorten a 1 TiB file. What it does not do is throw away data below the new size: shortening a file to 100 bytes must keep the first 100 bytes, and those records survive untouched. Making the epoch part of a chunk's name instead would have either hidden the surviving data or forced a truncate to rewrite millions of records.

The chunk the new end lands in the middle of is part of the same step. Shorten a file to 100K when chunks are 128K and the leftover 28K has to be gone for good — if the file grows again those bytes must read as zeros, not as whatever used to be there. So that one chunk is rewritten with its tail zeroed and stored first, and then the new length, the epoch bump, the deletions and that rewritten chunk all become real in a single step. Doing the rewrite afterwards would leave a moment where the file claims to be 100K long while the old bytes past 100K are still readable. If another writer changes that chunk in the meantime, the truncate starts over.

Storage targets are dumb; metadata decides — and metadata checks the receipts. A fragment (file id, chunk, version, fragment, coding profile) is immutable; writing it is idempotent, and the "file id" carries the file's incarnation number so a slow write for a deleted file can never land inside the file that reused its number. A target checks placement epoch, its own incarnation, and object identity — it does not order versions and does not check client sessions. Because nothing on the storage side enforces the layout rules, the publication step is where they are enforced: the write carries its receipts (which targets acknowledged, under which coding profile and placement), and metadata refuses a publication whose receipts don't match the current layout — so a client working from an out-of-date map can write a perfectly durable stripe to the wrong machines and still not make it visible (I15, I20).
Every stored piece carries a checksum (I25). Erasure coding is oddly bad at corruption: hand it a fragment whose bits rotted and it will rebuild the data confidently and wrongly, because the maths has no way to tell which input lied. Disks and memory do corrupt data without anyone lying, so each fragment is checksummed over both its contents and its name (a good fragment filed under the wrong name is also an error), verified before it is ever used to rebuild, and treated as missing — and repaired — if it fails.
The EC publication rule — the durability floor. 2+1 can rebuild from any 2 fragments — but publishing after 2 durable ACKs loses the write if one of those 2 machines dies. Healthy rule: all k+f fragments durable before publication; latency tracks the slowest target, hidden by queue depth — never by weakening the guarantee. Exception: with u domains already down, publish with ≥ k+(f−u), mark degraded, re-stripe on repair. Degraded is for unavailable targets, never slow ones.
write() = durable is a deliberate latency-for-durability trade. POSIX requires durability only at fsync(); efs makes every returned write durable. Small-write latency pays; throughput is recovered through parallelism and batching — not by weakening the guarantee. Benchmarked against the strict-POSIX alternative before final. "Durable ACK" is defined precisely: it means the target completed the required persistent-NVMe operation (NVMe flush / FUA, or power-loss-protected media) — not that the RDMA WRITE completed; RDMA completion says nothing about the NVMe durability boundary. The same holds for a Raft follower's ACK (log entry at the defined persistence level, not a volatile write cache). "Returned write == durable" is only as strong as this definition.

3c · The hot-path implementation contract

§3–§3b make linear scaling possible. This contract makes it actual. Each item is a requirement, not a tuning suggestion.

FUSE must not re-serialize what efs parallelized hidden serializer

Without parallel_direct_writes, Linux serializes same-file direct writes above efs — P1 violated before we see the request. Required, not tuning: FOPEN_DIRECT_IO, FOPEN_PARALLEL_DIRECT_WRITES, FUSE_CAP_ASYNC_DIO, FUSE_CAP_PARALLEL_DIROPS, large max_write/max_pages/max_background.

And some of it we cannot fix from here. Today's Linux still takes an exclusive lock on a file when a direct write makes the file longer, even with parallel_direct_writes on; it does the same for O_APPEND; and it locks the parent directory for every file creation (the "parallel directory operations" flag only covers lookups and listings). These locks are per mount, so a job spread over 64 machines never meets them — but 64 processes on one machine sharing one mount can queue up in their own kernel before efs is even asked. Creating the file at its final size turns lengthening writes into ordinary ones and avoids the first case; the other two have no workaround today. This is written down as a known limit of the current kernel interface, not quietly folded into "efs scales".

Direct-I/O kills kernel readahead → the client owns prefetch

FUSE direct-I/O bypasses the page cache and does no read-ahead — a naive client reads in lockstep and never fills the hardware queues. The client runs an async prefetch pipeline (read N → prefetch N+1, N+2, …, adaptive depth). A requirement of the direct-I/O decision, not an extra.

Multi-Raft runtime — 4096 logical groups ≠ 4096 mini-databases

No per-group timers, logs, syncs, sockets, or threads (~1365 leaders per node on a 3-node cluster would do bookkeeping instead of work). A few reactor threads drive many shard state machines; messages batched by destination, heartbeats coalesced, WAL group-committed across groups, KV applies batched. Each shard keeps its own logical order.

NUMA-local, queue-depth-driven execution P4

NIC queue → reactor core on its memory domain → local NVMe queue; buffers stay memory-local. Ordinary PUT/GET and commits take no cross-core lock, no thread handoff. SPDK or io_uring is an implementation choice; the absence of cross-core coordination on the common path is the requirement.

Traffic isolation between planes

Saturation and responsive metadata fight without isolation. Raft / membership / transactions / small RPCs get their own RDMA queues and credits — latency isolation from bulk data. On NVMe: log, KV, fragments, and rebuild have separate queues and backpressure.

Rebuild is distributed and rate-limited

Repair is deterministically assigned, reads k surviving fragments from distributed peers, writes the replacement — spread, never centralized. Priority: foreground I/O > metadata > rebuild. Rebuild consumes unused bandwidth only.

Read freshness is amortized, not per-request

No client caches + a majority check per lookup would flood leaders. The leader batches: one majority-backed freshness check serves every request it covers. Consistency unchanged; redundant synchronization removed.

Sequential reads fetch chunk maps in windows, not per chunk

100 GB/s = ~800k chunks/s — one metadata lookup per chunk would make metadata the ceiling even with a perfect data path. The lanes make the fix cheap: lane i holds chunks i, i+64, i+128, …, so one range request per lane covers a contiguous file window, and the prefetch pipeline runs the metadata window ahead of the data window. Per-chunk lookups remain only for true random I/O.

One trip to the disk should cover many operations

Batching is binding on every hot path: many publications per Raft proposal, WAL group commit across groups, batched KV applies, amortized read freshness. Paying a separate flush to disk per chunk, per record, or per shard when one flush could have covered thousands is a contract violation, not a slowdown. Stated honestly: we don't claim zero flushes — a returned write is durable, so something must reach the disk before it returns. What must never happen is paying that cost once per operation when it could be shared.

4 · Why the theory holds up

Raft-per-shard over an embedded KV is not a new mechanism. The claim is stronger than novelty: the design follows from the constraints — a derivation, not an analogy. A copy-cat imitates a working system; a derivation starts from what must be true.

The constraints are forces, not preferences

The constraints do not mathematically force "Raft + ordered KV" — Multi-Paxos, Viewstamped Replication, B-tree/LSM stores satisfy the same forces. The honest statement: the constraints strongly favor a partitioned, replicated state machine with persistent, paged state; efs chooses Raft and an ordered embedded KV because they satisfy that with proven, understandable primitives. That Ceph and CockroachDB landed in the same place is convergent evolution — evidence the derivation is right, not that it was copied.

Safety = inherited theorems + explicit composition obligations

  • Core shard-replication safety is inherited from Raft, implemented to its assumptions. Leader completeness (I2) is Raft's theorem — not majority intersection alone.
  • Quorum durability (I10/I11): a majority-acked write survives any f permanent losses because the majority is sized to outlive f. The old root-2PC never had this — its decision point was one under-replicated node — and the bug history is the system repeatedly discovering that.
  • The composition is not covered by Raft's proof. RPC dedup, KV persistence ordering, cross-shard transactions, FUSE cache coherence, EC generation publication, chunk read-modify-write, reconfiguration, orphan lifecycle — explicit simulation obligations. That is what the simulator is for.

What is genuinely ours — stated precisely

Every primitive here has existed — Raft, distributed metadata, RDMA, EC, immutable generations, ordered KV, directory sharding, deterministic simulation. WEKA, DAOS, VAST, CephFS each get close to parts. IndexFS/GIGA+ precede threshold-spread dirs; FoundationDB is the canonical simulator. We claim none of these as inventions.

The claim is the composition and the principle. We know of no public system presenting this as one open POSIX filesystem: POSIX + no MDS tier + metadata authority on ordinary storage nodes + Raft only for small metadata + client-direct RDMA + immutable EC generations + no invented serialization + simulation-first + small-cluster simplicity. The principle: never serialize work that semantics and hardware allow in parallel.

Metadata on a log, data on versioned EC

Strong consensus where correctness is cheap (small metadata); EC where bandwidth matters (bulk data). Most systems pick one substrate for both.

A hot-file path that does not serialize

Disjoint chunks publish to different metadata shards via bounded lanes; size and mtime are sharded high-waters; sub-chunk writes are versioned compare-and-swap. Only semantically-required serialization is serialized.

The namespace is the database

Metadata is already a distributed ordered KV, so du/find/lifecycle are queries, not traversals — no crawler, no catalog, no cron forest.

Minimalist operations

3 nodes → efs init → efs mount → done; 64 nodes, same architecture. No MDS tier, no special node types, no kernel module.
Thesis in one line: the constraints force the family, Raft + KV are the proven primitives in it, and the composition — plus the never-serialize principle — is ours. The principle is falsifiable: if hardware could parallelize a workload and efs serializes it, that is a bug.
On the name. "extremfs" collides phonetically with XtreemFS (trademark, Quobyte); "EFS" is overwhelmingly Amazon Elastic File System. The idea is the identity; the public name is left open pending a trademark/search check. This document uses "efs" as a working name only.

5 · Why it reaches the target

The RAM wall, drawn to scale

A cache miss must never turn into "not there". Once RAM is a cache in front of the KV rather than the store itself, every miss has to be answerable from local disk. When it cannot be — an I/O error, corruption, or an evicted entry whose backing is gone — that is a resource problem and must come back as a retryable error, never as "no such file" (I9). This is not hypothetical. A cache whose miss path is allowed to fail quietly is exactly how a row that is still alive comes to read as missing, and on the read path that mistake cannot be undone: a lookup that wrongly answers "absent" invites the next create to allocate a second inode for an object that already exists.

6 · Invariants — the rules that define "bug"

A bug is a violation of one of these rules. The simulator checks them after every step; fsck checks them on disk. Rules are stated over the committed, externally visible state; transaction intents are internal (I17/I18).

Replication & leadership (Raft's actual safety properties)

I1 · election uniqueness — at most one server is elected leader for a shard in a given term.
I2 · leader completeness — every later elected leader contains every previously committed entry (Raft's theorem, not majority-intersection alone).
I3 · term fencing — a node that sees a higher term immediately stops exercising old-term leader authority.
I4 · majority acknowledgement — no mutation is acknowledged unless committed under the shard's current authoritative config. "No dual owner" = commit authority, not local belief.

Metadata state

I5 · name uniqueness — one visible name maps to at most one inode.
I6 · no visible dangling name — every committed visible name resolves to a valid inode.
I7 · nlink — nlink equals the number of committed visible links.
I8 · no resurrection — a committed removal is never reverted by replay/recovery/rebuild/stale clients.
I9 · absent ≠ unavailable — failing to establish authoritative read state never returns ENOENT; it returns an error saying "I could not find out", not "it is not there" — usually one worth retrying, occasionally a final one (a corrupt copy with nothing left to repair from), but never "absent". This is a safety rule, not a nicety about error codes: if a lookup wrongly says a name is absent, the next create makes a second inode for an object that is still alive — which breaks I5, I6 and I7 and leaves no trace that it happened. (the Sep 1 dangling-dentry class)
I10 · metadata durability — an acknowledged committed op survives any f simultaneous permanent node losses, for the configured f (quorum is always bigger than f, so a survivor always holds it).
I16 · request idempotency — replaying a mutation with the same op-ID cannot apply its effect twice.
I17 · transaction atomic visibility — a cross-shard transaction is visible as committed everywhere or nowhere.
I18 · safe reconfiguration — no config transition permits two disjoint authoritative majorities for the same history.
I19 · open-unlinked lifetime — an nlink=0 inode stays valid for pre-existing authorized open handles; never reclaimed/reused while valid.

Data

I11 · EC durability — a generation published in a healthy cluster has all k+f fragments durable on distinct failure domains (any f losses leave ≥ k to rebuild from). A generation published while u domains are already unavailable has ≥ k+(f−u) durable fragments, is marked degraded, and is repaired when capacity returns.
I12 · chunk consistency — every returned chunk is one valid committed generation and a legal serialization of committed byte-range writes.
I13 · generation coherence — reconstruction never mixes fragment generations. Version names are globally unique and carry the file's incarnation, so no two writers and no two lives of one inode number can ever put different data under one name.
I14 · publish-after-durability — metadata cannot publish G before G satisfies EC durability.
I15 · orphan-generation safety — unpublished generations are reclaimable without changing committed state.
L7 · reclamation — any generation no chunk record still points at is eventually reclaimed: the ones never published (a lost race, an abandoned write) and the ones that were published and are no longer reachable — everything a truncate cut away, and every old-layout copy a re-stripe replaced.
I20 · stale-writer fencing — a stale client/node cannot overwrite or publish over a newer committed chunk generation.
I21 · publish+size atomicity — an extending write never commits its chunk publication without its size-lane update, nor the reverse; they are one Raft entry on one shard.
I22 · epoch fencing — a write still in flight under a superseded content epoch is never committed, and stale-epoch lane values are never read. The epoch fences work in progress; it does not discard data already stored, so shortening a file keeps the part that survives.
I23 · session fencing — a fenced session can perform no authoritative mutation: no metadata commit, no data publication; no lock, open reference, or append reservation of a fenced session survives it. Metadata leaders enforce the epoch; storage targets need not. Fencing is a barrier: nothing that assumes the old session is gone may happen until every shard that ever acted for it has confirmed it will not do so again.
I24 · atomic write publication and atomic observation — a returned write is visible in its entirety to every later read; a concurrent read sees all or none of an in-flight call's chunks (default mode). The duty runs both ways: a read spanning several chunks must also come back with a picture that really existed, so it re-checks the chunk versions it used. Committing a write in one stroke does not stop a slow reader from stitching an old chunk to a new one.
I25 · end-to-end integrity — every stored fragment carries a checksum over its contents and its name. A fragment that fails the check is never used to rebuild anything; it counts as missing and is repaired.

Liveness (bounded, testable)

L1–L8 — shards eventually elect leaders; committed ops eventually apply everywhere; intact and empty replicas eventually catch up; prepared transactions eventually COMMIT/ABORT; orphans and unpublished generations eventually reclaim; reconfiguration eventually converges once failures stop.

7 · The simulator — build first, architecture-independent

N servers + M clients in one process. A seeded random generator drives message order, drops, delays, duplicates, partitions, crashes. The real metadata state machine runs inside it, against a simulated network and disk.

A scenario runs in milliseconds. A failure replays exactly from its seed. Millions of interleavings overnight, each step checked against the rules — a bug is a seed + a named violated rule, not a log line on a live cluster. The hardware cluster stops being the correctness oracle and becomes the performance harness.

The generator must produce: lost/duplicated RPCs; restarts with same or empty disk; delayed packets from a prior incarnation; leader crash at every point around commit/apply/reply; interrupted snapshots and membership changes; coordinator/participant crash in every transaction phase; client crash between fragment PUT and publish; stale placement maps and chunk generations. Complete histories are checked by an independent linearizability checker, not only handwritten rules (the FoundationDB method). Scope: the logical data-commit protocol and its interaction with metadata — else I11–I15 / I20–I22 are uncheckable. Not RDMA/NVMe mechanics; those stay with the perf harnesses.

The bottleneck is not writing code — it is how long a change takes to prove itself. Strategy: push each bug class to the cheapest layer that can catch it.

The simulator is the layer that is both fast and deterministic. Unit tests can't see a message race; the cluster can't reproduce one. It converts the slowest, noisiest part of the cycle into the fastest and most repeatable — and is the regression gate for every migration step after. It is in the tree and gated (test_sim); production efsd is not on it yet.
  • Correctness moves down, performance stays up. The cluster confirms speed, not correctness.
  • Deterministic over flaky. Forced collisions, not fork-and-pray — no more "passes isolated, fails under load."
  • Fail fast, not timeout. A violated rule aborts at the step; saturation is reported separately from correctness.
  • Live attach over rebuild-and-reprobe. gdb -p on a wedged efsd answers in seconds.
  • Bounded-context change. Load one module + its header, not the whole tree.
  • Rules as executable checks (simulator assertions + fsck), not prose.

Modularity is an architectural constraint, not a style preference

The rule: a module must be understandable, changeable, and testable from its own source plus its interface header alone. If you have to read the rest of the tree to change one component safely, the modularity has failed.

The bar, stated plainly: a less advanced AI model must be able to contribute a correct change. (1) Local correctness must be locally decidable — module + header + tests, never global reasoning; else the project scales with model quality, not contributor count. (2) A mistake's blast radius is one module, failing fast and locally — a unit test, a simulator assertion, an interface check. (3) Interfaces carry the contract: invariants, ownership, threading rules live in the header. (4) Conventions are machine-checkable — enforced by tooling, not reviewer vigilance.

Why there is a step 10.5. Steps 3 and 4 built the key-value store and Raft as interfaces with in-memory implementations. That is all the simulator needs, and it proved a lot — but nothing in it writes to a disk. Meanwhile the running server still keeps metadata in memory and makes it durable with the old whole-table flush, which is exactly what step 11 deletes. Delete it first and the system stops being durable. So 10.5 goes in between: build a real on-disk key-value store, then a real on-disk Raft log, then finish the applied-state machine in the simulator, then host Raft inside efsd behind a flag (that host is in; gated on a scratch cluster) and serve LOOKUP/GETATTR from ReadIndex + KV (also in) and file CREATE as one Raft entry (also in) and MKDIR as a 2-shard txn (also in) and last-link file UNLINK (also in) and nlink>1 UNLINK as a 2-shard txn (also in). Cross-group propose and the rest of the mutations are next — not a cutover of the live table. The key-value store is done. It keeps a write-ahead log for durability and sorted, never-modified data files for the rest, merging them in the background; only one small index entry per data block stays in memory, so memory use does not grow with the number of files. We proved it by re-running the entire simulator on it instead of the in-memory store, so all the same invariants had to hold against data sitting on disk.
The Raft log is done too, and it decided something worth stating plainly. There is one log file per machine, not one per shard group: every group writes its records into the same file, and when several groups write at once they share a single flush to disk. Thousands of groups therefore cost one stream of disk flushes instead of thousands. Each record says which group it belongs to, so on restart a group's state is rebuilt by reading back just its own records. A half-written record at the end of the file is what a crash looks like, so it is thrown away — but a record that is intact and still makes no sense means the file is damaged, and then we refuse to start rather than come up quietly missing writes.

What is the durability boundary? A write could be made safe twice — once in the Raft log, once in the key-value store — but that is one disk flush too many. Instead the Raft log is the only place durability lives, and the key-value store is treated as a view that can be rebuilt by replaying the log from the last snapshot. That is already how the Raft code behaves on startup, so it cost no new machinery — only one rule: never take a snapshot until the key-value store has safely stored everything applied so far, because a snapshot throws away the log entries that would otherwise rebuild it. We proved the whole thing the same way as the key-value store, by re-running the entire simulator against it, with one addition: in the simulator a machine restarting now genuinely closes and reopens its log file, so every crash the simulator invents becomes a real replay from disk. We also checked the check — deliberately breaking replay makes those tests fail, so passing them means something.
Read the map bottom-up: the data path, test harnesses, and simulator are the strong foundation. On-disk KV and the Raft log are gated in the simulator; production efsd still makes metadata durable with the old whole-table flush. The remaining metadata work is finishing the applied-state machine in-sim, then putting a new export on that engine — not a cutover of the live table.

9 · Migration — gated, never a big bang

Step 1 has a hard prerequisite: the carve-up (Phase M). The simulator can only reuse a state machine that is already pure — and today the state machine is fused with its I/O. So the first move is carving the monolith into modules: behavior-preserving, gated by the existing suites. Nothing in steps 2–11 is built as new monolith code.

Each step is gated; the system stays runnable throughout. Details live in the scaling roadmap.
