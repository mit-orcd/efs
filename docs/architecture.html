The binding constraint is 232 on 4 nodes. That single number forces metadata out of RAM and onto NVMe, and forces the store to be paged rather than serialized whole.

2 · What we have today

One monolithic in-RAM table. Every flush serializes the whole table to find what changed, erasure-codes it into pages, and commits a root with two-phase commit. Leadership is “lowest live node id from each node's own local view.”

thinks is alive no term · no vote · no fence → split-brain EVERY BUG BELOW IS A FAILURE MODE OF THIS MODEL dual-writer root · extras-loss-on-adopt · catchup-vs-GC · peers pinned at old gen · rebuild drops unflushed ops

RAM is the wall blocks 2³²

The whole table lives in RAM on every server. Measured 1.9–3.4 KB/inode. 232 × 512 B of inode region alone ≈ 2 TB before overhead.

Flush degrades with size O(table)

incr=0 on 100% of flushes during growth; ser=350ms/flush at 10M. Eviction faults slabs straight back in — it accomplishes nothing.

No consensus split-brain

Primary is a pure function of unreplicated local liveness. Two primaries are possible. 2PC blocks or diverges on coordinator failure — that is what Raft/Paxos exist to fix.

Absent ≠ unavailable data loss

A failed slab fault returned ENOENT, so CREATE minted a second inode for a live object. The system cannot tell “not there” from “couldn't read it.”

3 · Where we're taking it

Shard the inode space. Each shard is an independent Raft group that appends every mutation to a replicated log and applies it to an on-disk ordered key-value store. RAM becomes a bounded cache. This is the Ceph PG / CockroachDB range model.

A log only ever writes what changed. There is no whole-table serialize, no CoW page placement, no GC of referenced pages, no extras-merge, no 2PC, no catchup-vs-GC race. Those subsystems are deleted, not patched — and with them the entire bug class they generate.

Leadership is now real

A leader is elected by a majority vote in a term, and a node that sees a higher term stops serving writes (fencing). Two leaders cannot both get a majority. That is invariant I1–I4 by construction — not by careful coding.

Many shards, spread leaders

Shards are cheap; a node hosts many. Leaders are spread across nodes, so metadata write throughput scales with node count — there is no single metadata primary to saturate.

4 · Why the theory holds up

Let's be precise about what is and isn't claimed. Raft-per-shard over an embedded KV is not a new mechanism — and the doc says so. The claim is stronger than novelty: the design is a consequence of the constraints, and the argument for it is a derivation, not an analogy. A copy-cat cites a system that works and imitates it. A derivation starts from what must be true and shows only one shape survives. Here is the derivation.

Step 1 — The constraints are forces, not preferences

Four facts about the goal act as forces that eliminate designs. None is a taste choice.

ConstraintForce it exertsDesign it eliminates

Step 2 — Each force admits exactly one answer

This is why it's not a copy of Ceph or CockroachDB. Those systems independently arrived at the same shape because the same four forces act on any strongly-consistent, horizontally-scaled, fault-tolerant store. We are not imitating their solution — we are solving the same equations, and the equations have one solution. Convergent evolution is evidence of a correct derivation, not of imitation.

Step 3 — The safety properties are theorems, not testing goals

The reason the current system produces the same bug family forever is that its safety rests on careful coding — and careful coding does not compose under message reordering. The target rests on two results that are proven, not tested:

  • Majority intersection. Any two majorities of a fixed set share a member. So an election (needs a majority) and a committed write (needs a majority) always overlap on at least one node — which is what guarantees a new leader learns every committed entry. This is I1, I2, I4, and it is arithmetic, not engineering.
  • Quorum durability. A write acknowledged by a majority survives any failure that leaves a majority, because at least one survivor holds it. With RF=3, that is exactly one node. This is I10, and it is why "survive 1 node down" is a theorem here and a hope in 2PC.
2PC fails the second theorem by construction: its commit point is the coordinator, a single node, so coordinator loss mid-commit blocks or diverges. That is not a bug in our 2PC — it is what 2PC is. The bug history (dual-writer root, peers pinned at an old gen, adopt-before-pages-local) is the system repeatedly discovering that its commit protocol does not satisfy quorum durability. A design whose safety is a theorem does not have a bug budget for that class — the class is excluded by the proof.

Step 4 — What is genuinely ours

The mechanism is proven and shared. What is specific to efs — and where the real design work lives — is the composition:

Metadata on a log, data on EC — decoupled

Strong consensus where correctness is cheap (small metadata), erasure coding where bandwidth matters (bulk data). Most systems pick one consistency substrate for both; efs puts each on the substrate that fits its cost model.

POSIX on sharded consensus

rename / hardlink / unlink-while-open are cross-shard. The two-phase + reconcile rule that keeps POSIX atomicity without a global lock or a global consensus group is the part that is not in any textbook.

The inode record shaped for the KV

The 512 B self-contained row (Cut A) and the (parent, name) + (ino) key split are designed around the store, so readdir is a range scan and lookup is a point get — not bolted on after.

Deterministic simulation as the gate

Making the whole thing testable in-process from a seed is what turns "the theory holds" from an argument into a checkable artifact.
The thesis in one line: the constraints force the shape, the shape's safety is a theorem, and the part that is ours — the composition with EC data and POSIX semantics — is where the design earns its keep. That is a stronger position than novelty: a novel-but-unproven design is a risk; a derived-from-first-principles design on proven primitives is a foundation.

6 · Invariants — the test oracle

A bug is a violation of one of these. The simulator (§7) checks them after every step; fsck checks them on disk.

Replication & leadership

I1 · single leader — at most one leader per shard per term; only a majority vote in that term elects.
I2 · leader completeness — a committed entry is present in every later leader's log.
I3 · fencing — a node that sees a higher term rejects writes and stops applying.
I4 · no dual owner — at most one node serves writes for a shard (follows from I1+I3).

Metadata state

I5 · name uniqueness — within a directory, a name maps to at most one inode.
I6 · no dangling dentry — every dentry points to an existing inode row.
I7 · nlink — nlink equals the number of dentries naming the inode.
I8 · no resurrection — a committed unlink is never undone by a flush, report, rebuild, or leader change.
I9 · absent ≠ unavailable — a lookup that can't reach the store returns EIO/BUSY, never ENOENT. (the Sep 1 dangling-dentry class)
I10 · durability — an acknowledged op survives any single-node failure.

Data

I11 · chunk durability — an acknowledged chunk has ≥ 2 of 3 fragments on distinct nodes.
I12 · no torn chunk — a read returns the old chunk or the new chunk, never a mix.

7 · The simulator — build first, architecture-independent

A deterministic discrete-event simulator: N servers + M clients in one process. A seeded PRNG drives message order, drops, delays, partitions, crashes, and clock steps. The real metadata state machine runs inside it against a simulated network and disk.

A cluster scenario runs in milliseconds. A failure replays exactly from its seed. You explore millions of interleavings overnight, and every step is checked against the invariants — so a bug is a seed + a named violated invariant, not a log line on a live cluster. The hardware cluster stops being the correctness oracle and becomes the performance harness.

Nearly every bug in the project history is a message-ordering or failure-timing bug. None needed NVMe or 13 nodes to reproduce — they needed the right interleaving, which a seeded simulator hands you and printf-on-a-live-cluster cannot. This is the FoundationDB / TigerBeetle central thesis. Scope: the metadata layer only; the RDMA data path stays covered by the perf harnesses.

7a · Shortening the code → signal cycle

The bottleneck is not writing code — it is how long a change takes to prove itself. Today that proof is a 13-node wipe + rsync + rebuild + ssh orchestration, and the signal is poor: 99% of posixstress “failures” are 15s timeouts (saturation, not correctness), and a single run is noise that needs ≥3 fresh-wipe repeats. We already have the layers below; the work is to push each class of bug to the cheapest layer that can catch it, and to close the gap the simulator fills.

Each layer answers a different question. A bug should be caught at the lowest layer that can see it — and today correctness bugs fall all the way to the top because nothing in the middle is deterministic.

LayerAnswersCostCatches

Why the simulator is the next step

It is the only missing layer that is both fast and deterministic. Unit tests can't see a message race; the cluster can't reproduce one. The simulator sits exactly in that gap: it runs the real protocol against a seeded fault-injecting net+disk, replays any failure from its seed, and checks the §5 invariants on every step. Building it first converts the slowest, noisiest, least reproducible part of the cycle (distributed correctness on hardware) into the fastest and most repeatable — and it becomes the regression gate for every migration step after.

Deliberate moves that shorten the loop

  • Correctness moves down, performance stays up. The cluster stops being the correctness oracle. posix/posix2 confirm filesystem semantics; the cluster confirms speed. A correctness bug should never need a 13-node wipe to find.
  • Deterministic over flaky. Replace fork-and-pray races with forced collisions (threading.Barrier) so a test either always collides or never runs — no more “passes isolated, fails under load.”
  • Fail fast, not timeout. A violated invariant aborts at the step, not after a 15s POSIX_TEST_SEC. Saturation (a timeout) is reported separately from correctness (an assertion) so the two are never conflated again.
  • Live attach over rebuild-and-reprobe. ptrace is open on all 15 hosts — gdb -p on a wedged efsd answers in seconds what an NDJSON-probe redeploy answers in tens of minutes.
  • Invariants as executable checks (simulator assertions + fsck), not prose — so “is this a bug” is decidable without a human reading a log.

8 · Migration — gated, never a big bang

The simulator comes first because it pays for itself against the current code, before any new architecture exists — and it becomes the regression gate for every step after.
