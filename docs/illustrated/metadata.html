Metadata

Names, attributes, chunk maps, sessions and locks live in a replicated key-value store split into shards. In alpha 1.0 the shards map to two Raft groups of three voters each. A change is visible only once a majority of a group holds it.

From inode number to voters

The shard is the low 12 bits of the inode number, so consecutive numbers spread over all 4096 shards. Today every odd shard belongs to group 0 and every even shard to group 2. The root directory, inode 1, is on shard 1, in group 0.

Create stays on one shard

A new file's inode number is drawn from a range whose low 12 bits equal its parent directory's shard. The new name and the new inode row then sit on the same shard, so a create is one Raft entry, not a transaction.

A Raft group in action

Each group has three voters and one leader. Any live voter accepts a client request and passes it to the leader. A write commits when two of the three hold it. Switch voters off and send requests.

  • No clocks decide anything. A read is answered by the leader after a fresh majority round (ReadIndex), never by a time-limited lease. A deposed leader cannot serve a stale answer.
  • Uncertainty is never “not found”. If a node cannot establish authority, the client gets a retryable error. A cache miss is resolved from stored state; only a real absence returns ENOENT.
  • Clients retry smartly. The client follows leader hints, picks another voter when one is dead, and keeps the same request identity so a retry is recognised as a duplicate.

A cross-shard transaction

Operations that span shards, such as a hard link or cross-directory rename, use prepared intents and one durable decision. Intents are invisible until the decision commits. Prepares never wait, so deadlock cannot happen. Step through it and try the two failure toggles.

    What other clients see

    • A namespace change such as create, rename or unlink is visible to every client as soon as it returns. There are no time-based attribute caches.
    • File contents are visible to others after the writer's fsync or last close publishes them, see Data path.
    • readdir returns only names that existed at some point during the scan; concurrent renames are handled by the transaction rules above.
    • Directories keep their entries on the parent's shard. The hot-directory spread across many shards is after alpha 1.0.
