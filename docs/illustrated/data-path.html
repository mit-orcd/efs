The data path

A file is a series of 128 KiB chunks. Each chunk becomes two data fragments and one parity fragment on three different nodes. The client sends them itself, and a write only becomes visible when metadata publishes it.

This whole-file model checks a metadata group for each chunk; real operations can involve additional authorities. Barriers and elections are explicit steps here, not timing predictions.

Short chunks are zero-padded for encoding, but reads return only file bytes. File totals count encoded payload, excluding headers, metadata, alignment and old versions. Placement is illustrative. These are simulated barriers, not a product qualification or a promise of whole-file atomicity.

One write, step by step

  1. Buffer. A buffered write() need not wait for durability. Unpublished bytes are private to the writer; background work may publish before close. A client crash can lose bytes that have not completed the required publication and durability steps.
  2. Allocate a candidate generation. Every attempt gets a globally unique identity (never “the old one plus one”), so two writers can never put different bytes under one name.
  3. Encode and send. The chunk is cut into D1 and D2, parity is their XOR, and the three fragments go out in parallel over RDMA or TCP. Each lands as a file of 64 KiB payload plus a 4 KiB tail that carries its identity and checksum, written with direct I/O.
  4. Acknowledgements. Before it accepts a fragment, a node checks its identity and placement and asks the metadata leader whether the upload ticket is still admitted for a live, unfenced session; a fenced client is refused. It answers once the fragment is written and closed. It is then in the root's open epoch, not yet durable: a background barrier targets an approximately 200 ms window by default, or fsync requests a barrier through DATA_COMMIT. This is not a completion deadline: slow or failed barriers can delay or fail durability confirmation.
  5. Publish. The client asks the chunk's metadata group to swap the chunk map from the old generation to the new, carrying the acknowledgement evidence. The leader rejects evidence that does not match the current placement. A write that spans several chunks uses a transaction, so the chunks become visible together.
  6. Return. fsync/fdatasync prove sufficient durable fragments for every relevant stripe: two may suffice with a durably recorded degraded mark. O_SYNC/O_DSYNC writes invoke the corresponding sync path. Close drives publication; do not treat publication or a PUT acknowledgement alone as durability proof. Visibility begins at publication, not necessarily when close or fsync returns.

A crashed writer can leave fragments nobody published. Those are orphans, collected later; they never become visible. A fenced client's later uploads are refused at the storage node, which learns the sealed epoch from metadata. See Space and Sessions.

Parity is just XOR

With two data fragments, the parity fragment is their bitwise XOR. Edit the bytes, then “lose” one fragment and rebuild it from the other two.

Reads and integrity

  • The fast path reads two fragments. The client asks for D1 and D2 in parallel and joins them. Parity is only fetched when one of them is unavailable.
  • The chunk map says where fragments are. A reader uses the nodes recorded at publication and never recomputes placement, so changing the cluster does not move existing data.
  • Every fragment is checksummed. A fragment that fails verification counts as missing and is rebuilt, never decoded. Erasure coding without this would reconstruct confidently from corrupt input.
  • Reads are consistent. A read that spans chunks collects the chunk maps, fetches, and revalidates, so it never splices old and new halves of one published write. The unit of atomicity is the write request EFS receives from FUSE; the kernel may split a very large application write into several requests.

Transport and caching

RDMA or TCP

EFS_TRANSPORT=auto uses RDMA when an active device exists, otherwise TCP. rdma never falls back. Set the same value on servers and clients.

Always direct I/O

Daemons read and write fragments with O_DIRECT; a root that cannot do it is refused. The client bypasses the kernel page cache too. Direct I/O alone is not durability; the explicit sync barriers remain.

Flash only

The design assumes NVMe-class devices and deep queues. Spinning disks are out of scope.
