Space: packing, quota, reclaim, truncate, expiry

EFS publishes new data versions and reclaims obsolete objects in the background. Retries may rewrite the same fragment object; new file versions use new objects. Reclamation can lag the metadata change, so deleting a file does not immediately return disk space.

Small files get packed

Each file is first written as ordinary fragments. A per-file fragment costs a whole 69,632-byte file on each of three nodes, however small the file. A background packer moves closed files of at most 16 KiB into shared segments of up to 128 KiB, still erasure coded, and the old fragments are reclaimed.

4

Estimate: a full segment holds 128 KiB of file bodies and costs three fragment files of 68 KiB, ignoring the small per-file record. Real savings depend on how closely files are grouped.

  • Nothing changes for the application. Close and fsync behave as before; packing happens afterwards. There is no switch to turn it off.
  • It compare-and-swaps. One Raft entry moves up to 128 files, each guarded by the exact old chunk row; a file changed, opened or deleted meanwhile stays as it was.
  • It steps back under load. Packing drops to a floor while the foreground is busy and ramps up only under space pressure. efs-mgmt pack-compact NODE:PORT 0 prints the packer state.
  • Segments are compacted. Files are grouped by creation time and directory so deleting a tree empties whole segments; survivors of mostly dead segments are compacted forward in idle batches or a daily window.
  • Segments are protected too. A segment holds files only with two of its three fragments durable. A missing one is rebuilt by the group leader, and until then status shows the cluster as degraded. Two lost fragments are reported as lost and the files read EIO.
  • Segments spread over all nodes. They follow the data ring of every node, not only the metadata voters.

Deleting small files leaves holes, and holes are not refilled

A packed segment is written once, as an erasure-coded stripe, and never changed. Deleting a file only marks its record dead. New small files go into new segments, never into the hole. The space comes back in one of two ways: a segment with no live record left is retired and its fragment files are reclaimed, or compaction copies the survivors of a holey segment into new cold segments and then retires the old one. Click a live record, or focus it and press Enter or Space, to delete it.

  • Whole-tree deletes are cheap. Files are grouped by creation time and directory, so deleting a tree tends to empty whole segments, which retire without any copying.
  • Scattered deletes are not. Deleting one file in each segment frees nothing until compaction runs. Compaction is background maintenance: after 60 s of idle load, in a daily window, or on demand with efs-mgmt pack-compact. Tiny holes and cold segments go first.
  • It needs headroom. Compaction writes new segments before the old ones go, so a node keeps a reserve; without it, a node at quota could never pack its way back under it.
  • No hole punching. EFS does not punch holes in any file, so there is no partial free inside a segment.

Quota, ENOSPC and delayed free space

The quota is per node. A write needs all three fragments to fit on three distinct nodes. Write chunks until a node fills, then delete and watch the three stages: the delete, the node accepting the cleanup (quota is credited, so new writes fit again), and the files leaving the disk. New published versions use new objects. A retry of the same object may rewrite its fragment file; reclamation releases the quota held by obsolete objects rather than reusing their identity.

  • A full node is not a down node. With a member down, a write may succeed on two fragments and be recorded as degraded. With a member full, the client places the chunk again on a member that has room (four or more nodes); if none is left, the write gets ENOSPC, never a two-fragment acknowledgement.
  • A write that cannot place all three fragments on members with room gets ENOSPC. That is not permanent: space freed in the background by reclaim, a pack or a session cleanup lets a later write succeed.
  • df shows logical 2+1 capacity using cached member figures. An unreachable member keeps its last known figures, so node loss alone does not reduce df. Usage can still change as reachable members report updates; unlinks and truncates lag until cleanup is accepted. Use status for member availability. used counts fragment payload only, not metadata or logs.
  • The default quota keeps 20 % of each filesystem free (at least 1 GiB) and uses 7/8 of the rest for fragments. A node refuses to start without that headroom.

Where space goes when you delete

  1. Unlink or overwrite. Metadata changes at once: the name is gone, or the chunk map points at the new generation. Fragments are still on disk and still counted against the quota until a node accepts the cleanup.
  2. Last reference dropped. A file that is still open is kept until its last descriptor closes. Then the inode is removed and the metadata group's cleanup pass queues it, in batches, to the nodes that hold its fragments.
  3. The node accepts. It writes the batch to its reclaim journal and syncs it, refuses any late write to those inodes, and credits their bytes back to its quota. From here new writes fit again, even though the files are still on disk. A physical headroom check still guards the real filesystem.
  4. Files are deleted. Background threads remove the fragment files and retire the journal records. A crash in between replays the deletion.

Orphans take the same road. Fragments from a client that died before publishing are collected, and status reports abandoned uploads.

Truncate is logical

Shrinking a file changes one inode record in constant time, whatever the file size. Chunks beyond the new end are masked at once; their fragments are swept in the background.

Expiry

Expiry removes files at a deadline fixed when they were created inside a folder with an enabled policy. It is part of every build and has one control, the cluster expiry policy, which is off until an operator turns it on. Set the conditions to see whether an overdue file goes.

  • Files created while the policy was off never get a deadline, and turning it on later does not give them one.
  • expiry renew moves a deadline within the folder's renewal limit. A renamed file keeps its deadline. A file with a deadline cannot get a second hard link.
  • Turning a policy off keeps every file; turning it on again lets overdue deadlines act.
  • Removal goes through the same unlink and reclaim path as above, so space returns after the last close and the background cleanup.
